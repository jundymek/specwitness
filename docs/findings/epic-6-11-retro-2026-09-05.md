## 2. Post-run observations

**1. My own spec was wrong twice, and both errors survived until an implementer read the code.**

*Symptom.* AC-3 required that an infra error still reach `aggregate → persist → teardown`. The merged pipeline has never done that: `run-pipeline.ts:322-329` skips everything from the failing stage to teardown, for every stage. Separately, the spec asserted that "six other stages still use `createPlaceholderStage`"; the real count on the base was two, one of which was the file being replaced.

*Cause.* I wrote both claims from reading adjacent code and from the Epic 3 placeholder commit, not from the pipeline at the revision the story would build on. The AC-3 error is the more serious one: it describes behaviour no stage has, so an agent obeying it literally would have written a setup-specific path unlike every other stage.

*Why no story caught it.* There was no story before this one. A supervisor-authored spec gets no second reader — the planning artifacts it would normally be checked against do not cover it, and the only reviewer is the agent implementing it, who meets it after the scope is frozen.

*Fix.* A supervisor-authored spec should carry, for every claim about merged behaviour, the `path:line` read in the session that wrote it — the same rule the spec itself imposed on the implementer as Task 0 (Epic 5's e5-B). I imposed it downward and did not apply it to myself. **Action item e6.11-A.**

**2. A security defect in merged code was found three times in one run, each time one layer deeper than the last.**

*Symptom.* Under AD-3 there is no shell, so `NPM_TOKEN=… pnpm test` tokenizes with the credential as the executable, reaches `notFoundError`, and is printed unredacted. Found first in the new `setup.ts` (by alice's own review), then in the merged `gates.ts` and `data.ts` (by alice, reported not patched), then in the shared redactor itself, where `PGPASSWORD=` and `MYSQL_PWD=` were never covered at all.

*Cause.* The vocabulary that decides what is sensitive was written once and never measured against the credentials this product's own users would type. `PGPASSWORD` is libpq's standard variable and `data.reset` is exactly where it gets written, so the redactor was weakest where a real credential was most likely.

*Why no story caught it.* Each of the three sites was written by a different closed story (6.11, 3.4/4.3, and the original evidence work), and each was correct in isolation. The defect is only visible when you ask what a *declared command line* looks like when it is not a command — which is a question only the AD-3 no-shell rule makes interesting, and no single story owns that rule.

*Fix.* Landed: all three layers are closed. The value-shaped case is not — see §5.

**3. The most valuable thing the agent did three times was refuse to fix something.**

*Symptom.* Not a defect. Alice reported the `gates.ts`/`data.ts` leak instead of patching it, reported the `PGPASSWORD` gap instead of patching it, and reported the `REDIS_URL` case instead of patching it — each time naming the file as another story's and each time correct.

*Cause.* Story 6.11's spec carried the precedent explicitly (`data.ts`'s own author had done the same thing to `services.ts`), and both of my instructions froze scope in writing and said what to do with anything found outside it.

*Why this is in a retrospective at all.* Because the counterfactual is expensive. Had she patched the first one silently, the diff would have crossed three stories' files, the security sign-off would have covered code the spec did not mention, and the owner would never have been asked. Instead each finding became an owner decision, and the two the owner said yes to shipped inside half an hour.

## 3. What we learned

- **A frozen scope in an instruction is what makes a fast follow-up safe.** Both follow-ups were merged within 15 minutes of being asked for, and both stayed inside four files and two files respectively. The freeze is what let me verify them by reading the whole diff rather than sampling it.
- **Withdrawing my own suggestion cost one paragraph and saved a defect.** I proposed to the owner that the matcher's boundary rule be loosened so `PGPASSWORD` would match. Reading `SENSITIVE_SEGMENTS` before writing the instruction showed the file already documents the counterexample that breaks: loosening it enough to find `password` inside `pgpassword` finds `key` inside `monkey`. The instruction told the agent not to do what I had told the owner I would.
- **A measurement beats an argument, in both directions.** Every claim that moved a decision this run was a measured table: the redactor's covered/uncovered keys, the `REDIS_URL` shapes, the placeholder-revert experiment showing both corpus fixtures go red. None of them were long, and each replaced a discussion that would have been.

## 4. What went well

- **TDD held under time pressure**, including in both follow-ups. Every test was recorded red first, and the failure text is quoted in each PR body.
- **The corpus proved itself as a discriminator, not decoration.** The story's author reverted the composition root to the placeholder, rebuilt, and confirmed both new fixtures went red for exactly the reasons their `why` fields claim — including the failed-install fixture reaching `PASS` at exit 0 under the placeholder. That experiment is the single strongest artifact this epic produced.
- **A red fixture was answered by hand and the amendment was recorded.** When a review-driven message change broke `setup-install-fails`, the expectation was rewritten to the stronger strings and the `why` field records the amendment and its date. There is no regeneration affordance and none was invented.
- **Three review rounds on the story found three real defects**, one of them a P1 credential leak, and each was re-reviewed after its fix rather than assumed clean — e6-B applied rather than merely known.

## 5. Technical debt carried forward

- **Credentials inside URL-shaped values are not redacted, anywhere.** Measured on the merged head and reproduced by me: `DATABASE_URL=postgres://admin:s3cr3t@db:5432/app` leaks whole, and so does a bare `postgres://admin:s3cr3t@db/app` in captured output with no assignment at all. No name-based rule can reach the second one; it needs a value-shaped rule redacting the URL userinfo component. This is **more consequential than the gap this epic closed** — `DATABASE_URL` is at least as common as `PGPASSWORD`. Assessed and deliberately not built. **Action item e6.11-B.**
- **Bare `PWD` now redacts**, as an accepted collision of the `pwd` segment. Recorded here so it stays a decision: `PWD` holds an absolute path usually under the operator's home, which this project already wants out of evidence, and the name survives as `PWD=[REDACTED]`. `OLDPWD` is not caught, which is the whole-segment rule working as designed.
- **Fourteen of this file's twenty-nine action items carry prose in `status` rather than one of the three values `sprint_status.py` accepts** (`open`, `in-progress`, `done`). The convention is four epics old and predates this run; the practical cost is that `bmad-sprint-planning` cannot retire any of them from its surfaced list. Found by the auto-review of this retrospective's own commit. I made only **e6-F** canonical, because that is the one this epic closed and it should actually retire — its detail moved to a comment above the entry. The other thirteen are not mine to rewrite. **Not raised to an action item**: it is bookkeeping hygiene, and the reader of this file is a human before it is the tool.
- **AD-10 config-declared redaction patterns remain unimplemented** — carried unchanged from Epic 6, and deliberately kept clear of this epic's work. It is a different problem: this epic fixed built-in defaults that fail where a project has configured nothing, which survives AD-10 being built.
- **The closing-pipe exit-1 question** (a PASS can exit 1 under a closing pipe, an ADR-002 violation) is untouched, as the story spec directed. Carried from Epic 6 as **e6-G**.

## 6. Next-epic readiness (Epic 7 — first real dogfooding)

**The thing Epic 6's retrospective named as "the one thing that will bite immediately" is closed.** A project declaring `setup.install` now has it executed in the verification worktree before the gates, and a failed install is exit 3 with the gates stage `skipped` — not exit 1 with the branch blamed. The first dogfooding target is a pnpm monorepo whose gates need `pnpm install --frozen-lockfile`, which was precisely the case that would have inverted.

One caveat for that run, stated rather than discovered: the two corpus fixtures prove the path with POSIX shell installs and no `package.json` at any depth. That was deliberate — a fixture proving itself only with a JavaScript package manager proves something narrower than the key promises — but it does mean **the first real `pnpm install --frozen-lockfile` through this stage will happen during dogfooding**, not in the corpus. The ten-minute timeout is the parameter most likely to need revisiting there.

## 10. One story, Stage 4, and what the owner did not see

Three PRs merged without the owner reading a diff. What they saw instead was four decisions put to them: whether to spec the `gates.ts`/`data.ts` leak or fix it now, whether to do the same for `PGPASSWORD`, and — implicitly, by my holding each merge — the two CI waits.

That ratio is worth recording because it inverts the usual worry about Stage 4. The risk people expect is a supervisor merging too freely; what actually happened is that the agent surfaced three findings outside her scope and every one of them became an owner decision rather than a silent patch or a silent omission. The mechanism was not my judgement. It was that both instructions froze scope in writing and said what to do with anything found outside it, and the spec had already set that precedent before I wrote either.

The one thing the owner could not have caught from my reports alone: I verified alice's claims by re-running her measurements rather than reading her tables, and in one case (`REDIS_URL`) my reproduction is what turned a footnote into action item e6.11-B. A supervisor who trusts a well-written PR body would have merged the same three PRs and carried none of that forward.
