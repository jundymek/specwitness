## 2. Post-run observations

Each as symptom / cause / why no story caught it / fix.

**(1) The three-cohort split worked — and the wall clock did not improve, because the bottleneck moved.** This is the finding the experiment was run to get, and it is a mixed result rather than a success or a failure.

*The split did what it was for.* Epic 3 lost **~7.5h to three subscription session-limit freezes** across eight parallel agents (Epic 3 retro observation 1, action item C). **Epic 4's log contains no freeze evidence at all** — no limit banner, no resume-after-reset, no agent silent mid-turn and needing a tmux wake. Two, four and one concurrent agents did not exhaust the window that eight did.

*But the bottleneck moved to the owner's merge click, and it cost almost exactly as much.* Measured from each `verdict-chime` to each `mergedAt`:

| PR | chimed | merged | waited |
| --- | --- | --- | --- |
| #41 (4.1) | 09-01 20:27:02Z | 20:32:31Z | 5m |
| #42 (4.2) | 09-01 20:51:56Z | 20:54:30Z | 3m |
| #43 (4.5) | 09-02 00:04:52Z | 06:40:05Z | **6h35m** |
| #46 (4.3) | 09-02 01:03:01Z | 06:39:42Z | **5h37m** |
| #45 (4.6) | 09-02 01:05:40Z | 06:56:21Z | **5h51m** |
| #44 (4.4) | 09-02 01:16:17Z | 07:47:38Z | **6h31m** |
| #49 (4.4 follow-up) | 09-02 10:37:02Z | 11:19:52Z | 43m |
| #52 (4.7) | 09-02 14:21:20Z | 16:19:49Z | 1h58m |

Cohort 2 finished its work at 01:16Z with all four PRs verdicted ready, and then **the epic sat still for 6h31m** until the owner woke. The critical-path cost of that single overnight block is ~**7h43m** — within fifteen minutes of the number the cohort split was designed to eliminate.

*Cause.* A cohort's throughput is bounded by whichever human-in-the-loop step is slowest, and merging is the one step this system deliberately never automates (and should not). Smaller cohorts reduce the freeze risk but do not reduce the number of merge clicks; four PRs landing at 01:00 need four clicks whenever the owner is next awake.

*Why no story caught it.* It is not a code property. It is only visible by joining `verdict-chime` events to `mergedAt` across a whole epic, which nobody had done before.

*Fix — the owner's, and it is a scheduling decision rather than a code one.* Options worth weighing: launch cohorts so their expected finish lands in the owner's waking hours; allow a cohort's next wave to start against the *unmerged* predecessor branch; or accept the latency and stop counting it as a defect. **What should not happen is treating this as an argument against the cohort split** — the split solved the problem it was aimed at.

**(2) A plan that refused to automate a criterion reported PASS at exit 0.** Symptom: a plan-author writing `disposition: needs-human, reason: not-safely-automatable` for a criterion whose contract says `verifiability: automated` produced exit 0, merge-eligible. Cause: the disposition lives in the plan, and `deriveCriterionResult` had never been handed it — the criterion produced no attempts, derived to `skipped`, and `aggregate` treats `skipped` as inert. Why no story caught it: nothing executed a plan before 4.7. `src/domain/plan.ts` states the rule correctly and `src/schemas/plan.ts` permits the shape; the two had simply never met. Fix: `DerivationOptions.plannedNeedsHuman`, checked before attempts as human verifiability is, additive, AD-13's single-producer invariant untouched.

**This is Epic 3's defect wearing different clothes, one epic later.** Epic 3 found a `verifiability: human` criterion auto-PASSing because `verifiability` was dropped at the integrity stage. Same class — *a criterion nobody could adjudicate reporting PASS* — second occurrence, different route. Both were found by an integration story running the built binary. Two independent instances is no longer a coincidence: **`skipped` being inert to `aggregate` is a standing hazard**, because every new way for a criterion to produce no attempts is a new way to reach green-for-nothing. Epic 5 adds exactly such a way (a browser probe with no executor), which is why 4.7 made that path throw an `InfraError` naming Epic 5 rather than contribute nothing.

**(3) Observation probes' process groups never reached the manifest.** Symptom: after an interrupted or crashed run, `specwitness clean` could not name or reap an observation probe's process group. Cause: `ObservationSurfaceExecutor` passed no `onProcessGroup` hook. Why no story caught it: every other spawning module carries it — `gates.ts`, `services.ts`, `data.ts`, and `shell.ts`, the last after 4.6's own codex review found the identical omission there. 4.5 and 4.6 agreed at intent-sync that their two command-spawning surfaces would "present one shape to their common caller", and on this field they did not; 4.7 was the first caller positioned to see it. Verified independently by me against merged source: `observation.ts` 0 occurrences, `shell.ts` 3, `http.ts` 0 and correctly so. Fix: 4.6's shape adopted verbatim, forwarded on every snapshot.

**(4) Only the observation surface left a persisted non-pass criterion with zero evidence references (FR-28).** Found by the surface-conformance test the owner assigned to 4.7 precisely because it is the only story that sees all three executors — **the test produced exactly the finding it was created to produce**, which is worth recording because owner-assigned cross-cutting work is easy to treat as ceremony. Cause and the instructive part: 4.5 disclosed the gap itself and assigned it to 4.7 *believing it required widening the closed evidence union*, i.e. an ADR. It did not. The typed **member** and the evidence **reference** are separate channels, and 4.4's merged `http.ts` had already closed its own version of this on a refused connection — write a redacted record of what was *attempted*, never of what was observed, and reference that. No union widened, no ADR needed. Three merged assertions encoding the old behaviour were updated in place with the reasoning; I read both diffs and confirmed every change is a **tightening** (each removed `toEqual([])` replaced by a stronger assertion, the member-absence rule kept).

**(5) A shared wrapped action ran once per observation — the worst-shaped defect in the epic.** Symptom: two observations wrapping one action ran the action twice, duplicating its writes, and the second wrapper's *before* snapshot then saw state the first action had already changed — so both its snapshots were wrong, silently, **in the direction of a delta that looks correct**. Cause: the first probes stage gave each wrapper its own `runAction`. Why no story caught it: `PlanCriterionSchema` blesses this exact shape and calls it "the case that actually occurs", but nothing executed a plan until 4.7, and 4.7's own first tests did not cover it. Found by codex review, not by the author. Fix: wrappers sharing a target run concurrently against a barrier that fires when no further wrapper *can* arrive — not at N arrivals, which deadlocks when a failed before-snapshot returns without calling `runAction`. **A verification tool that returns a plausible-looking wrong answer is the worst failure this product has**, and this is the only defect in the epic that would have produced one silently and repeatably.

**(6) Six codex findings across seven passes, and one review pass would have caught two of them.** All six were real, all fixed, none dismissed, and **every one was in 4.7's own new code rather than in the seams it was sent to inspect**. Findings 4, 5 and 6 were the same class — a provider-independent precondition running after compilation, spending provider quota that no run document could record, because compilation happens before a run directory exists. The author fixed 4 and 5 as point fixes; on the third instance she stopped patching and **stated the rule as an invariant** at the line itself, so a future precondition has an obvious home. That progression — two point fixes, then generalise on the third — is the cleanest evidence in this epic that a review loop works rather than grinds. The corollary is uncomfortable and worth stating plainly: **a single review pass would have left four of these six in the branch.**

**(7) Two guards passed without discriminating, and both were caught by planting the failure.** The seeded-secret suite, verified red against a neutered `redactText`, caught the author's own vacuous assertion — the `specwitness report` case called `report` with no argument, exiting 64 with empty stdout, so both `not.toContain` assertions passed against nothing at all. Separately, the plans-directory test's first version made the path a **file**, which fails earlier in `readPlanFile` with `ENOTDIR`, so both orderings refused identically and **the test passed against unfixed code**; only an *absent* directory discriminates. Generalisable: **a guard must be shown to fail, not merely to pass.** PR #52 carries a table of six such plantings, each naming what was planted and what failed.

**(8) The orphaned-process leak: three passes, two wrong answers first, and a measurement error on each side.** Symptom: 30 orphaned `node gates/slow.cjs` at `ppid=1`, four appearing per run of the interrupt suite, the oldest more than a day old — i.e. accumulating since before this epic.

- *Pass 1 was a measurement error, and it is the instructive one.* The author reported "no new orphans" from a **total count**, which cannot distinguish *reaped four, leaked four* from *leaked nothing*. **I made the mirror-image error in my own first sample**, sorting `etime` lexicographically across `ps`'s mixed `MM:SS` and `HH:MM:SS` forms, so a six-minute process sorted after a five-hour one and the four briefly looked reaped. Two independent observers, two different wrong methods, the same wrong conclusion.
- *Pass 2 fixed a real hole that was not the cause* (`interruptMidRun` asserting before signalling the child). The leak reproduced afterwards with four *new* pids in four *new* worktrees.
- *Pass 3, root cause.* The gate runs in a **detached process group**; `child.kill()` kills the `specwitness` process and never touches the group. `specwitness clean` normally reaps it through the manifest — but clean deliberately **skips a run whose recorded owner is still alive** (`skipped: 'active'`), which is correct product behaviour and is exactly the race. Differential measurement, cleanup selectively disabled: clean + group reap → 0 new; group reap alone → 0 new; **pid-kill alone → 4 new**, the reported signature exactly.
- *The fix that generalises is not the group reap.* It is the fixture change: the `slow` gate now self-exits after ten minutes. **When a test run is killed outright, no `afterEach` executes at all**, so no in-suite cleanup can help, and an immortal gate then lives until reboot. Verified by me against the clock: pid 60084, born ~14:00:17Z, was gone by 14:11:56Z; a full suite run of my own, in a different worktree, left **zero** orphans.
- *Why no story caught it.* No test can observe it — the leak is a property of the machine between runs, and it was found by the supervisor reading the process table rather than by anything in the suite.

**(9) The supervisor brief's §10 project delta is wrong, for the second epic running.** It states that `docs/findings/` does not exist and instructs the supervisor to establish the precedent. The directory holds four documents, three of them retrospectives with a settled structure — this one follows theirs. Epic 3 filed this as action item **I** and it is still open; this is the second sighting, and the cost is that a supervisor obeying the brief literally would write a retrospective in the wrong shape and claim a precedent that already exists.

**(10) `events.log`'s agent field is unreliable in two independent ways.** The 4.7 spec already warns that **names are recycled per cohort** — `alice` is 4.1, then 4.3, then 4.7 — so attribution by name is wrong for roughly half the epic. Separately, I observed `superman tests-passed` entries at times when I ran nothing (13:04:42Z, 14:01:56Z); one later entry (14:18:26Z) *was* genuinely mine, from a background suite run I started in another agent's worktree, which suggests the id follows the invoking session rather than the worktree. Anyone mining this log for an epic-level fact must join on timestamps or PR numbers, never on the name alone. I did.

## 3. What we learned

1. **Smaller cohorts move the bottleneck; they do not remove it.** Epic 4 traded ~7.5h of subscription freezes for ~7.7h of overnight merge-click latency. Both are human-availability costs, and only the first is fixable by scheduling agents.
2. **An integration story's job is to run the product, and it keeps paying.** Epic 3 said this; Epic 4 confirms it with four seam defects, three of them found by running the built binary and one by the review of the code that ran it. None was reachable by any unit suite that existed before.
3. **A cross-surface conformance test earns its cost.** It found the FR-28 gap no per-surface suite could see, because it is the only thing in the product that asks whether three implementations of one contract behave alike.
4. **"Merged source is the contract" held — and it held because the previous cohort worked at it.** All three of cohort 2's surface PR bodies carried the same `recordEvidence` warning in the same words, about a dependency 4.7's spec never mentions and whose misbinding fails silently and green. That warning is the single reason this epic does not ship reports containing gate evidence and no probe evidence. Cohort 2 solved a problem it would never see the consequences of.
5. **Where handover failed, it failed in exactly one way: stale claims about *other* branches.** Three instances — 4.5 saying "4.4 has not adopted it either" when 4.4 had; 4.5 and 4.6 each expecting the other to add a barrel export line that neither added; 4.4's note that the barrel gap was "a convenience one, not a wiring one", true only until somebody tried to use it. **Every claim a PR body made about a sibling aged badly; every claim it made about its own merged code was reliable.** Adopt for Epic 5: *describe your own diff; point at, but do not characterise, anyone else's.*
6. **The cost of a solo cohort is not information — it is disagreement.** 4.7's author reported that merged source answered every question she had except one, and that one was answered by a PR body. What she could not do was *argue with anybody*: three defects here would have been contested at intent-sync and instead became solo judgement calls with a paragraph each. That is tolerable where she was confident and unsatisfactory for D6, which she declined to decide and handed back.
7. **A guard is only a guard once you have seen it fail.** Two vacuous tests in one story, both caught by planting the failure rather than by reading the assertion.

## 4. What went well

- **Zero subscription freezes**, against three in Epic 3. The cohort split delivered on its own terms.
- **Zero orphaned processes at epic head**, from a baseline of thirty accumulated over more than a day — and the fix that achieved it is the general one, not the local one.
- **Every codex finding real, none dismissed**, across seven passes. `total=6, fixed=6, dismissed=0, escalated=0`.
- **Two claims corrected under measurement without defensiveness.** 4.7's author was wrong twice about process leakage and said so both times in her own words, including the sentence that matters most: *"I have a plausible mechanism that matches your evidence and a fix that closes it, but not a reproduction. I would rather tell you that than dress up a hypothesis as a diagnosis."*
- **The owner rider closed a carried action item in a branch rather than deferring it again.** Epic 3's item F (SIGINT: ADR or story) is answered: a synchronous, self-removing, re-raising handler that decides no signal semantics the project had not already decided, so no ADR was needed — and the author argued that explicitly rather than by omission. Exit 130 was correctly *not* added to `cli/exit.ts`.
- **Scope discipline under a widened mandate.** 4.7 was told seam defects were its to fix rather than escalate — a deliberate widening of escalate-not-patch. It fixed four and escalated none it should have fixed, while declining three tempting consolidations as named follow-ups rather than doing them quietly.

## 5. Technical debt carried forward

1. **The harness does not reap process groups after a killed test run.** The fixture self-exit bounds the damage to ten minutes; it does not close it. Owner: owner-harness.
2. **`specwitness clean`'s `skipped: 'active'` guard has a liveness race** — a just-died owner still looks alive, leaving its detached process group reaped by nothing. This is a **product** question about FR-21 that 4.7 surfaced but does not own. It is my finding, not the story's. Owner: owner.
3. **Three near-identical `slugify` helpers and three structurally-identical evidence-callback types** across the surfaces. Flagged by all three cohort-2 PRs as a 4.7 consolidation candidate and deliberately not done: it touches three merged modules to buy tidiness. Named follow-up.
4. **Per-surface probe schemas in `src/schemas/plan.ts` are module-private**, so all three surfaces hand-validate their params independently. An additive export is a reasonable follow-up story.
5. **The `params` contract diverges across surfaces** — http nests the probe under `params.probe`; observation and shell take its fields flat. Honoured rather than normalised, because changing an executor's params shape breaks its merged suite and buys nothing an operator can see.
6. **`src/pipeline/stages/setup.ts` is still an empty placeholder**, in no Epic 4 story's acceptance criteria. Named so it does not become folklore.
7. **`fenceMask` in `src/ingest/bmad-v6/markdown.ts`** (Epic 2 §5a defect i) — still open; no Epic 4 story ingests markdown.
8. **ADR-003's prose still says `gateFailed: true`** where the thrice-confirmed implementation is `gateFailed?: string`, and **PRD addendum §B** still claims no JSON-schema-constrained output flag exists. Both are the owner's; no Epic 4 story touched them, correctly.

## 6. Next-epic readiness (Epic 5 — browser & human judgment)

- **The browser seam is empty and refuses loudly.** A `browser` probe throws an `InfraError` naming Epic 5 rather than contributing nothing — deliberately, because a silently skipped browser probe would let a plan that mapped a criterion to a browser check report PASS having checked nothing (observation 2's standing hazard). The dispatcher's `switch` is exhaustive, so adding the executor is a compile-time-guided change.
- **`PROBE_SURFACES` already contains `browser` and the `browser` evidence kind is unused** — no union widening is needed, so no ADR is needed to start.
- **Retries are built and proven but have no field anywhere** — not in the config schema, not in 4.2's frozen Plan schema. "Opt-in per probe class, default 0" resolves today to an internal policy of zero, injectable only by tests. The mechanism exists, so the ADR that adds the field has nothing left to design. Epic 5's flakiness story (5.4) inherits this in a good state.
- **Epic 5 adds a browser to a product whose signal handling has never run on Linux.** See §9.
- **The conformance test is the right place to add the fourth surface**, and it will fail loudly if a browser executor diverges structurally from the other three.

## 10. The three-cohort experiment — the short answer

**It worked, for the reason it was tried, and it did not make the epic faster.** Zero subscription freezes against Epic 3's three. Wall clock 20h54m, of which one overnight block of ~7h43m was four ready PRs waiting for a merge click — almost exactly the 7.5h Epic 3 lost to freezes. The handover mechanism that made sequential cohorts viable was cohort 2's discipline in writing PR bodies as handover documents, and its one failure mode was describing other people's branches. Whether to run Epic 5 this way is **e4-A**, and it should be decided on the merge-latency evidence rather than on the freeze evidence alone.
