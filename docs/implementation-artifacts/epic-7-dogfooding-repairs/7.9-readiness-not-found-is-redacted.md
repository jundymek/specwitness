## The defect, in one paragraph

Under AD-3 there is no shell. A declared command is split into a binary and arguments, so a plausible-but-unsupported declaration shaped `NPM_TOKEN=… curl --fail http://…` tokenizes with the ASSIGNMENT as the executable. That is the shape a developer reaches for when a readiness probe needs a token. Nothing on PATH has that name, so the readiness probe comes back `not-found`. `src/pipeline/stages/services.ts:684-693` then interpolates `binary` **unredacted** into both the `InfraError` message and its hint, which prints the token in the one message an operator pastes into an issue.

Story 6.11 closed exactly this hole in `setup.ts` and then, as owner-authorised follow-up, in `gates.ts` and `data.ts`. The services stage's readiness arm was never in that list, so it was never fixed.

## Acceptance criteria

**AC1: a secret in a readiness binary is absent from the message AND the hint.**
Declare a readiness command whose executable token is credential-shaped, for example an assignment the built-ins recognise. Drive the arm to `not-found` and assert that the secret string is **absent** from both `error.message` and the hint. Assert absence, not the presence of a redaction marker (Epic 3 retro §7): a test that only looks for the marker passes against code that prints both.

**AC2: config-declared extra patterns apply too.**
Plant a token that no built-in rule can match, and have the redaction options passed to the stage declare a pattern for it. The token must be absent. Pair this with a control that passes no pattern, in which the token must be present. Without the control, the test cannot tell the pattern ran from the built-ins happening to match. This is the AD-10 half, and story 7.4 is why it now reaches this stage at all.

**AC3: an ordinary missing binary is still named.**
`services.test.ts:290` keeps passing unchanged: `curl-that-is-missing` still appears in the message. Redaction must not take away the operator's ability to see WHICH binary is missing. `{ shellCommand: true }` exists for exactly this kind of declared text (see the comment at `gates.ts:337-338`), so do not drop it.

**AC4: the same shape elsewhere in the services stage.**
Sweep `src/pipeline/stages/services.ts` for any other arm that interpolates a declared token into an `InfraError` without `redactText`. Fix the ones that are the same defect, each with its own test seen red. If you find the shape in a file outside `services.ts`, report it and do not patch it.

**AC5: seen red.**
Every test you add is recorded red against the current arm first, and the failure text is quoted in the PR body.
