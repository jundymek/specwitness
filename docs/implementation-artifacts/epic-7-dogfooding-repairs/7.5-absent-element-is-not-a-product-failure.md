## The defect, in one paragraph

`readOne` in the generated browser spec answers a `visible` read on a selector that matches
NOTHING with `{ present: false }` (`src/surfaces/browser.ts:603-605`). The assertion is then
unsatisfied, and an unsatisfied assertion is a product FAIL. But `expected: "false"` for
`source: visible` is the standard way a contract says **"this element must not be showing"**,
and the strongest possible evidence for that claim is that the element is not in the DOM at
all. SpecWitness today reports the desired outcome as a failure.

## What is NOT wrong, and must not be "fixed"

The surrounding design is deliberate and the comment above `readOne`
(`src/surfaces/browser.ts:580-593`) states it. Changing any of it fails this story.

- **`readOne` must still not catch.** An earlier version wrapped the body in a try/catch that
  turned every Playwright exception into an absent value, so a page that crashed or timed out
  WHILE BEING READ produced a product FAIL. That is the headline defect the browser story
  exists to prevent. **An EXCEPTION must still escape to the caller and become an execError.**
- **The absence/exception distinction is the point**, stated in that comment as: *"an ABSENCE
  is a fact about the page and is reported as one; an EXCEPTION means the page could not be
  read at all"*. This story does not blur it — it decides what the FACT of an absence means
  for one specific comparison.
- **`source: text` on a missing element stays absent.** There is no text to compare, and no
  expected value makes "the text is not there" into a satisfied assertion. Only `visible`
  has a defensible reading, because visibility is a claim about the rendered page and a
  missing element is definitively not visible.
- **An unparseable selector still escapes as an infra error.** SpecWitness could not perform
  the read; nothing was adjudicated.

## The decision this story must make explicitly

`visible` currently has two outcomes (`true`, `false`) and a third state (absent). The fix
is to map absence onto `false` FOR THE `visible` SOURCE ONLY — an element that is not in the
DOM is not visible, which is a true statement about the page rather than a convenience.

**This makes `expected: "true"` on a missing element a normal, honest FAIL** — the element
was required to show and it is not there. That case must keep failing, and a test must pin
it: the change must not turn "the thing I demanded is missing" into a pass.

If, having read the code, you conclude the absence should instead be reported as a distinct
third value that a contract can assert on, **say so in your PR body with your reasoning and
build the smaller change anyway** — a schema widening is an ADR, not a story.

## Acceptance criteria

**AC1 — absence satisfies `visible == false`.**
A browser probe asserting `source: visible`, `comparison: equals`, `expected: "false"` on a
selector matching no element reports the assertion as SATISFIED. Evidence still records that
the element was absent rather than present-and-hidden, because those are different facts about
the page and the reader must be able to tell them apart.

**AC2 — absence still fails `visible == true`.**
The same probe with `expected: "true"` reports a product FAIL. Pin it with a test, seen red.
**This is the acceptance criterion most likely to be broken by a careless fix.**

**AC3 — an exception is still an execError, never an assertion outcome.**
A page that crashes, closes or times out while being read still escapes `readOne` and becomes
`ok:false` → execError → exit 3. The no-catch rule holds. Pin it.

**AC4 — `source: text` is unchanged.**
A missing element read as `text` is still absent and still unsatisfied. No expected value
makes it pass.

**AC5 — a corpus fixture pins it.**
`fixtures/corpus/README.md` is the contract; `expected.json` is HAND-WRITTEN and never
generated by the code under test. Add a fixture covering AC1 and AC2 together — the pair is
the behaviour, not either half. **Verify it fails before your change and passes after**, and
quote the red output in your PR body.
