## What this story is for, in one paragraph

`specwitness init` produces a config that, comments stripped, is three lines. Everything a
plan can probe is then the operator's to write, and in the first client project that came to
645 lines of hand-written JavaScript in seven files — five of which only read the filesystem.
Three of the eight failures in the second dogfooding run were defects in that hand-written
code, all in generic file-reading logic. This story adds the surface that makes those five
scripts declarations instead of code, so a new project reaches a meaningful first verdict
without writing any.

## Acceptance criteria

**AC1 — the surface exists and is closed properly.**
`file` joins the discriminated union in `src/schemas/plan.ts` and `PROBE_SURFACES`, and the
existing two-way pin still passes. A plan naming `surface: file` validates; one naming an
unknown surface is still refused.

**AC2 — it executes no command and reads only the worktree.**
A `file` probe spawns no process and opens no socket. Every path it reads resolves inside the
verification worktree root; `..`, an absolute path, and a symlink resolving outside it are each
refused as an **InfraError**, never as a product FAIL — nothing was adjudicated. Pin all three
with tests, seen red. **This is the acceptance criterion a careless implementation breaks**:
the surface takes data rather than a command id precisely so that nothing a provider writes can
become an executable string, and a path escape would reopen that door from the other side.

**AC3 — it obeys AD-13 unchanged.**
It implements the same `SurfaceExecutor` interface, returns the same `ProbeAttempt`, evaluates
assertions mechanically and produces no `CriterionStatus`. Retries, `flaky` and classification
stay in `domain/criterion-result.ts`. Assert that this surface is reachable from the same
dispatch path as the other four rather than a parallel one.

**AC4 — absence is a fact, and its meaning is per source (ADR-009 §5).**
A missing path read as existence is the value `false` and compares like any other value, so
`expected: "true"` on a missing path still FAILS. A missing path read for its content is
unsatisfied for every comparison including negative ones. An unreadable path — a permission
error, a directory where a file was named — escapes as an `execError`. Three tests, three
distinct outcomes, each seen red first.

**AC5 — it replaces real scripts, shown against a real project.**
Take `gitnebula`'s `docs-presence.mjs` and `pkg-scripts.mjs` — both in
`~/dev/gitnebula/scripts/specwitness/`, both readable from here — and express what they report
as `file` probes in a corpus fixture. You are not editing gitnebula; you are proving the surface
covers what a real project actually needed. **Include the case its `findReport` got wrong:** a
document nested two directories deeper than the search looked. A surface that reproduces that
bug has not earned its place.

**AC6 — the template teaches it.**
`templates/config.yaml` gains worked, commented `file` examples that a new project can uncomment
and edit. A reader who has just run `init` must be able to write a first probe from the template
alone, without reading `src/`.

**AC7 — corpus fixtures pin it.**
`fixtures/corpus/README.md` is the contract; `expected.json` is HAND-WRITTEN and never generated
by the code under test. Cover at minimum: a satisfied existence check, a failed one, a content
match, a path escape refused as infra, and the nested-document case from AC5. **Verify they fail
before your change and pass after**, and quote the red output in your PR body.

**AC8 — nothing else changes.**
`observation` keeps its behaviour and is not deprecated (ADR-009 §6). No existing corpus fixture
changes its expected result. The full suite passes: at `db84f65` it is 213 files, 4060 passed,
3 skipped — quote your own numbers.

## The thing this story could make worse

ADR-009 records it as an accepted cost and it is the reason AC5 is written against a real
project rather than an invented one: **a declarative matcher makes it cheaper to write a probe
that passes over unmet work.** That is the failure mode the entire product exists to prevent.
The plan-authoring prompt refuses to map a criterion it cannot probe safely, and that refusal
must not weaken because a `file` probe is now cheap to emit.

You are not asked to solve this. You are asked to (a) not make it worse in the prompt, and
(b) say in your PR body what you observed about it while building — whether a plan author
handed this surface reaches for it where an `observation` or a browser probe was the honest
answer. That observation is worth more than a guess in this spec.

## One thing nobody can tell you

Three defects were found in gitnebula's hand-written probes, and all three were in code a
product would have written once: a non-recursive directory walk, hand-picked regexes that
missed the documents that satisfied the criterion, and a pattern count that counted comments.
**The third is the interesting one** — it counted occurrences inside the very test that
enforced the convention it measured. Ask what your matcher does about comments, about the file
that defines the thing being counted, and about a document that satisfies a criterion in
words the author of the probe did not think of. A declarative surface that cannot express
those distinctions has moved the defect rather than fixed it.
