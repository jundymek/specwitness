## The defect, in one paragraph

`tests/integration/doctor.test.ts:156-166` asserts that `doctor` prints `⚠ playwright-capability`
on a fixture project, and its comment states the assumption in one line: *"The fixture has no
@playwright/test, so playwright-capability warns."* The fixture indeed has none — but the check
does not only look at the fixture. It reports three facts, and the first of them is a SOURCE that
is `project` **· SpecWitness cache ·** `absent` (`src/cli/doctor/checks/playwright-capability.ts:38-41`).
The test's helper spawns the CLI with `extendEnv: true` and no `HOME` override
(`tests/integration/doctor.test.ts:119-131`), so the real user's cache is in scope. On a machine
that has ever provisioned SpecWitness's own Playwright cache the check **passes** instead of
warning, the regex does not match, and the test fails. Story 7.0 is what made that state
reachable: before it, nothing in the product ever wrote that cache.

## Why this is worth a story and not a shrug

**From Epic 7 onward the owner's machine is exactly the machine this test fails on.** This is the
dogfooding epic: its stories are found by running the real binary against a real project, which
provisions the cache, which breaks the test, permanently, for everyone who does the thing this
epic exists to do. CI stays green — a fresh runner has no cache — so the failure appears only in
front of the person least able to dismiss it and never in front of the gate.

It is also the shape of defect this product is about. A test whose verdict depends on state
outside the tree under test is a green that means nothing on a clean machine and a red that means
nothing on a dirty one, and neither reading is a fact about the code.

## What is NOT wrong, and must not be "fixed"

- **The check's behaviour is correct.** A provisioned SpecWitness cache IS the capability that a
  browser probe will use, so reporting it as present rather than as a warning is the truth. Do
  not make the check ignore its own cache to make a test pass.
- **`playwright-capability` stays optional.** The rule the test exists to protect — an optional
  check never moves the exit code — is the valuable half of it and must survive whatever you do.
- **Do not delete the test.** The rule it pins is real; what is broken is how it arranges for a
  warning to happen.

## Acceptance criteria

**AC1 — the test's verdict does not depend on the machine.**
`tests/integration/doctor.test.ts` passes on a machine WITH a provisioned SpecWitness Playwright
cache and on one without. Prove both, in the PR body: run it once as-is on this machine, and once
with a constructed `HOME`/`XDG_CACHE_HOME` pointing at an empty directory. Neither run may skip
the case.

**AC2 — the optional-check rule is still pinned.**
Whatever arrangement you choose, some test must still assert that a `warn` from an optional check
leaves the exit code at 0. If you make the warning happen by constructing an environment with no
capability, say so in the test's comment — the current comment is wrong and is half of why this
went unnoticed.

**AC3 — the pass branch is pinned too.**
A machine WITH the cache reports `playwright-capability` as passing, from source `SpecWitness
cache`. That is a real state of a real developer machine and no test covers it today. Pin it with
a constructed environment rather than with the developer's own.

**AC4 — no other test in the suite reads the developer's `HOME`.**
Sweep `tests/integration/` for the same shape — `extendEnv: true` with no `HOME` override, on a
command whose result depends on a cache, a global config or a credential store — and report what
you find. Fix the ones that are the same defect; report the rest rather than patching them.
**Nothing in this repository may read `~/.claude/` or `~/.codex/`**, and a test that lets the real
`HOME` through is how that would happen by accident.

**AC5 — seen red.**
Every test you change or add is recorded red first, on a machine in the state that makes it red,
and the failure text is quoted in the PR body.
