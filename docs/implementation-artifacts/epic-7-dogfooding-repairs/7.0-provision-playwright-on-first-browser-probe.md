## The defect, in one paragraph

`provisionPlaywright` is exported from `src/infra/playwright-env.ts:931`, is unit-tested, and
**is called from nowhere in `src/`**. A browser probe on a project that does not resolve
`@playwright/test` from its own root therefore fails with `InfraError` and the run stops at
exit 3 — while two user-facing messages promise a provisioning step that does not exist.

## What is NOT wrong, and must not be "fixed"

The surrounding design is deliberate. Changing any of it fails this story.

- **Refusing to skip is correct.** `src/infra/playwright-env.ts` header: an unavailable browser
  environment is `InfraError` (exit 3) or criterion `error`, **never** `skipped`. Epic 4's
  retrospective recorded twice that a criterion nobody could adjudicate reported PASS.
  **There must still be no skip path in this file when you are done.**
- **Exit 3 rather than 1 is correct.** A missing browser says nothing about the branch.
- **`doctor` not downloading is correct** and is required by AD-12. Do not make `doctor` provision.
- **Resolving once in `verify` is correct** (`verify.ts:338-341`): read-only, offline, no spawn,
  so a run with no browser probes pays almost nothing.

## Acceptance criteria

**AC1 — a run that needs a browser provisions one.**
Given a project with a compiled plan carrying at least one `browser` probe, and no resolvable
`@playwright/test` and no SpecWitness cache, when `verify` runs, then Playwright is provisioned
into SpecWitness's own cache and the browser probes execute. Exit 3 with "cannot run" is no
longer the outcome of a merely unprovisioned machine.

**AC2 — a run that needs no browser provisions nothing.**
Given a plan with no `browser` probe, when `verify` runs on the same unprovisioned machine,
then nothing is downloaded, no `npm` is spawned, and the run's duration is unchanged.
**This is the acceptance criterion most likely to be broken by a careless fix**: provisioning
unconditionally at `verify.ts:341` would make every gates-only run pay for a browser it never
uses. Decide from the PLAN whether a browser probe exists.

**AC3 — nothing is written into the target project.**
The `⚠️` rule in `provisionPlaywright` holds through your call site: no bytes land under
`projectRoot`, including when `PLAYWRIGHT_BROWSERS_PATH` or `XDG_CACHE_HOME` point there.
Pin it with a test, and seen red.

**AC4 — a project's own pinned Playwright still wins.**
Route 2 of the header (`playwright-env.ts:920-930`): when the project resolves its own
`@playwright/test`, that version is honoured and only browsers are downloaded, into the
project's own registry — never SpecWitness's cache, and never the project tree.

**AC5 — provisioning failure is `InfraError`, never a skip and never a product FAIL.**
A network failure, an `npm` that is absent, a refused write: each is exit 3 with a message
naming what could not be done. `stageProductNegative` must remain unreachable from this path.
There must still be no path from an unusable browser environment to `pass` or `skipped`.

**AC6 — the messages become true.**
`doctor`'s hint (`playwright-capability.ts:131`) and the executor's refusal
(`browser.ts:1136-1141`) must describe what the product now does. Today the first promises
provisioning "on the first browser probe" that never happens, and the second points the
operator at `doctor`, which cannot provision. After this story, either both describe real
behaviour, or — if you and the supervisor conclude provisioning must stay opt-in — they name
the command that actually provisions. **Do not leave a message that promises what the code
does not do; that is half of what made this defect invisible for two epics.**

**AC7 — a corpus fixture pins it.**
`fixtures/corpus/README.md` is the contract; `expected.json` is HAND-WRITTEN and never
generated by the code under test. Add a fixture covering the behaviour this story adds.
**Verify the fixture fails before your change and passes after** — the 6.11 author reverted
the composition root to the placeholder to prove exactly this, and that experiment is called
"the single strongest artifact this epic produced" in the 6.11 retrospective. Do the same and
quote the red output in your PR body.

  than the decision inlined in `verify.ts` — a decision inlined there is testable only by
  driving the whole command, which is how this defect survived. (ii) `npm`/`npx` tripwires in

  public origins on every CI run, and the corpus's own hermeticity promise stops being true

- **A UX cost of the eager design, stated plainly.** A provisioning failure is now an edge
  refusal: `ERROR:`/`HINT:` with no stage timeline, where before the operator saw ten stages
  and then the refusal. Same shape as a tampered contract. The alternative — provisioning
  inside the probes stage — starts a multi-minute download after a worktree and the declared
  services are live, and needs memoising against the retry policy (`DECISIONS.md` D1).
- **What still executes none of this: `verify` driving a REAL provisioning end to end.** The
  corpus proves the call site is reached and the refusal is correct, on both required runners,
  without downloading. Real provisioning is proven by

  but that calls `provisionPlaywright` directly, not through `verify`, which is the same shape
  of gap that hid D-5, one level up. Closing it means `pnpm build` plus one step in that job
  (`.github/workflows/ci.yml`, story 6.9's file, not in this story's scope) — and I could not
  have seen such a test pass before proposing it: this machine has no browser registry.
  **Recommended as a follow-up for the owner.**
- **Not done, deliberately:** nothing outside the Exact scope. No retry-policy change, no
  classification-table change, no `doctor` network behaviour, no plan-schema change (that is
