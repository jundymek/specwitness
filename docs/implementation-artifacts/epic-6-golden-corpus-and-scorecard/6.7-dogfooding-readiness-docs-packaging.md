### A process failure of mine, recorded because it nearly shipped three defects

**I stopped reading the harness auto-review logs.** This branch's *first* auto-review
echoed its own prompt file instead of producing a report, so I concluded the auto-review
was noise, ran `codex exec review` myself each round, and thereafter treated every
`auto_review_findings` notification as the classifier failing closed — **without opening
the log.**

It was not noise. A later auto-review had found **three real defects in my documentation**
that my own manual runs had not surfaced, and they sat unread while I iterated on other
things:

1. **P1 — "Nothing leaves your machine" was false.** Configuring an AI role makes
   SpecWitness run `claude`/`codex`, which send the epic specification, criterion
   statements and failure evidence to a cloud provider. A security promise, wrong in
   general, in the section where a user with a confidential spec would look.
2. **P1 — the freshness advice could merge unverified code.** I told harnesses to compare
   `finishedAt` against the head commit's timestamp. Commit timestamps are not monotonic
   (rebase, cherry-pick, amend, force-push, other people's clocks), so a run that verified
   *different code* can look fresh. The correct check is SHA equality against `headSha`.
3. **P2 — `runId` does not totally order same-second runs.** The timestamp is truncated to
   whole seconds and the four-character suffix is `RandomIds`, not a counter. I wrote that
   it "sorts chronologically" and that a harness can rely on it; `report <epic>` uses that
   sort too, so it is a product limitation as well as a documentation error.

**The lesson is e3-A read the other way round.** That action item warns that the classifier
can report "no findings" over real findings. The inverse also holds and is what caught me:
it can report findings I assume are spurious. **The remedy is the same in both directions —
open the log and count `Review comment:` blocks; never act on the classifier's word.** I
applied that rule to `clean` verdicts and not to `findings` verdicts, which is exactly
half a rule.

All three are fixed. Both P1s were independently re-found by my next manual run, which is
luck rather than process.
