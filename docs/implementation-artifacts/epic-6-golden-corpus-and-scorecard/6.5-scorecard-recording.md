## Story

I want every run appending a local scorecard record automatically,

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` § "Story 6.5" (authoritative — expand, never weaken):

1. **Given** any completed run
   **When** it persists
   **Then** a record (run id, epic, verdict/outcome, per-status criterion counts, durations, provider invocations, retry/flaky counts, infra errors) is appended to `.specwitness/scorecard.jsonl` — **locally only, no network I/O anywhere in the scorecard path**.

Clarifications (detail only, no weakening):

- **"Without ceremony" is the requirement, not a nicety.** Brief §54 and NFR-4: the record is appended **automatically**, by every completed run, with no flag to remember and no command to run afterwards. The measurement window is ~30–50 real tasks across weeks; **anything the operator must remember to do will not be done**, and the north-star metric will be computed over a biased sample without anyone noticing. **If recording is opt-in, the story has failed its purpose even with every test green.**
- **"Any completed run" needs a definition you must write down, and the interesting cases are the failures.** A PASS run obviously records. So does a FAIL, a NEEDS_HUMAN, and — **most importantly** — an infra-errored run: infra-error rate is one of the metrics 6.6 must report, so a run that dies of infrastructure **must still leave a record**, or the metric is structurally unmeasurable. Decide and document what happens for: a run killed by a signal, a run that never got past config validation, a `--no-ai` run, and a run whose contract failed integrity. **State each answer and its reasoning**; the defensible line is roughly "a run that produced a classified outcome records; an invocation that never became a run does not", but you own the decision and 6.6 depends on it.
- **⚠️ THE SCORECARD MUST NEVER CHANGE A RUN'S OUTCOME. THIS IS THE STORY'S HARDEST RULE.** Recording is instrumentation, and instrumentation that can fail a verification is worse than no instrumentation. If the scorecard file is unwritable, locked, on a full disk, or corrupt:
  - the run's **verdict and exit code are unaffected**;
  - the failure is surfaced (a warning, not silence — a scorecard that silently stops recording is a metric that silently becomes wrong);
  - **it is never an `InfraError` that changes exit code**, and never a FAIL.
  **Test this directly** with an unwritable path. The temptation is to treat a failed write as a real error, because everywhere else in this product a failed write *is* one.
- **Concurrency is real and you must decide about it explicitly.** Two `specwitness verify` runs can execute at once — the harness is a multi-agent system, and Epic 5's own waves ran five agents in parallel. JSONL append is *usually* atomic for small records under `O_APPEND`, and "usually" is not a design. **Decide, document the guarantee you are providing and its limits, and test concurrent appends.** A single interleaved line corrupts one record; per ADR-008 §5 the summary must survive that, but you should not rely on the reader to paper over a writer you never thought about.
- **ADR-008 binds this story, and it was decided for you.** Read `docs/adr/ADR-008-persisted-envelope-strictness.md` in full. It answers action item e5-D and rules directly on `scorecard.jsonl`:
  - each line is an **independently-parsed record carrying its own `schemaVersion`**;
  - a record whose only failure is **unknown keys** is **skipped with a warning naming the line number and the unknown fields**, and the summary continues;
  - a **malformed** line is likewise skipped-with-warning rather than fatal;
  - **`scorecard summary` reports the count of skipped records**, so a silently shrinking denominator is impossible.
  This is deliberately softer than for single-document artifacts, and §5 explains why: an append-only log accumulated across versions is still evidence when partially readable. **Register `scorecard` in `src/schemas/versions.ts` as a one-line addition** — that file's header describes exactly this move.
- **Local only. No network I/O anywhere in the scorecard path** — the AC says it and it is a founding product rule (`CLAUDE.md`: *"Local-first: no SaaS, no web UI, no cloud telemetry"*). **This is the one place in the product where someone might reasonably think telemetry belongs, which is precisely why the AC forecloses it.** Make it structurally impossible, not merely absent: no HTTP client imported into the scorecard module, and a dependency rule or test that would catch one being added. **Say in the module header that this is a product rule, not an oversight**, so a future contributor does not "improve" it.
- **The fields are named in AC1 and each has a meaning 6.6 will compute over. Get them right and write them down:** run id, epic, verdict/outcome, **per-status criterion counts** (pass/fail/needs_human/error/skipped — and note that `skipped` is the subject of open action item **e4-D**, so record it faithfully and do not editorialise), durations, **provider invocations** (the count is what proves the AI-free-run share 6.6 reports), retry/flaky counts (story 5.4's `flakiness`), and infra errors.
- **Redaction applies.** A scorecard record is derived from run data that includes provider text and command output. **Nothing untrusted or unredacted enters the file** — prefer counts and enums over free text, and where free text is unavoidable, redact and bound it exactly as the run does (`src/domain/evidence.ts` — `redactText`, `boundedText`). **A scorecard is the file most likely to be pasted into an issue**, so it is the file least able to afford a leak.

## Dev Notes

### Goal & Context

**This is the instrumentation that decides whether SpecWitness was worth building.**

The product hypothesis — brief §54, PRD SM-1 — is that independent epic-level verification finds *real defects that already passed coding-agent tests, Codex review and supervisor review*. Nobody knows whether that is true. Epic 7 answers it by gating a real epic and measuring; **your file is the measurement**, and 6.6 is the arithmetic over it.

That gives your story an unusual property: **its defects are invisible until they have already destroyed the thing they were measuring.** A recording path that silently skips infra-errored runs produces an infra-error rate of zero — a number that looks like good news. A recording path that is opt-in produces a biased sample nobody can detect after the fact. A record whose fields 6.6 misreads produces a north-star metric that is confidently wrong. There is no test in Epic 7 that catches any of these, because by then the only evidence is the file itself.

So the two disciplines that matter most here are: **record automatically, including on the paths that failed**, and **write the field semantics down completely** for the agent in wave 3 who will compute over them and cannot ask you what you meant.

### The Codex review found a real P2 while reporting `auto_review_clean`

The background job's message said `auto_review_clean`, `codex exit 0`, *"The
review reported no findings."* **The log said otherwise**, and reading the log
rather than the status line is what this story's spec requires (*"Sign off on
what you actually verified, from the actual review report and not from a status
line"*, e3-A's mitigation) — and what the wave supervisor had messaged all six
agents about an hour earlier, having been bitten by the identical shape on their
own PR. **e3-A is live in this wave, not a historical note.**

**[P2] Reject unsupported scorecard schema versions** —
`src/schemas/scorecard.ts:378`. **Valid, and the sharpest defect this story could
have shipped.** `schemaVersion` was validated as `z.number().int().positive()`,
so a record written by a NEWER build parsed as though it were version 1. The
unknown-key branch cannot catch this: ADR-008 §3 defines a version bump as an
existing field CHANGING meaning, type or requiredness, so a version-2 record can
carry exactly the version-1 key set and mean something different by it. No
unknown keys, every type valid, and every number 6.6 computes from it wrong,
with nothing on screen to say so.

**Fixed** by reading the version BEFORE the shape — the ordering `parseRunResult`
already uses for `result.json` — and returning a `version-skew` skip naming both
versions. A ceiling, not a wall: a record at this build's own version still
reads, per AD-5. Two tests added; the schema-level one was written first and
watched fail with `ok: true`, the defect demonstrating itself.

First-round verdict: total=1, fixed=1. The second and third rounds are below; the recorded verdict covers **all four rounds: total=6, fixed=6, dismissed=0, escalated=0**.

bind a loopback port, so the four cases using the probe fixture report

probe-fixture suites already bind loopback.

### The second review round — two more P2s, both acted on

Run once after the account-wide codex limit reset, as the supervisor instructed,
over the final rebased head. **Two findings, both P2, both mine, both addressed.**

**[P2] Apply the finding-ID cap across the whole record** —
`src/schemas/scorecard.ts:424-433`. **Valid and reproducible; FIXED.** The cap
was per STATUS, so 150 failures + 150 needs-human + 150 errors put **450 ids in
one record with `findingCriterionIdsTruncated` still false**, because no single
bucket exceeded its own allowance. A contract has no criterion-count limit, so
it is reachable rather than theoretical — and it matters because the LINE SIZE
is exactly what the concurrency guarantee rests on. A record that can grow to
three times its documented bound can outgrow the size at which a single
`O_APPEND` write stays atomic, which is the one property the append design
depends on. Now one shared budget of 200 spent in a fixed order (`fail`, then
`needs_human`, then `error`), with the flag set on the combined count. Test
written first; it failed with `expected 450 to be less than or equal to 200`.
Reverting the fix turns it red again.

**[P2] Redact untrusted validation paths before warning** —
`src/schemas/scorecard.ts:622-625`. **Applied, but NOT a reproducible leak, and
the distinction is stated rather than smoothed over.** The finding's theory is
that an attacker-controlled map key reaches `issue.path` and is printed verbatim
by the malformed branch, which — unlike the unknown-key branch — did not call
`field()`. **Measured against this schema, it does not happen:** an unexpected
key under `stageDurationsMs` produces an `unrecognized_keys` issue carrying the
key in `issue.keys`, with `path` stopping at `stageDurationsMs`, so it routes to
the branch that already redacts. Every path segment this schema can produce is
one of its own field names, a `STAGE_NAMES` enum member, or an array index.

I applied the redaction anyway, and no test accompanies it, because a
non-vacuous one cannot be written against the current field list — that is
itself the reason to apply it. The safety argument was a property of TODAY'S
FIELDS, not of the function; the day someone adds a free-form-keyed field (6.6
has every reason to want one) a path segment becomes attacker-controlled and
this silently becomes a leak in the file least able to afford one. One
`.map(field)` makes the module header's claim true by construction instead of by
an argument that has to be re-derived. **Recorded as `fixed` rather than
`dismissed` because the change shipped — but a reader should know it is
defence-in-depth, not a patched vulnerability.**

Round-2 verdict: **total=2, fixed=2, dismissed=0, escalated=0.**

### The third review round — two more P2s, and one of them was the sharpest in the story

Run over the final head after the round-2 fixes, because the supervisor's
instruction was one review **over the final head** and my earlier run had covered
a head I then moved. Both findings valid, both fixed.

**[P2] Contain failures raised by the warning callback** —
`src/infra/scorecard-store.ts:158-163`. **The single most important finding in
this story, because it broke the method's headline guarantee from the one line
that exists to uphold it.** `warn` is caller-supplied and bound at the edge to
`printWarning`, which writes to `process.stderr`. `warn` was invoked INSIDE the
catch, so a throw from it escaped `appendRecord` — and the call site in
`verify.ts` deliberately has no try/catch, so it would have reached `main.ts`
and become **exit 3**. A completed verification turned into "the environment is
broken, retry" by the instrumentation that exists to be invisible.

It is entirely reachable: `specwitness verify | head -1` destroys stderr, and
EPIPE on a broken pipe is an ordinary way to run a CLI. The test written first
failed with *"promise rejected `Error: EPIPE: broken pipe, write` instead of
resolving"* — the guarantee breaking in one line of output.

Fixed with an inner boundary around the `warn` call. **What it does on failure is
nothing, deliberately:** there is no third channel. We cannot report a failure to
report, and every other option — rethrowing, writing to stdout (which carries the
`--json` document a harness parses), exiting — changes something this method
promises not to change. Silence about a warning is the least-bad outcome
available; silence about a verdict never is, and that is the distinction.

**[P2] Block networking built-in subpaths** — `.dependency-cruiser.cjs:288`.
**Valid; fixed.** The rule anchored on `$`, so `node:dns/promises` — a real
module, with exactly the shape of the `node:fs/promises` this codebase uses
everywhere — went straight through. A probe test now plants it.

⚠️ **And the first fix for it was worse than the hole.** Writing the pattern as
`(/.*)?$` made dependency-cruiser reject the whole config as *"an unsafe regular
expression. Bailing out."* — which disables **every rule in the file**, not just
this one. Twenty-four tests went red at once and the suite named the cause. The
shipped form is `($|/)`, which carries no nested quantifier. Recorded because the
failure mode is silent in exactly the wrong way: a bail-out looks like a passing
lint run to anybody not reading the output, and the guard that caught it is
`cruises the whole tracked tree, cleanly` — a test whose value is easy to
underestimate until it fires.

Round-3 verdict: **total=2, fixed=2, dismissed=0, escalated=0.**

### The fourth review round — one P2, and my own tests had a blind spot

**[P2] Preserve the first append after a torn final line** —
`src/infra/scorecard-store.ts:141-144`. **Valid, reachable, and it is the failure
this whole module exists to prevent; FIXED.**

ADR-008 §5 makes ONE torn line survivable. But a crash or a short write leaves the
file with **no trailing newline**, and the append then glued the next COMPLETE
record onto the fragment — so the reader skipped the pair as a single malformed
line. One casualty became two, and the second one was healthy. A completed run
disappearing from the measurement with no symptom anywhere is precisely the
defect class this story is written against.

**The more useful half of the finding is what it says about my tests.** Every
torn-line case I had written — the unit one and the integration one — wrote its
damaged line WITH a trailing newline, so none of them could reach this. I had
tested the shape of corruption I imagined rather than the shape a crash actually
produces.

Fixed by reading ONE BYTE of the tail and prepending a newline when it is
missing. It does not reintroduce the read-modify-write this module refuses: the
separator travels in the same buffer, so the append is still one `write(2)`. Two
concurrent writers can both observe a torn tail and both prepend, which yields a
blank line between records — and `read` skips blank lines without counting them.
A benign outcome was chosen over a lock, deliberately. Any failure of the
inspection answers `''`, so the worst case is exactly today's behaviour.

Round-4 verdict: **total=1, fixed=1, dismissed=0, escalated=0.**

### The record shape — field by field, for story 6.6

**One line of `.specwitness/scorecard.jsonl` is one `ScorecardRecord`
(`src/schemas/scorecard.ts`), appended by `ScorecardStore.appendRecord`
(`src/infra/scorecard-store.ts`).** The module header carries the same table in prose with the
reasoning; this is the summary.

| field | type | meaning, and how 6.6 computes over it |
| --- | --- | --- |
| `schemaVersion` | `number` | ADR-008 §5 — **per LINE**, not per document. `1`. |
| `runId` | `string` | **The join key.** `.specwitness/runs/<runId>/result.json` is the full evidence. `(runId, criterionId)` is the key an FR-34 attribution hangs on. |
| `epic` | `string` | canonical id, e.g. `epic-6`. Group by this. |
| `startedAt` / `finishedAt` | ISO-8601 UTC with ms | the RUN's instants, not the append's. |
| `durationMs` | `number` | wall clock, clamped ≥ 0. **SM-2 cost/time.** |
| `outcome` | `{verdict, gateFailed?}` \| `{infraError}` | AD-6: one or the other, never both. **Infra-error rate = records with `infraError` ÷ all records.** Derive the exit code from this; there is no `exitCode` field (see below). |
| `criteria` | `{total, pass, fail, needs_human, skipped, error}` | every key always present and zero-valued. `total` is the denominator. **Do not fold `skipped` into `pass`** — e4-D is open and this records it faithfully. |
| `gates` | `{total, pass, fail, skipped}` | same shape; `skipped` is an early stop, not an omission. |
| `flakiness` | `{flakyCriteria, retriedCriteria, extraAttempts}` | story 5.4 verbatim. **Retry-to-green (SM-C3) = `flakyCriteria` ÷ `retriedCriteria`**; `extraAttempts` is the repetition bought. A flaky pass counts in `criteria.pass` too — it is a pass AND a flake (FR-32). |
| `providerInvocations` | `number` | `providerUsage.length`. **AI-free-run share (FR-18) = records with `0` ÷ all records.** |
| `providerRoles` | `string[]` | distinct, sorted. Distinguishes "compiled a plan" from "was explained", which a bare count cannot. |
| `stageDurationsMs` | partial record over the 11 `STAGE_NAMES` | where verification time went. A skipped stage is present with `0`. |
| `findingCriterionIds` | `{fail, needs_human, error}: string[]` | **the FR-34 hook.** Exactly the criterion ids a finding could be about; passing and skipped criteria are absent because they produced none. Capped at 200 per bucket. |
| `findingCriterionIdsTruncated` | `boolean` | true when the cap bit. **Never read a cut list as complete** — the `criteria` counts stay exact regardless. |
| `adapted` | `boolean` | story 5.6: an adaptation applied AND KEPT. A refused proposal is `false`. An adapted run executed a plan differing from the committed one, so it is a different measurement. |
| `environment` | `{specwitnessVersion, nodeVersion, platform, arch}` | which build produced the record — the premise ADR-008 exists for, since this log spans versions. |
| `contract` | `{fingerprint, version, amendments, criterionCount}`, **optional** | **presence IS fingerprint validity.** Absent means the run ended before or at integrity. Two records sharing a fingerprint verified the same spec. |

**There is no `exitCode` field, deliberately.** `src/schemas/**` may not import `src/cli/**`
(`nothing-imports-cli`), so it is unreachable from where the record is built — which makes
"the scorecard adds no exit code and changes none" a property of the layer graph rather than a
promise. Derive it from `outcome` via `src/cli/exit.ts`, still the only module that knows what
a code means (ADR-002).

**`skippedRecords` is NOT a field.** It comes from reading: `ScorecardStore.read()` returns
`{records, skipped}` where each `skipped` entry is `{line, reason: 'version-skew' | 'malformed',
message}`. ADR-008 §5 requires `scorecard summary` to report the count. **I provide the
primitive; 6.6 owns the arithmetic and the CLI, and this story deliberately builds neither.**

**Which runs record**, because a summary over the wrong population is a wrong metric:
`store.createRun` (`src/cli/commands/verify.ts:334`) is the boundary, enforced by POSITION
rather than by any predicate. PASS, FAIL, NEEDS_HUMAN and **infra-errored runs all record**;
an invalid config, an unresolvable ref, an uninitialised project, `--no-ai` with no plan and a
usage error record nothing, because none of them became a run. A signal-killed run records
nothing — the record is a projection of a finished `RunResult` and an interrupted run has
none. **So the record count is a count of runs that FINISHED, not of invocations.** Full
per-case table with reasoning in `DECISIONS.md` D1–D3.

### Completion Notes List

- **Recording is automatic and unconditional below `createRun`.** No flag, no command, no
  predicate. Opt-in recording is the failure mode this story names first, and plant 7 shows
  eleven tests catching it.
- **A failed scorecard write cannot change an outcome, and the signature is what enforces it.**
  `appendRecord` returns `Promise<void>` and has no rejection path; the call site in
  `verify.ts` has deliberately no try/catch, because a caller that had to guard is a caller
  that could get the guard wrong.
- **Concurrency:** one record = one `write(2)` under `O_APPEND`, records bounded so a line
  stays inside the size where that holds. Not guaranteed on NFS; no lock is taken, on purpose.
  Tested with 20 concurrent stores. `DECISIONS.md` D6 and the module header state the limits.
- **Local-only is structural:** the `scorecard-is-local-only` depcruise rule plus a global-`fetch`
  source scan, both planted and seen red.
- **Nothing untrusted enters the file:** counts and enums only — no criterion statements, no
  stage details, no hints, no evidence, no SHAs, no paths. Every remaining string is bounded
  and redacted (`boundedText`, 256-byte cap). Secret-absence is asserted, never marker-presence
  (Epic 3 retro §7). Skip warnings carry zod paths and codes but never an issue `message` or a
  value from the file.
- **The corpus suite passes with recording on** — `pnpm test:corpus`, 14 passed. Confirmed for
  alice, bob and pamela, who all asked.
- **Deliberately NOT built:** `scorecard add` / `scorecard summary` (6.6), any attribution
  (FR-34, 6.6), any corpus fixture, anything under `src/authoring/**`, any workflow file, any
  retention or rotation policy (Q11/Q12/Q50/Q51 record keep-all; bounding the file is an ADR —
  raised in `DECISIONS.md` D11, not implemented), any exit code, and any network call in any
  form.
- **`src/infra/scaffold.ts` was NOT touched:** `specwitness init` already writes
  `scorecard.jsonl` into `.specwitness/.gitignore` (`scaffold.ts:43-50`, reserved by story
  1.4). I had provisionally claimed that file in my intent and withdrew it in a rebroadcast.
- **`aggregate()` is called by nothing here.** The outcome is READ off the finished
  `RunResult`, which is stronger than re-invoking it: there is no second answer to compare.
- **Limitation, stated rather than hidden:** the concurrency guarantee is argued from POSIX
  semantics and tested in-process on one filesystem. It is not tested on NFS, and Windows is
  out of scope for this epic. Linux and macOS both run the suite in CI.
