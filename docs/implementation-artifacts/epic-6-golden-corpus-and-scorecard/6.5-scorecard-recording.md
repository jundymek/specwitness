## Story

As hypothesis instrumentation,
I want every run appending a local scorecard record automatically,
So that dogfooding data accumulates without ceremony (FR-33, NFR-4; brief §54).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` § "Story 6.5" (authoritative — expand, never weaken):

1. **Given** any completed run
   **When** it persists
   **Then** a record (run id, epic, verdict/outcome, per-status criterion counts, durations, provider invocations, retry/flaky counts, infra errors) is appended to `.specwitness/scorecard.jsonl` — **locally only, no network I/O anywhere in the scorecard path**.

Clarifications (detail only, no weakening):

- **"Without ceremony" is the requirement, not a nicety.** Brief §54 and NFR-4: the record is appended **automatically**, by every completed run, with no flag to remember and no command to run afterwards. The measurement window is ~30–50 real tasks across weeks; **anything the operator must remember to do will not be done**, and the north-star metric will be computed over a biased sample without anyone noticing. **If recording is opt-in, the story has failed its purpose even with every test green.**
- **"Any completed run" needs a definition you must write down, and the interesting cases are the failures.** A PASS run obviously records. So does a FAIL, a NEEDS_HUMAN, and — **most importantly** — an infra-errored run: infra-error rate is one of the metrics 6.6 must report, so a run that dies of infrastructure **must still leave a record**, or the metric is structurally unmeasurable. Decide and document what happens for: a run killed by a signal, a run that never got past config validation, a `--no-ai` run, and a run whose contract failed integrity. **State each answer and its reasoning**; the defensible line is roughly "a run that produced a classified outcome records; an invocation that never became a run does not", but you own the decision and 6.6 depends on it.
- **⚠️ THE SCORECARD MUST NEVER CHANGE A RUN'S OUTCOME. THIS IS THE STORY'S HARDEST RULE.** Recording is instrumentation, and instrumentation that can fail a verification is worse than no instrumentation. If the scorecard file is unwritable, locked, on a full disk, or corrupt:
  - the run's **verdict and exit code are unaffected**;
  - the failure is surfaced (a warning, not silence — a scorecard that silently stops recording is a metric that silently becomes wrong);
  - **it is never an `InfraError` that changes exit code**, and never a FAIL.
  **Test this directly** with an unwritable path. The temptation is to treat a failed write as a real error, because everywhere else in this product a failed write *is* one.
- **Concurrency is real and you must decide about it explicitly.** Two `specwitness verify` runs can execute at once — the harness is a multi-agent system, and Epic 5's own waves ran five agents in parallel. JSONL append is *usually* atomic for small records under `O_APPEND`, and "usually" is not a design. **Decide, document the guarantee you are providing and its limits, and test concurrent appends.** A single interleaved line corrupts one record; per ADR-008 §5 the summary must survive that, but you should not rely on the reader to paper over a writer you never thought about.
- **ADR-008 binds this story, and it was decided for you.** Read `docs/adr/ADR-008-persisted-envelope-strictness.md` in full. It answers action item e5-D and rules directly on `scorecard.jsonl`:
  - each line is an **independently-parsed record carrying its own `schemaVersion`**;
  - a record whose only failure is **unknown keys** is **skipped with a warning naming the line number and the unknown fields**, and the summary continues;
  - a **malformed** line is likewise skipped-with-warning rather than fatal;
  - **`scorecard summary` reports the count of skipped records**, so a silently shrinking denominator is impossible.
  This is deliberately softer than for single-document artifacts, and §5 explains why: an append-only log accumulated across versions is still evidence when partially readable. **Register `scorecard` in `src/schemas/versions.ts` as a one-line addition** — that file's header describes exactly this move.
- **Local only. No network I/O anywhere in the scorecard path** — the AC says it and it is a founding product rule (`CLAUDE.md`: *"Local-first: no SaaS, no web UI, no cloud telemetry"*). **This is the one place in the product where someone might reasonably think telemetry belongs, which is precisely why the AC forecloses it.** Make it structurally impossible, not merely absent: no HTTP client imported into the scorecard module, and a dependency rule or test that would catch one being added. **Say in the module header that this is a product rule, not an oversight**, so a future contributor does not "improve" it.
- **The fields are named in AC1 and each has a meaning 6.6 will compute over. Get them right and write them down:** run id, epic, verdict/outcome, **per-status criterion counts** (pass/fail/needs_human/error/skipped — and note that `skipped` is the subject of open action item **e4-D**, so record it faithfully and do not editorialise), durations, **provider invocations** (the count is what proves the AI-free-run share 6.6 reports), retry/flaky counts (story 5.4's `flakiness`), and infra errors.
- **Redaction applies.** A scorecard record is derived from run data that includes provider text and command output. **Nothing untrusted or unredacted enters the file** — prefer counts and enums over free text, and where free text is unavoidable, redact and bound it exactly as the run does (`src/domain/evidence.ts` — `redactText`, `boundedText`). **A scorecard is the file most likely to be pasted into an issue**, so it is the file least able to afford a leak.

## Dev Notes

### Goal & Context

**This is the instrumentation that decides whether SpecWitness was worth building.**

The product hypothesis — brief §54, PRD SM-1 — is that independent epic-level verification finds *real defects that already passed coding-agent tests, Codex review and supervisor review*. Nobody knows whether that is true. Epic 7 answers it by gating a real epic and measuring; **your file is the measurement**, and 6.6 is the arithmetic over it.

That gives your story an unusual property: **its defects are invisible until they have already destroyed the thing they were measuring.** A recording path that silently skips infra-errored runs produces an infra-error rate of zero — a number that looks like good news. A recording path that is opt-in produces a biased sample nobody can detect after the fact. A record whose fields 6.6 misreads produces a north-star metric that is confidently wrong. There is no test in Epic 7 that catches any of these, because by then the only evidence is the file itself.

So the two disciplines that matter most here are: **record automatically, including on the paths that failed**, and **write the field semantics down completely** for the agent in wave 3 who will compute over them and cannot ask you what you meant.
