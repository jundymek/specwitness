- **⚠️ WHY THIS STORY EXISTS, IN ONE PARAGRAPH.** Five merged integration suites — `tests/integration/surfaces/browser.test.ts`, `browser-security.test.ts`, `browser-adaptation.test.ts`, `browser-dispatch.test.ts`, `browser-combined-evidence.test.ts` — sit behind `describeWithBrowser` (`tests/integration/surfaces/helpers/browser-fixture.ts:114`), which calls `describe.skip` when `BROWSER_ENVIRONMENT.ready` is false. **`@playwright/test` is an optional peer** (a binding spine decision, `ARCHITECTURE-SPINE.md:153`), so `pnpm install --frozen-lockfile` does not bring it and nothing downloads chromium. **On every CI runner, all five skip and the job goes green.** Epic 5's retro §9 names the same gap from the other side: *"a real browser download — performed by no gate on any platform in this epic; provisioning is proven against an injected `ProcessRunner`."* **You are closing it.**

## Dev Notes

### Goal & Context

**Epic 5 shipped a browser verification surface that has only ever run on one machine.**

The five suites are good — real chromium, real `ProcessRunner`, real classification, a dedicated security suite. They also self-skip whenever no browser is present, which on every CI runner is always, because Playwright is an optional peer by binding spine decision and nothing downloads a browser. So the check goes green, and the greenness means five suites did not run.

That is the project's oldest hazard wearing new clothes.     orphan 7826: exited on its own after 0s

```
BROWSER SURVIVAL SCAN (after a run killed with SIGKILL (no afterEach ran))
  RESULT: no surviving browser process (scanned after 0.0s)
==> [5/5] reaping anything that survived
    nothing to reap
```

**Why the kill is a GROUP kill and not a tree kill, and why that is the honest simulation.** My
first version killed the runner's whole descendant closure — which killed Playwright too and
reported "no survivors" in 0.1s, proving only that killing the browser kills the browser.
`src/infra/process-runner.ts` spawns `detached: true`, so Playwright and its browser get their
**own process group** while remaining descendants in the ppid chain; a CI cancellation kills the
step's process group, so a detached child survives, orphaned. The check now kills only descendants
sharing the runner's pgid and deliberately spares the rest — which is why two processes appear in
the SPARED line above. **Those two are the leak candidates, and both terminated on their own
within a second.**

**The bounded claim.** This says the detached Playwright group is self-limiting on
`ubuntu-latest` under Node 22.13 for `browser.test.ts`, killed at one point in its run — not that
no configuration can leak. The mechanism is almost certainly stdio: the orphan's pipes lead to a
dead worker. A run killed while chromium is mid-navigation with a longer Playwright timeout is a
case nobody has measured.

The scan itself was seen red: `tests/integration/browser-leak-check.test.ts` drives synthetic `ps`
output containing a `headless_shell` under the registry, a `chrome_crashpad_handler`, and a leaked
`@playwright/test/cli.js` runner, and asserts exit 1 with the full argv reported in each case.

The AD-3 injection surface is now proved absent on two operating systems rather than one.

**Finding 1 — the story spec's stated cause is half wrong, and the wrong half changes which code
path runs. (Reported; no code change; no ADR.)** The spec says `@playwright/test` being an optional
peer means *"`pnpm install --frozen-lockfile` does not bring it"*. pnpm's auto-install-peers
resolves the optional peer into the root importer's dependencies in `pnpm-lock.yaml:11`, so the
package **is** installed; what is missing on a fresh runner is the **browser binaries**. Three
independent confirmations: a fresh `pnpm install` here printing `+ @playwright/test 1.62.1`; the
baseline CI log printing `no browsers are downloaded` rather than an `absent` reason (that string
is chosen by `browser-fixture.ts`'s `announce()` only when `source !== 'absent'`); and my own run
printing `source: project, browsersPresent: false`. **Consequence:** CI takes 5.1's route 2, and
browsers land in `~/.cache/ms-playwright`, not `~/.cache/specwitness/playwright`. Caching the
wrong directory would have re-downloaded chromium on every run.

**Finding 2 — a sixth browser-dependent suite that no skip counter can see.**
`tests/integration/surfaces/conformance.test.ts` resolves 5.1's environment directly (line 136)
and, with no browser, narrows `SURFACES` from four to three (lines 142-150). It does not skip, so
it appears in no skip report and is not in `tests/unit/browser-gated-suites.test.ts`'s list of
five. **Measured:** the baseline run reports `conformance.test.ts (15 tests)` and my browser run
reports `conformance.test.ts (15 tests)` — *identical test count, one more surface asserted over*.
A suite that quietly asserts less is invisible to every counter in the repository. It is included
in this job, `tests/unit/browser-ci-coverage.test.ts` keeps it included, and the file itself is
untouched.

**Finding 3 — SpecWitness's provisioning downloads a browser but installs no OS packages, and on
`ubuntu-latest` that turned out to be fine.** `installBrowsers` runs `playwright install chromium`,
never `install-deps`, so no system shared libraries are installed and none of it needs `sudo`.
Chromium launched and drove 61 tests without them. **This is a fact about the GitHub
`ubuntu-latest` image, not about Linux**: a leaner container may well need `libnss3`/`libatk` and
would fail at launch — which 5.2 classifies as `execError` / criterion `error`, correctly, never as
a pass. Carried, not fixed: adding an `install-deps` step would hide a real environment signal
behind `sudo`, and changing provisioning is out of scope.

**Finding 4 — an absolute browser-process scan is unusable, and this is a measurement.** My first
leak checker matched browser processes absolutely and reported **77 survivors on a clean local
run**, because every Electron application answers to `--type=renderer` and ships a
`chrome_crashpad_handler`. Narrowing the patterns until the laptop went quiet would have narrowed
away precisely the helper processes most likely to outlive their parent. The check became a
baseline diff instead. Recorded because anyone writing the next process-hygiene check will hit it.

**Not a finding, worth stating:** `verify (ubuntu-latest)` and `verify (macos-latest)` still report
the same 5-file/10-suite/42-test browser skip. That is correct — those runners have no browser and
`describeWithBrowser` is untouched. **A machine without a browser must still be able to run the
suite**, and the new job provides a browser rather than deleting the fallback.

### Proposed promotion criterion

The job lands **non-blocking** (`continue-on-error: true`). I propose the owner promotes it to
required when **all four** hold:

1. **Ten consecutive `browser (ubuntu-latest)` runs green over at least seven days**, across at
   least three different PR branches. Ten and a week, because flake is a rate: this job's slowest
   single test is 36s and the suites total 72s, so a real flake surfaces within days, not hours.
2. **Zero survivors in every one of those runs**, from both AC4 steps — including the cancelled-run
   check, which is the one that can leak.
3. **The cold-cache path exercised at least twice** in that window (a cache key change, or an
   eviction), with the job still finishing under **5 minutes**. 113s cold today; the budget is for
   a bad network day.
4. **The `install-deps` question answered** (Finding 3): either the runner image is confirmed to
   carry chromium's shared libraries as a stable property, or the job is made to fail loudly and
   specifically when a launch failure is a missing-library failure. A required check that goes red
   because GitHub changed its image, with a stack trace nobody can read, is exactly the
   ignore-red outcome this criterion exists to avoid.

**Promotion is then two changes:** delete `continue-on-error: true` from the `browser` job, and add
`browser (ubuntu-latest)` to branch protection. That second half is an owner action needing admin
rights this agent does not have, and there is **no branch protection on this repository at all**
today — verified this session: `gh api .../branches/master/protection` → `404 Branch not
protected`, the same for the epic branch, and `.../rulesets` → `[]`.
