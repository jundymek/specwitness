## Dev Notes

### Goal & Context

**Epic 5 shipped a browser verification surface that has only ever run on one machine.**

The five suites are good — real chromium, real `ProcessRunner`, real classification, a dedicated security suite. They also self-skip whenever no browser is present, which on every CI runner is always, because Playwright is an optional peer by binding spine decision and nothing downloads a browser. That is the project's oldest hazard wearing new clothes.   grows between scans — but a process seen at `T` with elapsed `E` started at `T − E`, and **that
  instant is stable**. Identity is now pid **plus** that computed start, with a 3s tolerance for
  `etime`'s one-second resolution; an older pid-only baseline still matches on pid rather than
  reading as a mismatch. Both directions seen red, and verified against the real 82-process table
  on this machine.
  - *A note on the fixture, recorded because it cost me a cycle:* elapsed grows by exactly the
    wall-clock that passed between samples — that is what keeps the computed start fixed — so a
    test fixture cannot grow it faster than the test takes to run. Growing it 4s while real time
    advanced none is what failed first, and **the tolerance was not the thing that was wrong.**
- **Codex review, sixth round: one P1 — the vacuity guard could itself be vacuous.** The best
  finding of the six, because it landed on the thing I was most confident about. The
  cancelled-run check waits for a browser before killing, precisely so it cannot report *"nothing
  survived a cancelled run"* about a run that never started one — and it detected launch by
  asking the scanner for a non-zero exit. **Two independent defects made that fire without a
  browser, and either alone was enough:**
  1. The scanner deliberately matches the **detached Playwright runner** (leaking it is a leak),
     and that process **starts before chromium**. A kill could land after the runner started and
     before any browser existed.
  2. The scanner also exits non-zero when it **cannot look**. A failing `ps`, or a missing
     baseline, read as a positive detection.
  - Both closed. `--browsers-only` narrows the match to real browsers and never the runner; and
    **the exit code now discriminates — `1` survivors FOUND, `3` the scan COULD NOT LOOK.** That
    is the product's own taxonomy (ADR-002 / AD-6) applied to a script that had been collapsing a
    finding and an infra failure into a single number. Only a `1` counts as a launch; a `3`
    aborts, kills the tree and exits 3. Six cases, five seen red; verified with a failing `ps`
    stub as well as the happy path.
  - **One of those was a wrong TEST rather than wrong code**, and it is worth saying so: it
    asserted the runner's pid was absent from the output, but that pid appears in the surviving
    browser's PPID column. The assertion moved to the runner's argv.
- **Codex review, seventh round: one P1 — the reaper could have killed the operator's own
  browser.** The most serious finding of the seven, and **my own log already contained the
  instance.** Detection is broad on purpose; *"suspicious enough to REPORT"* is a far weaker claim
  than *"mine, so safe to SIGKILL its entire process group"*. Run locally, a browser window opened
  during the wait matches the patterns, is absent from the baseline, and would have had its whole
  group signalled — and an early local run of the cancelled-run check **did** report a Vivaldi
  renderer that appeared during its 120-second wait. With reaping armed, this script would have
  killed my browser. I had read past that line at the time.
  - Ownership is now required before signalling, in two bounds: a group is owned when at least one
    member runs a binary out of **the browsers registry this job was given** — the whole group
    then goes, because a browser is a tree and its helpers do not all name the registry — and
    `--owned-pgid` lets a caller that knows exactly which groups it spawned say so. The
    cancelled-run check passes the groups it spared, which it had been computing all along.
    Everything else is **reported and left alone**, with the reason printed; the exit code is
    unchanged, because an unowned survivor is still a finding.
- **Codex review, eighth round: one P1 — a regression from my own previous fix.** I had composed
  the two ownership bounds as **AND**, so a caller that *knew* a group was its own still had the
  registry heuristic veto it. The case that exposes it is the one the cancelled-run check exists
  for: chromium exits, its detached `@playwright/test/cli.js` runner does not, and the runner is a
  survivor whose argv names no registry path — so reaping was refused, leaving behind exactly the
  process being cleaned up. Either signal is now sufficient. **The correction also proved an
  assertion I had written earlier wrong**: I encoded the caller's list as a *narrowing* filter,
  which would refuse to reap a genuine registry-owned survivor — *detect the leak and walk away*,
  a fourth time, this time written into a test.
- **⚠️ AND THEN THE JOB ITSELF WENT RED, WHICH IS THE FIRST TIME IT EARNED ITS KEEP.** Run
  [33913171525](https://github.com/jundymek/specwitness/actions/runs/33913171525),
  `browser (ubuntu-latest)`, **exit 64** — a defect of mine that neither local runs nor eight
  review rounds had caught. The descendant walk and the per-pid pgid lookup are separate `ps`
  calls, so a short-lived child can exit between them and the lookup returns an **empty pgid**.
  Handled nowhere, it produced two defects from one missing branch:
  1. **It corrupted AC4's evidence in the direction that flatters it.** An empty pgid means the
     process is already GONE, not detached into its own group — but it was classified as
     **SPARED**. The run reported *eight orphans, seven of which "exited on their own after 0s"*,
     because seven had exited **before** the kill. Vanished processes are now counted and printed
     as their own line, and they are not orphans.
  2. **It caused the exit 64.** The empty pgid emitted `--owned-pgid` with no value; the parser
     took the following `--label` as that value and the label text read as a bare argument. The
     caller now skips non-numeric pgids **and** the parser validates rather than swallowing the
     next flag — *"the caller should not do that" is not a parser.*
  - **The evidence quoted above is unaffected, and I checked rather than assumed:** run
    33894470397 spared `7813:7813` and `7826:7813`, both real pgids in one group, so those two
    orphans were genuine and their `1s`/`0s` stand. Only the latest run hit the empty-pgid path.
  - **This is the single best argument in the story for the job existing at all.** A defect in the
    process-hygiene evidence, invisible to eight adversarial reviews and to every local run,
    surfaced the first time the code met a real Linux runner under real timing.
- **Codex review, ninth round: one P1 — and it defeated my own reasoning about an accepted
  residual.** When chromium exits but its detached `@playwright/test/cli.js` runner does not, the
  runner is reported — but the normal-exit step supplies no `--owned-pgid` (it does not know the
  pgids) and the runner's argv names no browsers registry, so it was reported and **left
  running**. I had recorded that as the conservative default and moved on.
  - **The half I missed: the NEXT check takes a fresh baseline, which then contains that process,
    and subtracts it.** The job finishes carrying exactly the leaked tree AC4 exists to clean up,
    and nothing reports it a second time. **Reported-then-hidden is worse than reported**, and the
    note in an earlier draft of this record calling it a safe default was wrong.
  - `--owned-under` closes it precisely: the runner's argv carries its `cliPath`, which lives
    under the workspace this job checked out; an operator's own Playwright, in another project,
    does not. The CI step passes `$GITHUB_WORKSPACE`; the cancelled-run script passes its own
    repository root. **A value of `/` or a relative path is refused with exit 64** — a directory
    that claims everything is not an ownership signal, it is the destructive direction wearing a
    flag. Four cases, two seen red.
  - Verified end to end locally on the fixed code: **six real orphans across two groups, every one
    measured at 1s from the kill** — where the old per-orphan deadline would have reported
    `1s, 0s, 0s, 0s, 0s, 0s`.

- **Codex review, tenth round: one P2 — a live hazard on the machine this was written on.**
  `--owned-under` matched by **substring**. This story was written in one of **six sibling agent
  worktrees** under `/Users/jundymek/dev/specwitness-agents/`, beside a main checkout at
  `/Users/jundymek/dev/specwitness` — and `specwitness` is a prefix of `specwitness-agents`. So
  `--owned-under <main checkout>` would have classified **a peer agent's Playwright process group
  as mine and SIGKILLed it**, while five other agents were mid-story. Ownership now requires the
  separator (`dir` + `/`): that is what makes it a path rather than a spelling. One case, seen red.
- **Codex review, eleventh round: CLEAN.** *"No discrete correctness issues were identified in the
  changed implementation. The browser CI workflow, provisioning path, suite coverage checks, and

  the log rather than the status line — which reported `auto_review_clean` four separate times on
  this branch while the log carried real findings.
- **⚠️ THE REAPER HAD THREE DESTRUCTIVE-DIRECTION DEFECTS, AND LISTING THEM TOGETHER IS THE POINT.**
  All three were mine, all three were in code whose entire purpose is process hygiene, and all
  three were caught by review rather than by me:
  1. **No `pgid <= 1` guard** before `kill -TERM -<pgid>` — `-1` signals **every process the user
     owns**. (Found by my own security review.)
  2. **Broad pattern matching decided what to SIGNAL**, not merely what to report — it would have
     killed **the operator's own browser**, and a Vivaldi renderer was already sitting in my log
     when I first ran it.
  3. **Substring path matching** for owned directories — it would have killed **a peer agent's
     process tree** in a sibling worktree.
  4. **Substring matching for REGISTRY ownership** — the same bug as 3, four lines away, found one
     round later; it would have killed **an unrelated browser or a concurrent Playwright run**.
  - Every fix narrowed *what may be signalled* without narrowing *what is reported*. Detection
    stayed broad throughout; the first version simply did not make that distinction at all, and
    three separate reviews were needed to install it.

- **⚠️ Codex review, thirteenth round: one P1 — I WROTE THE LESSON INTO THE RECORD AND THEN
  REPEATED IT.** This story's headline finding was already written down: *after each fix I
  repaired the site that was reported and did not ask where else the shape lived.* One round after
  making `--owned-under` separator-aware — having just described that failure mode — **I left the
  identical prefix bug in the registry ownership check four lines away.**
  `--browsers-path /cache/ms-playwright` still claimed anything under `/cache/ms-playwright-other`
  and authorised SIGKILLing its whole process group.
  - Fixed by splitting the two questions into two named functions: `matchesRegistry` (substring,
    for **detection**, broad on purpose) and `isOwned` (separator-aware, for **the reaper**,
    because permission to signal is a far stronger claim than a suspicion). Two cases, one red.
  - **The generalisation was correct and I still did not apply it, which says the lesson has to be
    a MECHANISM rather than a paragraph.** Two named functions is that mechanism: the next person
    to widen a pattern will find it hard to widen the signalling half by accident. That is the
    single most useful sentence this story can hand the retrospective.

- **⚠️ A REQUIRED CHECK WENT RED ON THIS PR, AND IT WAS NOT MINE — ESTABLISHED, NOT ASSUMED.**

#### The last three rounds, and the tally they produced

**Round 16 — P2, and the supervisor caught me recording over it.** A finding landed against my
current head and I recorded `codex_review: addressed` **without ever opening it** — the exact
failure I had spent twelve rounds avoiding, committed at the last step. The finding was right:
identity was pid plus a start time *derived* from `etime`, which needed a ±3s tolerance, and **a
pid reused inside those three seconds fell back into the hole the rule existed to close.** Now
keyed on `lstart`, an absolute instant `ps` measures, compared exactly — a derived value needs a
band; a measured one does not. Residual stated: `lstart` has 1s resolution, so same-second reuse
would still collide.

**Round 17 — P1, the recursive one.** `cancel-in-progress: true` means a superseded push cancels
this step routinely, and if that landed between sparing the detached group and the explicit reap,
**the script would leave behind exactly the browser tree it created on purpose.** The trigger is
not hypothetical here: two `verify` jobs on this branch already show `cancelled`. Reaping is now
an `EXIT`/`INT`/`TERM` trap rather than something trusted to reach the last line.

⚠️ **And what I could not demonstrate, stated plainly.** I tried to see it red — SIGTERMing the
check while a real browser was up, first with the trap and then with it deliberately disabled.
**Neither run leaked**; on macOS the orphan self-terminates in about a second. So the trap is
**defensive, justified by reasoning rather than by a reproduction**, and I am not claiming a
seen-red guard. What is demonstrated is that it preserves the normal path and the exit code.

**Round 18 — P2, against the fix from round 17.** The trap was armed before `descendants()` was
defined, so a cancellation in that window would have called an undefined command and reaped
nothing — **the safety mechanism moved the failure into the guard itself.** General form, now in
the comment: *a cleanup handler may not depend on code that runs after it becomes reachable.*

#### Round 19 — P2, the fifth destructive-direction defect, and pid reuse for the third time

After the runner is killed and reaped, `runner_pid` refers to nothing. The orphan wait that
follows runs for up to `WAIT_SECONDS` (180 in CI), and if the OS hands that pid to an unrelated
process in the meantime, the EXIT trap would walk **its** descendants and SIGKILL a process tree
with nothing to do with this check. Cleared rather than verified — there is no handle left worth
keeping, and the trap still reaps the detached groups by pgid with the scanner's guards in front.

**Pid reuse has now bitten this story three separate times, which earns a general form rather than
three fixes:**

> **A pid is not an identity, and a dead pid is not a handle.**

| | where | symptom |
| --- | --- | --- |
| 1 | baseline identity keyed on pid | subtracted a reused pid — **false clean** |
| 2 | ±3s tolerance on a *derived* start time | the same hole, narrowed — **false clean** |
| 3 | a stale `runner_pid` held across a 180s wait | the trap would **destroy an unrelated tree** |

The first two made the instrument report in my favour; the third would have made it destroy
something. **Same root, opposite symptom** — which is why the fixes went to *measured* identity
(`lstart`, exact equality) and to *not keeping* handles that no longer refer to anything.
