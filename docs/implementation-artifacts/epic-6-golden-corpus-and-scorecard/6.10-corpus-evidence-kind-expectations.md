## The consequence today, stated exactly

Story 6.2's AC1 (`docs/planning-artifacts/epics.md:877-879`) reads:

> **Then** the expected verdict, failing criterion ids, and **evidence kinds** match `expected.json` exactly

Two of those three clauses are mechanically pinned by the merged format. The third is not, and cannot be, without this story. Until it lands, the corpus is **silent** about evidence kinds — and the corpus's own governing rule is that silence must never be readable as a claim. A future reader opening a green corpus should not be able to conclude that evidence kinds are pinned, because they are not.

## Story

As the reader of a corpus fixture six months from now,
I want an `expected.json` to be able to pin the **kinds** of evidence a run produced, in the same hand-written, mechanically-compared way it already pins the verdict and the criterion statuses,
So that a change which quietly stops a verification surface from producing evidence turns a fixture red instead of passing unnoticed (FR-15, AD-6, story 6.2 AC1).

## Acceptance Criteria

**Not from `epics.md`** — this story was written by the supervisor during Epic 6 wave 2 (see Provenance). Its ACs are stated here in full and are authoritative.

1. **Given** an `expected.json` carrying an optional `evidence` expectation
   **When** the corpus runner compares a fixture's run against it
   **Then** the distinct `kind` values in the run's `document.evidence` are compared against the expectation, and a mismatch is a **fixture failure naming the kinds expected and the kinds observed** — not a warning, not a log line.
2. **Given** an `expected.json` that omits the `evidence` key entirely
   **When** it is loaded and compared
   **Then** it loads and passes exactly as it does today, asserting nothing about evidence — the key is **additive and optional**, so no merged fixture is *required* to change and none changes meaning by virtue of this story landing.

   This is a statement about the **format's backward compatibility**, not a prohibition on editing fixtures. Deliberately strengthening a selected fixture by *adding* an `evidence` expectation to it is exactly what Task 5 asks for and is permitted. What AC2 forbids is a fixture's meaning changing **without its author touching it** — the silent reinterpretation `tests/corpus/expected.ts:39-46` exists to prevent.
3. **Given** the expectation's `assertion` discriminator
   **When** it is `exact`, the observed set of kinds must equal the expected set; **when** it is `subset`, every expected kind must be present and additional kinds are permitted
   **And** `assertion` is **required whenever the `evidence` key is present**, so that a fixture can never be read as making the stronger claim when its author meant the weaker one.
4. **Given** the change to `ExpectedOutcomeFileSchema`
   **When** an author decides whether `EXPECTED_VERSION` must be bumped
   **Then** the decision is **recorded in the code with its reasoning**, consistent with `tests/corpus/expected.ts:39-46` (*"a change to the format is a visible, dated event rather than a silent reinterpretation of files nobody re-read"*) and with the additive-evolution posture of **ADR-008** — and whichever way it goes, a fixture written against the old version still loads or fails loudly, never silently reinterpreted.
5. **Given** the new comparison path
   **When** the story is delivered
   **Then** at least one hand-written fixture **proves it goes red on a kind mismatch** — planted, seen red, and recorded in the Verification log — because a comparison nobody has watched fail is exactly the green-for-nothing this corpus exists to catch.

## Dev Notes

### Goal & Context

The corpus exists to make silent regressions loud. It currently pins what a run *concluded* — verdict, exit code, criterion statuses — and is entirely silent about what a run *observed*. Those are different failures. A change that leaves the verdict correct while a verification surface quietly stops producing evidence is invisible to every fixture merged today, and it is precisely the shape of defect this project has now hit twice at other altitudes: Epic 4's retrospective named it at the criterion level (*"every new way for a criterion to produce no attempts is a new way to reach green-for-nothing"*), and Epic 6's story 6.9 exists because it recurred at the CI level, where five browser suites self-skipped into a green check.

This story closes the same hole one level down, in the artifact that is supposed to be the product's own witness.

### Exact scope

- `tests/corpus/expected.ts` — one optional key, its inner shape, and the version decision.
- `tests/corpus/runner.ts` — one comparison branch inside `compareOutcome`.
- One new proving fixture under `fixtures/corpus/`.
- Optionally, `evidence` expectations added to already-merged fixtures (Task 5).
- The unit tests for all of the above.

### Out of scope (do NOT build)

- **Any change to `src/`.** This is a test-side format. The product's `EvidenceSchema` is correct as it stands and is not yours to touch.
- **Pinning evidence *contents*** — URLs, bodies, exit codes of observed commands, screenshots. Kinds only. Contents are a much larger design question about normalisation and secrets, and it is not this story's.
- **A regeneration affordance of any kind.** Not a script, not a flag, not a `--update` mode. It is forbidden by story 6.1's merged tests, stated in three module headers and in `fixtures/corpus/README.md`, and a red fixture is a question to answer by reading the run directory the failure names.
- **Relaxing `.strict()`** anywhere. The key is additive and optional; strictness stays.
- **Renumbering any existing fixture.** Four merged ACs across Epics 4 and 5 name fixtures by number.

### Dependencies & upstream contracts (by ID)

- Story **6.1** (merged, PR #64, `d428664`) — the corpus runner, `ExpectedOutcomeFileSchema`, `EXPECTED_VERSION`, the hermetic e2e harness. **Your contract.**
- Story **6.2** (Epic 6 wave 2) — the fixtures whose AC1 this story lets someone finally satisfy in full. **This is a BLOCKING dependency for Task 0's last item and for the whole of Task 5**, both of which read or modify 6.2's *merged* fixtures. This story stays `backlog` until 6.2 merges.
- **ADR-008** (`docs/adr/ADR-008-persisted-envelope-strictness.md`) — additive optional keys over relaxed strictness. **Note carefully: ADR-008 binds `src/schemas/versions.ts` and persisted product artifacts. `expected.json` is a test-side format and is NOT among them.** Follow the ADR's *posture* because it is the house style; do not claim it as binding, and do not import its version-skew `InfraError` machinery into a test harness where exit codes mean nothing.

### Architecture compliance

- **AD-3** — nothing here reaches a shell. The comparator is pure.
- **AD-6** — evidence belongs to a run document; you read it, you never synthesise it.
- Verdicts stay mechanical. A kind comparison is set arithmetic and must remain so.

### Testing requirements

- **TDD, and the failing test must actually be seen red.** AC5 is not satisfied by a test that has only ever been green.
- Tests spawn no real `claude` / `codex` and touch neither `~/.claude/` nor `~/.codex/`.
- The proving fixture's `expected.json` is **hand-written**.

### Failure modes (what "wrong" looks like here)

- **The comparison passes vacuously** — an empty expected set, or a fixture whose run produces no evidence at all, quietly satisfying `subset`. Guard it and test the guard.
- **`assertion` made optional with a default.** A defaulted discriminator is exactly the silence-read-as-a-claim this format forbids; AC3 requires it present.
- **Kinds compared as an ordered array.** They are a set. Two fixtures differing only in evidence order must not disagree.
- **A stringly-typed kind list.** The six kinds are a closed union in `src/schemas/result.ts`; a typo in a fixture must be caught at load, not silently never-matched.
- **Retro-fitting merged fixtures without saying so** (Task 5) — and then being surprised that `codex_review` and `security_check` went stale, because `fixtures/corpus/` is **not** in `REVIEW_IGNORE_PATHS`.

### Security

Low surface: no subprocess, no network, no credential path. The one thing to watch is that a failure message naming expected-vs-observed kinds must not start quoting evidence *contents* — kinds are safe to print, request bodies and provider payloads are not.

### Project Structure Notes

Everything lands under `tests/corpus/` and `fixtures/corpus/`. No `src/` file is touched, so no dependency-cruiser boundary is engaged.
