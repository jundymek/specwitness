## The consequence today, stated exactly — and stated fairly

A user writes this in `.specwitness/config.yaml`:

```yaml
setup:
  install: pnpm install --frozen-lockfile
```

`specwitness doctor` reports the command as resolvable. `specwitness verify` then creates the isolated worktree, records a `setup` stage with status `ok`, and runs the gates **against a worktree in which nothing was installed**. On a fresh worktree of a typical Node project, `pnpm test` in the gates stage then fails because `node_modules` does not exist — and a gate that says no is a **product FAIL, exit 1** (`src/domain/stage.ts`: `failed` — *"ran and produced a PRODUCT-relevant negative outcome"*). **A missing install is an environment problem being reported as the project's code being wrong. That is the exact inversion this product exists to prevent** (`CLAUDE.md`: *"Infra failures are never reported as product FAIL"*).

**Two things keep this from being silent, and the spec states them rather than overselling the defect:**

1. The placeholder records a timeline entry reading `not implemented yet — Epic 4 runs the configured install command`, and that detail is rendered and persisted. A reader of the terminal report or `result.json` **can** see that the setup stage did nothing. `src/pipeline/stages/placeholder.ts` says this is deliberate: *"a run of today's pipeline says plainly which parts of verification are not built yet instead of implying they passed."*
2. Every corpus fixture and every existing test passes today, because none of them declares `setup.install` — the fixtures install nothing and the gates they run need nothing installed.

**So the defect is not "a silent green stage". It is that `doctor` and `verify` disagree about whether a config key is live**, and the user is told by the command whose whole job is pre-flight validation that the key is fine. A user who reads `doctor` and does not also read the setup line of every run report gets gates run against an uninstalled tree. **The first reader of the new README is the author, dogfooding this on a real epic in Epic 7** (`docs/planning-artifacts/roadmap.md`), and a real project that declares an install is the normal case, not the edge case.

## Story

**As a** developer running SpecWitness against a project whose gates need installed dependencies,
**I want** the `setup` stage to actually run my configured `setup.install` command inside the verification worktree,
**so that** my gates and probes execute against a working tree, and a failed install is reported as an infrastructure error rather than as my code failing.

## Acceptance Criteria

Authored for this story; there is no `epics.md` entry to expand. **Expand, never weaken.**

1. **Given** a Project Config declaring `setup.install`
   **When** `specwitness verify` runs
   **Then** that command is executed inside the verification worktree, after the `worktree` stage and before the `gates` stage, and the `setup` timeline entry reports it ran — with the command, its exit code and its duration.
2. **Given** a Project Config declaring **no** `setup.install`
   **When** `specwitness verify` runs
   **Then** the `setup` stage is `ok`, records that nothing was configured, executes no subprocess, and the run is byte-identical in outcome to today's.
3. **Given** a `setup.install` command that **fails** (non-zero exit), is **not resolvable** on PATH, or **times out**
   **When** `specwitness verify` runs
   **Then** the stage status is **`error`**, the run ends with an `{infraError}` outcome and **exit 3 — never exit 1**, the pipeline stops before `gates`, and the run still reaches `aggregate → persist → teardown`. The error carries `ERROR:` + `HINT:` naming the command and the config key.
4. **Given** the same config
   **When** `specwitness doctor` and `specwitness verify` are both run
   **Then** they agree about `setup.install`: a key `doctor` validates is a key `verify` executes. **A test pins this agreement directly** — it is the actual defect this story closes, and it must not be provable only by reading two files.
5. **Given** a corpus fixture declaring `setup.install`
   **When** the corpus suite runs
   **Then** a hand-written `expected.json` pins the install having run, and a second fixture pins the failed-install path producing exit 3 with the gates stage `skipped` rather than `failed`.

Clarifications (detail only, no weakening):

- **AD-3 is the invariant that governs this whole story.** `setup.install` is a Project-Config-declared command and therefore may reach a shell; nothing else may. **Reuse the existing command machinery — do not write a second one.** `src/pipeline/stages/gate-command.ts` already exports `splitCommandLine`, `hasUnterminatedQuote`, `usesUnsupportedEscaping` and `hasGluedExecutableSuffix`, and the gates stage already resolves a bare name on PATH and distinguishes "not installed" from "file not found" (`src/pipeline/stages/gates.ts:293-326`). A second, subtly different command path is a security finding, not a convenience.
- **Read the gates stage before you write anything.** It is the merged, reviewed answer to every question this story raises — timeout handling, process groups, PATH resolution, the `ERROR:`/`HINT:` shape, and how a command's output becomes evidence. `src/pipeline/stages/services.ts` and `src/pipeline/stages/data.ts` are two more precedents for running a configured command; `data.ts:127` records why a data command's timeout is five minutes and reasons about it explicitly. **Pick your install timeout the same way — with a stated reason, not a guessed number.** An install is legitimately slower than a gate; the gates stage chose fifteen minutes (`gates.ts:110`) *because* real gates are `pnpm install` plus a test run, which is itself evidence about the right order of magnitude.
- **The `failed` / `error` split is the point.** `src/domain/stage.ts` states it: *"Collapse them into one 'bad' value and a branch that simply does not build starts reporting as 'the environment is broken, retry' — after which a retry merges it."* This story is the mirror image — an install that did not happen must never surface as the branch being wrong. **There is no case in which a `setup.install` failure yields exit 1.**
- **You add no new exit code and no new stage.** `src/cli/exit.ts` is the single table (0/1/2/3/64, ADR-002) and `STAGE_NAMES` is frozen at eleven. The `setup` name and its position already exist; you are replacing a placeholder body, not extending a sequence.
- **Process groups and teardown already exist and you must use them, not re-invent them.** Story 3.2 shipped process-group handling and `specwitness clean`; an install that spawns children and is then interrupted must not leak them. Read that code before spawning anything.
- **Do not remove the placeholder mechanism.** Six other stages still use `createPlaceholderStage` and its contract — *never fails, records which story fills it* — is load-bearing for them. You are replacing one call site.
- **`doctor` may need no change at all, and that is a legitimate outcome.** AC4 asks for agreement, and today `doctor` is the half that is already right. Verify it, pin it with a test, and say in the PR body that you changed nothing there rather than changing something to look busy.
- **Determinism and evidence.** Whatever the install stage records must satisfy AD-11: `--json` and the terminal report carry the same facts, and timestamps are ISO-8601 UTC. Install output is high-volume and machine-specific — **decide deliberately how much of it is persisted**, and say so, because `result.json` is a durable artifact and an install log can be megabytes. Absolute home paths must not leak into evidence.
- **The corpus fixtures in AC5 carry hand-written `expected.json`** — never generated by the code under test — and `fixtures/corpus/` is **not** in `REVIEW_IGNORE_PATHS`, so a fixture edit re-stales `codex_review` and `security_check` exactly as a `src/` edit does. Land the fixtures, then sign off, in that order.
- **The non-Node fixture (story 6.4) is the interesting AC5 case.** It has no `package.json` at any depth. An install story that only ever proves itself with `pnpm install` has proved something narrower than `setup.install` promises.

that did not happen has produced no product-relevant outcome at all.

So `setup.ts` does not import `stageProductNegative`. That is the mechanism rather than the
convention: **there is no expression in the file that can reach exit 1.**

### The timeout decision

**`SETUP_INSTALL_TIMEOUT_MS = 10 * 60 * 1000` — ten minutes**, chosen between its two
neighbours rather than copied from either, and pinned by a test so a later change is a
deliberate edit to a stated decision.

- **Longer than `DATA_COMMAND_TIMEOUT_MS` (five minutes, `data.ts:127`).** A data command is
  local: a schema drop, a fixture load, no network. An install is network- and disk-bound —
  resolve, fetch, extract, then run lifecycle scripts that may compile native addons. A cold,
  uncached `pnpm install --frozen-lockfile` on a large monorepo is minutes rather than seconds,
  and a cap that fires on a HEALTHY install converts honest work into a spurious exit 3, which
  is the same wrong answer as any other misclassification.
- **Shorter than `GATE_TIMEOUT_MS` (fifteen minutes, `gates.ts:110`).** That file chose fifteen
  *because a real gate is an install plus a full test run*. An install is the smaller half of
  that, and one phase rather than two, so borrowing fifteen would be borrowing a budget sized
  for work this stage does not do.
- **And the argument that actually decides it: what an install hang looks like.** The two common
  ones — a registry that accepts the connection and never answers, and a package manager
  prompting on a TTY that will never arrive — never resolve. Waiting a quarter of an hour to say
  so buys nothing and costs the operator their attention; ten minutes reports it while somebody
  is still watching.

Injectable via `SetupStageDeps.timeoutMs`, so the timeout path is asserted in milliseconds
rather than waited out.
