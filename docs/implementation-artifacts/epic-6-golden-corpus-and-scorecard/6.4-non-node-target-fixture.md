Clarifications (detail only, no weakening):

- **"Demonstrated, not asserted" is the entire story, and the words are the PRD's.** FR-4 says all stack specifics enter *only* through Project Config. Five epics have believed that. Nothing has tested it, because every fixture, test project and integration test in the repository has been a Node project — so a Node assumption anywhere in the pipeline would have been invisible in every run this product has ever done. **You are the first thing that can find one.**
- **Finding a leak is a success, not a setback.** If verify turns out to require a `package.json`, infer a command from one, resolve a binary through `node_modules`, or assume a lockfile — **that is the most valuable output this story can produce.** Report it with evidence. **Fix it only if the fix is small, obviously correct and inside a surface you understand**; otherwise escalate with a written recommendation. A hurried change to merged resolution logic from a fixture story is how stack neutrality gets *appeared* to be fixed.
- **The AC's parenthesis is the sharpest testable form of the claim: no `package.json` in the target.** Assert it structurally — the fixture directory must not contain one, and a test should fail if someone adds one later. **This is the single highest-value assertion in your story**, because it is the one a well-meaning future contributor will break while trying to make something work.
- **Choose the stack for auditability, not ambition.** The epic AC suggests a Python HTTP service plus a shell observation script; that is a good default because Python 3 is present on both CI runners and the code stays readable to reviewers who do not write Python. **Whatever you choose, it must already be available on `ubuntu-latest` and `macos-latest` without an install step** — and if it is not, adding one is a change to story 6.1's shared CI file and needs saying at intent-sync. **Do not choose a stack whose runtime must be downloaded**; hermeticity forbids the network (story 6.1 AC1) and the corpus must not become slow to run.
- **Exercise more than one surface.** A fixture with a single http probe would prove that HTTP does not care about Node — which nobody doubted. The claim is about **gates, services and observations**, all three named in the AC. Give it: a **gate** that is not `pnpm test` (a shell command in the fixture's own language), a **service** started by a non-Node command with real readiness, and an **observation** whose before/after invariant is checked by a shell script. **The observation surface is where a Node assumption is most likely to hide**, because it is the one that reads project state.
- **Hermetic, four teeth (story 6.1's rule):** no real providers (`FakeAgentProvider` or checked-in artifacts, **zero `claude`/`codex` invocations**); localhost only, no network, **no `pip install`, no package download of any kind** — use the standard library; no machine-specific state and never `~/.claude/` or `~/.codex/`; and your fixture must not mutate the checked-in tree.
- **⚠️ THE HAND-WRITTEN RULE.** `expected.json` is hand-written and never generated by the code under test (NFR-10, AD-12, ADR-006 §4). When your fixture and your expectation disagree, **decide which is wrong and write down which and why** — and here that decision carries extra weight, because a mismatch in your story is a *candidate stack-neutrality leak*, which is exactly the finding the story exists to produce. Never copy observed output into the file.
- **`.specwitness/` in a non-Node project is itself part of the proof.** `specwitness init` and the config model were built stack-agnostic; your fixture is the first evidence. **If `init` or config validation assumes Node anywhere, say so** — that is FR-4 evidence as much as the run itself.

### Failure modes (what "wrong" looks like here)

- **Adding a `package.json` to make it work.** It converts the story's falsifiable claim into an unfalsifiable one, and it will look like a two-line unblock.
- **Quietly accommodating a leak** in any other way — a Node-shaped file, an npm-resolvable binary, a lockfile — instead of reporting it.
- **A fixture exercising only HTTP**, proving something nobody doubted while leaving the observation surface untested.
- **Choosing a runtime that needs installing**, breaking hermeticity or slowing the corpus.
- **`pip install` or any package download.** Standard library only.
- **A green fixture that adjudicated nothing** — stack neutrality "proven" by an empty run.
- **A non-Node service that outlives the run** because process-group reaping was only ever tested on Node children.
- **Fixing merged resolution logic in a hurry** because a fixture went red.
- **Bending `expected.json` to match observed output.**
- **Reporting CI as "pending owner".** It runs now.

### Security

- **Your fixture adds executable commands in a second language to the repository** (AD-3), running in CI on two platforms on every PR. Keep every command trivially inspectable, local and obviously harmless; **no command reaches the network**, and the fixture app itself must bind only localhost on an ephemeral port.
- **A shell observation script is the highest-privilege thing your story adds.** Keep it short, keep it readable, and let it read state rather than change it.
- **Never mint a `DeclaredCommand`** outside the config boundary (`tests/unit/config/boundary-scan.test.ts` covers you).
- **Never read, copy or persist `~/.claude/`, `~/.codex/` or any credential store** (NFR-1, AD-4, Q59).
- **Assert a secret is ABSENT, never that `[REDACTED]` is present** (Epic 3 retro §7). No fixture file contains a real credential or anything shaped like one.
- **This story makes zero provider calls**, which is worth stating.
- **Your security sign-off may be the last gate before merge** (Stage 4). Sign off from the actual report; **every fixture edit re-stales it**, so plan it for the end.
