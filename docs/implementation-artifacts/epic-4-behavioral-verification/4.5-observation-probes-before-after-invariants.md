## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** an observation probe referencing a config observation id with assertions (equals/delta comparisons)
   **When** it executes standalone or as before/after wrapping another probe's action
   **Then** JSON stdout is parsed, asserted (e.g. `after.count - before.count == 1`), and both snapshots stored as evidence.
2. **Given** an observation command emitting invalid JSON or exiting non-zero
   **When** the probe runs
   **Then** the criterion classifies `error` with the raw output as evidence (never a silent pass/fail).
3. **Given** the duplicate-submission scenario fixture
   **When** verified
   **Then** the criterion fails with evidence showing requests=2 and rows-created=2 (brief §35 example realized).

Clarifications (detail only, no weakening):

- **⚠️ You never produce a `CriterionStatus`.** AD-13, and the merged code enforces it: a `SurfaceExecutor` **returns a `ProbeAttempt` and never a `CriterionStatus`** — *"there is nowhere in this interface to put one"*. The single producer is `deriveCriterionResult` in `src/domain/criterion-result.ts`. **You observe and evaluate assertions; something else decides what it means.** Read that module's header first: four surfaces each adjudicating status their own way would give four different answers to "did a retry that eventually passed count as flaky", surfacing only as a verdict nobody could reproduce.
- **AC2 IS THE CLASSIFICATION TEST AND IT IS THE ONE THAT MATTERS MOST HERE.** Q35 is explicit: **observation commands MUST emit JSON; non-JSON output ⇒ criterion `error`.** So:
  - **Invalid JSON ⇒ `execError`** ⇒ criterion `error`. You could not observe. The project's observation command broke its contract, which says nothing about whether the branch satisfies its criteria.
  - **Non-zero exit ⇒ `execError`** ⇒ criterion `error`. Same reasoning.
  - **"never a silent pass/fail"** is the AC's own emphasis and it is the trap: a `try { JSON.parse } catch { return notSatisfied }` would report a **product FAIL** for a broken observation command — infrastructure blamed on the branch. Equally, defaulting a missing count to `0` and finding `0 - 0 == 0` would report a **PASS** for a command that produced nothing. Both are green-or-red for nothing. `execError` is the only honest answer.
  - **Set `execError` and nothing else on that path.** Do not also emit unsatisfied assertions — you did not observe anything to compare. `outcomeOf` makes `execError` outrank assertions anyway, and its comment says why: *"those assertions ran against a broken observation, so reporting `fail` from them would manufacture product evidence out of an infrastructure failure."*

- **Note the deliberate asymmetry with 4.4, and say so in your module header.** For an *HTTP* probe, a non-JSON body with a JSON-path assertion is a product observation (the server answered; the answer was wrong). For an *observation command*, non-JSON is criterion `error` — because JSON is a **contract the project owner declared** when they wrote the observation into config, not an expectation the plan asserted. Same-looking inputs, different classifications, both correct. Write it down so a future reader sees a decision rather than an inconsistency.

- **AC1's before/after is the story's distinctive shape and it needs a stated model.** Two snapshots of the same observation with an action between them, asserting a **delta** (`after.count - before.count == 1`) or an **equality**. Decide and document:

That is the product being wrong — **criterion `fail`** — with evidence showing `requests=2` and `rows-created=2`. **Build it as a fixture**: an observation command that reports a count, an action that increments it twice, an assertion of `after - before == 1`, and an assertion that the result is `fail` with expected `1` and actual `2` in the evaluation. ## Dev Notes

### Goal & Context

**This is the surface that answers the questions a test suite cannot.** An HTTP probe asks "did the endpoint answer correctly?" An observation probe asks "and what did that do to the world?" — and the gap between those two is where the defects SpecWitness exists to find actually live. The brief's §35 example is exactly it: a duplicate submission returns 200 twice, so every response-level check is green, and two rows exist where one should. That defect passes coding-agent tests, passes review, and reaches production.

The design constraint is **stack neutrality** (FR-4, Q34): SpecWitness names no database, no ORM, no query language. The project owner declares an observation command in their config; it emits JSON to stdout; SpecWitness asserts over the JSON. That is the entire abstraction, and it is why Q35 makes JSON **mandatory** rather than best-effort — a "flexible" parser that guessed at non-JSON output would turn a broken observation command into a confident answer about the product.

That is your story's spine: **AC2 is not an edge case, it is the design.**

### Architecture compliance

- **AD-13.** One executor interface, one `ProbeAttempt`, **never** a `CriterionStatus`.
- **AD-3.** Observation commands are `DeclaredCommand`s referenced **by config id**; they reach `ProcessRunner` as binary + argv with no shell. Nothing a plan authored becomes an executable command.
- **AD-1.** `src/surfaces/**` is an adapter: `src/domain/**`, `src/schemas/**`, siblings and npm only — **not `src/config/**`**, not application layers, not `cli`.
- **AD-6/AD-7.** Criterion `error` is the "could not observe" channel ⇒ run-level `{infraError}` ⇒ exit 3. An unsatisfied assertion is product `fail` ⇒ exit 1. Never interchangeable.
- **AD-9.** Retries opt-in, default 0, every attempt recorded, orchestration outside your executor; `Clock` injected.
- **AD-10.** Redaction at capture, through the constructors, fail-closed.
- **AD-12.** Hermetic: fixture commands built by the test, no network beyond localhost, no real providers.
- **Conventions.** ISO-8601 UTC; integer ms; bounded output with a pointer to the full file.

### Failure modes (what "wrong" looks like here)

- **Non-JSON output reported as `fail`.** The headline defect: a broken observation command blamed on the branch. Q35 exists to prevent exactly this.
- **A missing count defaulted to `0`**, so `0 - 0 == 0` passes and a command that produced nothing reports green.
- **Returning or inferring a `CriterionStatus`.** Four surfaces, four answers, one irreproducible verdict.
- **Emitting unsatisfied assertions alongside an `execError`** — manufacturing product evidence out of an infrastructure failure.
- **Asserting a delta over a failed "before" snapshot.**
- **Parsing stderr, or stdout+stderr concatenated.** A command that logs to stderr then prints JSON stops working, and the failure looks like the project's fault.
- **A secret in the full evidence copy while the inline copy is clean** — the exact hole `redactText`'s separate existence closes, and a naive seeded-secret test passes green over it.
- **Treating command *output* as a declared shell string** (`{shellCommand: true}`) — the fail-open direction. The command text is declared; its output never is.
- **Retrying inside the executor.** `flaky` becomes wrong and the attempts are invisible.
- **Diverging from 4.4's executor shape**, which fails 4.7's conformance test in cohort 3 with nobody left to reconcile it.
