## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** services in config (command, readiness URL/command, timeout, env, port)
   **When** the services stage runs
   **Then** each service starts in the worktree with its declared env, readiness is polled until healthy or timeout, and startup order follows declaration order.
2. **Given** a service that never becomes ready
   **When** the timeout elapses
   **Then** the run ends InfraError (exit 3, never FAIL), with the service's captured output as evidence.
3. **Given** run end (including SIGKILL of SpecWitness)
   **When** cleanup/`clean` completes
   **Then** no service process survives (extends 3.2's manifest coverage to services; integration-tested).

Clarifications (detail only, no weakening):

- **AC1 "startup order follows declaration order" has a merged obstacle you must solve, not ignore.** `config.services` is `z.record(nonEmptyString, serviceSchema)` — a **map, not an array** (`src/config/schema.ts`). `gates` is `z.array(...)` and therefore ordered by construction; services are not. In practice `yaml` + zod preserve JS object insertion order for string keys, so `Object.keys(config.services)` *does* yield declaration order — **but that is an emergent property of two libraries, not a guarantee the schema makes.** Decide explicitly and write the decision in your module header: either (a) rely on insertion order and pin it with a test that loads a real multi-service YAML fixture and asserts the observed start order matches the file order, or (b) propose an ordered representation. **(a) is the recommendation** — it needs no schema change, which is 1.3's file and not yours — but a bare `Object.keys` with no test is not acceptable, because the day it silently reorders, services start in the wrong order and the failure looks like a flaky app.
- **AC1 "in the worktree" means the same cwd the gates stage uses**, `context.run.environment.worktreePath`. It is `string | null`. When it is `null` and services are declared, **throw an `InfraError`** — do exactly what `createGatesStage` does at the same point (`src/pipeline/stages/gates.ts`, the `cwd === null` branch) and for the same reason: falling back to the project root would start the operator's services against the wrong tree and could write into their working directory (AD-8, FR-19).
- **AC1 "with its declared env".** `ServiceConfig.env` is `Record<string, string> | undefined`. Q16 says services get "config-declared `env` merged over a pass-through base", so construct `{inherit: true, set: service.env}` and pass it whole. The merged `ChildEnvironment` resolution order is documented in `src/domain/process-runner.ts`: base from `inherit`, then `withhold`, then `set`. **`withhold` is for provider invocations (AD-4/FR-15), not for a project starting its own services** — do not withhold anything here.
- **AC1 readiness is TWO probe kinds and the schema already guarantees exactly one.** `readinessSchema.superRefine` rejects both-or-neither, so at run time exactly one of `url` / `command` is present and you must **not** re-validate that. Implement both:
  - **`url`**: poll with an HTTP GET; **ready when the response status is 2xx** (Q28: "URL probe (2xx)"). A connection refusal, a DNS failure or any non-2xx status is *not ready yet* — keep polling until the deadline. Do not treat a 500 as an error that ends the run; a service that is still booting legitimately answers 500 for a while.
  - **`command`**: spawn the `DeclaredCommand` through `ProcessRunner`; **ready when it exits 0.** Any non-zero exit is *not ready yet*. A `not-found` outcome is different — the probe command's binary is missing, which is an environment defect, not a service that is slow; classify it as an `InfraError` naming the binary rather than burning the full timeout.
  - **Poll interval:** a module constant with a stated value (recommend 250 ms), injectable through your deps so a test asserts the timeout path in milliseconds rather than waiting out `timeoutSec: 60`. Same pattern as `GATE_TIMEOUT_MS` in the gates stage — read how it did it.
  - **`timeoutSec`** is per-service and already defaulted to 60 by the schema. Convert to ms once; do not re-default.
- **AC2 is the single most important test in this story, and it is a CLASSIFICATION test.** A service that never becomes ready is an **`InfraError` (exit 3)**, never a FAIL. Reporting it as FAIL would tell a harness the branch has defects when SpecWitness merely failed to bring the environment up — the exact confusion this project treats as first-order (AD-6/AD-7, and the gates stage's header states the same rule for its own case). Your test must **produce the state**, not mock it: start a fixture command that runs but never answers its readiness probe (a `node -e` process that sleeps), with `timeoutSec` driven down through your injected interval, and assert the thrown error class and that **no `GateResult` and no criterion claims failure**.
- **AC2 "with the service's captured output as evidence" (Q29).** This is the hard part, and it is a design constraint on how you spawn. `ProcessRunner.run()` resolves only when the child **exits** — a service that starts successfully never exits, so awaiting `run()` for a service would hang until the timeout on the happy path. **You therefore cannot use `run()` the way the gates stage does.** Decide and document your approach; two are viable:
  1. Spawn without awaiting the settled result: hold the promise, let readiness polling drive the timeline, and read captured output from the settled promise only on the failure path (where the process has exited or is killed).
  2. Extend the runner seam. **If you conclude the merged port cannot express a long-lived child**, that is a real finding: `src/domain/process-runner.ts` says explicitly "EXACTLY ONE METHOD, still" and that adding a required method breaks every `ProcessRunner` fake in `tests/`. Any addition must be an **optional** method or a free function, and it must be argued in your PR body. Do not silently widen the port.
  Whichever you choose, the captured output on the timeout path must be real bytes the service printed, because that is the whole diagnostic value of AC2 — an operator reading "backend never became ready" with no stack trace from the service has been told nothing.
- **Evidence for AC2 goes through the merged constructors, never hand-built.** Use `commandEvidence` from `src/domain/evidence.ts` with the service id as `commandId` and `commandText(service.run)` as `displayCommand`. **Do NOT invent a new evidence kind** — `EVIDENCE_KINDS` is a closed union and `command` is exactly right for "a declared command was run and produced output". Widening the union is an ADR, not a branch.
- **REDACTION IS FAIL-CLOSED AND THIS IS A SECURITY CLAUSE, not a style note.** `redactText(raw, options)` accepts `{shellCommand: true}`. That option is **reserved for declared commands only** — text the project owner wrote. **Service stdout/stderr is capture output and MUST be passed undeclared** (i.e. without `shellCommand`), which is the fail-closed default. Epic 3's retro §6 states this for all Epic 4 callers, and §2 observation 7 records the six leak shapes that produced the rule: shell context is *declared by the caller*, never inferred from text, because an apostrophe in prose is indistinguishable from a shell delimiter. `commandEvidence`'s constructor already redacts what you hand it; where you build an error *message* containing captured output, call `redactText` yourself first — the gates stage does exactly this in its `spawn-failed` arm and its header explains why (an error reaches `printError`, which writes to stderr verbatim, so the persisted copy would be clean while the terminal showed the secret).
- **AC3's "no service process survives" is mostly already built — consume it, do not rebuild it.** Story 3.2 shipped process groups: every child `ProcessRunner` spawns is detached and is therefore its own group leader, `ProcessResult.pgid` reports it, `ProcessRunOptions.onProcessGroup` is awaited *before the run proceeds* so the pgid is fsynced into the manifest, and `terminateProcessGroup(pgid, {graceMs})` is **exported from `src/infra/process-runner.ts`** implementing SIGTERM → poll → SIGKILL → reap-verify. `specwitness clean` replays manifests. **Your job is to wire services into that machinery**: pass `onProcessGroup` on every service spawn so the pgid is durable before you wait for readiness, and bind teardown so every service group is terminated.
- **Teardown is the pipeline's guarantee, and you plug into the existing seam.** `createTeardownStage({release})` takes an injected `release(context)` callback, and `run-pipeline.ts` calls teardown after any early stop, after any thrown error, and after an error thrown by teardown itself. **Do not add a second teardown path.** Register your service groups so the composed `release` kills them. Because the release callback is bound at the CLI edge and 4.7 owns that wiring, publish in your PR body exactly what 4.7 must bind.
- **Teardown must terminate services even when readiness FAILED.** The AC2 path throws — and a service that started but never answered is precisely the process most likely to be left running. Test it: after the readiness-timeout `InfraError`, assert the spawned pgid is gone.
- **Q27: an occupied declared port is an `InfraError` naming the port — never a FAIL.** `ServiceConfig.port` is optional and V0 does **not** auto-allocate (Q26). There is a merged doctor check at `src/cli/doctor/checks/ports-free.ts` and a `tests/fakes/ports.ts` fake — **read them and reuse the port-probing seam rather than writing a second one.** Doctor pre-checks; the services stage pre-checks too ("doctor **and** the services stage pre-check declared ports are free" — spine Conventions, Ports row). Your test must produce the state: bind a real listener on a port, declare a service on it, assert `InfraError` naming that port and that nothing was spawned. A service whose config declares no `port` simply skips this check.
- **No production URL defaults, and localhost unless config says otherwise (AD-3).** You never synthesise a URL. The readiness URL comes from config verbatim. If you expose a base-URL resolution for 4.4, derive it from declared config values only.

## Dev Notes

### Goal & Context

**This is the first story in the product that runs the target project's application.** Everything before it ran the project's *build* — gates are `pnpm lint`, `pnpm build`, commands that start, do a thing and exit. You start a server and leave it running while other code talks to it. Epic 3's process-group discipline exists precisely for this moment, and you are its first real consumer.

That changes the failure modes. A gate that hangs is a gate that hangs; a *service* that hangs is the normal case, and the abnormal case is a service that exits. Every piece of machinery you touch — the runner's settle-on-exit contract, the readiness deadline, teardown — is about telling those two apart.

The classification rule is the story's spine: **a service that would not start says nothing about whether the branch satisfies its contract.** Exit 3 means "SpecWitness could not reach a conclusion". Exit 1 means "your code is broken". A readiness timeout reported as FAIL blocks a mergeable branch or sends a developer hunting a defect that does not exist.

### Architecture compliance

- **AD-1 (layering).** `src/pipeline/**` may import `domain`, `schemas`, siblings, `config`, `infra`, `providers`, `surfaces`. It may **not** import `cli`, `authoring`, `ingest`, `report`. Your stage constructs **no adapter** — every port arrives by injection, which is what keeps the pipeline unit-testable with zero I/O.
- **AD-3 (trusted commands).** Service commands and readiness commands are `DeclaredCommand`s from Project Config and nothing else. They reach `ProcessRunner` as **binary + argument array**; there is no shell, so `&&`, `$(…)` and `;` arrive as literal argv elements.
- **AD-6/AD-7 (classification).** A readiness failure, an occupied port and a missing readiness binary are all **thrown `InfraError`s** (exit 3). Your stage never returns `stageProductNegative` and never writes `context.run.outcome` — the aggregate stage is AD-6's only converter.

### Failure modes (what "wrong" looks like here)

- **A readiness timeout reported as FAIL.** The headline defect. Exit 1 tells a harness the branch has defects; the branch may be perfect.
- **A service left running after the run.** Silent, cumulative, and it makes the *next* run fail on an occupied port — so the symptom appears one run away from its cause. Epic 2 leaked nine `sleep 3600` processes this way.
- **Awaiting `run()` for a long-lived service**, which hangs the happy path until the timeout and then reports a "readiness failure" for a service that was healthy the whole time.
- **A single-shot readiness check** that passes on a fast machine and fails on a loaded one. Poll, with a deadline.
- **Insertion-order reliance with no test.** Works until it does not, and then services start in the wrong order and the app looks flaky.
- **Capture output redacted as a declared command** (`{shellCommand: true}`), which is the fail-open direction. The rule is fail-closed by default.
- **A green run in which nothing started.** If services are declared and none started, the run must not read as healthy.
