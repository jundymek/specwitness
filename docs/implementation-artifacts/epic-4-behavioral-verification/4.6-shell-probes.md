## Dev Notes

### Goal & Context

Shell probes exist because some criteria are not observable over HTTP or through a state query — a migration was applied, a generated file has the right shape, a binary reports the expected version. FR-26 calls them *"structural criteria and stack-specific checks"*, and the story's subtitle is the whole design: **"without opening arbitrary execution."**

That phrase is why your story is the security-sensitive one in cohort 2. Every other surface either touches no shell (HTTP) or runs a command the project owner declared in full (observation). Yours runs a declared command **with arguments a provider chose**. The allowlist is what keeps that from being a hole, and the no-shell spawn is what keeps a hole from being catastrophic even if the allowlist were wrong.

Two layers of defence, stated plainly:

1. **The plan cannot name a command.** It names a config id. The command text comes from the project owner's file, and `DeclaredCommand` can only be minted inside `src/config/` — *"there is no code path — none — by which a raw string, or output from a `claude`/`codex` subprocess, becomes an executable command."*
2. **The plan's arguments are checked against an allowlist, at compile time and again at run time**, and the process is spawned as binary + argv with no shell, so even an argument that slipped through is inert as a metacharacter.

You are building the second half of both.

### Architecture compliance

- **AD-3 — your invariant.** Only Project-Config-declared commands reach execution; plans reference them **by config id plus an argument allowlist**, never by command string; a draft containing an inline command string fails schema validation; no shell, ever.
- **AD-13.** One executor interface, one `ProbeAttempt`, **never** a `CriterionStatus`.

### Failure modes (what "wrong" looks like here)
