## Story

As a reproducibility guarantee,
I want scenario inputs fixed at compile time, stored in the plan, and surfaced in evidence,
So that identical plans produce identical probe inputs run after run (FR-17, AD-9, NFR-5).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** a compiled plan
   **When** two verify runs execute against the same revision
   **Then** probe inputs are byte-identical except fields the plan explicitly declares `volatile` (uniqueness-requiring values derive from a recorded per-plan seed).
2. **Given** any executed probe
   **When** evidence is stored
   **Then** the exact inputs used appear in the criterion's evidence (brief §48).
3. **Given** data setup/reset commands in config
   **When** the data stage runs before probes
   **Then** they execute in declared order and their failure classifies as InfraError.

Clarifications (detail only, no weakening):

- **AC1 is the story's whole point and it is a NEGATIVE requirement: nothing generates fresh data per run.** AD-9 states it plainly — deterministic test data is **resolved at plan compile time and stored in the Plan**. Your stage does not invent values; it *reads* values 4.2's schema already stored and makes them available to probes. The failure this prevents is "LLM-fresh test data per run", which would make two runs of the same plan against the same revision incomparable — and comparability is the entire premise of a verification gate.
- **AC1's "recorded per-plan seed" is the escape valve for values that genuinely cannot repeat**, and it must stay deterministic. Q36: *fixed values + a recorded seed, stored in the Plan at compile time*. A field needing uniqueness (an email that must not collide with a previous run's row) derives from the seed **by a pure, documented function** — same seed plus same field ⇒ same value, every run, on every machine. **`Math.random()` and `crypto.randomUUID()` are both wrong here**, and so is anything reading the clock: `Clock` is an injected port precisely so nothing on this path reads wall time (AD-9). Pick a small deterministic derivation you can state in one sentence and test with a fixed seed.
- **The seed is stored in the plan, not generated at run time.** If a plan carries no seed, that is 4.2's schema's business, not a value for you to mint. Read what 4.2 merged and follow it; if the field is optional and absent, decide and document what a plan without a seed means (recommendation: fields requiring uniqueness are simply not expressible in such a plan, i.e. it is a compile-time property, not a run-time fallback).
- **`volatile` fields are DECLARED and EXCLUDED from reproducibility comparison — they are not "allowed to be random".** AD-9's wording: *fields that legitimately vary per run are declared `volatile` in the plan and excluded from reproducibility comparison*. So the reproducibility guarantee reads: *for two runs of the same plan against the same revision, every probe input is byte-identical except those whose plan declaration marks them volatile.* Your AC1 test must be exactly that assertion — **not** "the two runs are identical", which would be false, and **not** "the two runs are mostly identical", which asserts nothing.
- **AC1's test must run the resolution TWICE and diff.** Assert byte-equality over the resolved input set with volatile fields excluded by their declaration, and assert that a volatile field's exclusion is driven by the *plan's declaration* rather than by a hardcoded field name. The tempting shortcut — assert once and eyeball — proves nothing about reproducibility.
- **AC2 "the exact inputs used appear in the criterion's evidence" is a cross-story obligation, and yours is the producing half.** The evidence union is **closed** (`EVIDENCE_KINDS` in `src/domain/evidence.ts`) and you may not widen it — that is an ADR. So resolved inputs travel to evidence through the surfaces: an `http` probe's evidence already carries its request (`HttpRequestRecord {method, url, headers}`), an `observation`'s carries its snapshot, a `command`'s carries its `displayCommand` and output. **Your job is to make the resolved inputs reach the executors in a form they can record, and to say in your PR body exactly how.** Coordinate the shape at intent-sync — this is the one place your work and the three surface stories genuinely interlock.
  - **Read `src/domain/criterion-result.ts` before designing anything here.** `ProbeRequest {criterionId, surface, params}` says `params` are "surface-specific parameters, **resolved at plan compile time** (AD-9)". That sentence is your seam: resolution happens before an executor sees a request, and `params` is what it sees.
- **AC3 is a CLASSIFICATION requirement and the third of three "infra, never FAIL" tests in this epic.** `config.data` is `z.record(nonEmptyString, declaredCommand())` — a map of named `DeclaredCommand`s, with `reset` the conventional key (`src/config/schema.ts`). A data command that fails is **`InfraError` (exit 3)**, never a product FAIL: SpecWitness could not establish the preconditions for verification, which says nothing about whether the branch satisfies its contract. Reporting it as FAIL would block a mergeable branch. The gates stage's header states the identical rule for its own case and is the precedent to imitate.
- **AC3 "in declared order" has the same merged obstacle 4.1 hit with services.** `config.data` is a **record, not an array** — `gates` is `z.array(...)` and ordered by construction; `data` is not. In practice `yaml` + zod preserve insertion order for string keys, so `Object.keys(config.data)` yields declaration order, **but that is an emergent property of two libraries, not a schema guarantee.** Decide explicitly, write the decision in your module header, and pin it with a test that loads a real multi-command YAML fixture through `loadConfig` and asserts the observed execution order matches the file order. **Do not change `src/config/schema.ts`** — it is story 1.3's file and no Epic 4 story owns it. (4.1 faced the identical question for services in cohort 1; **read what it merged and match its answer** rather than inventing a second convention for the same problem.)
- **AC3 "before probes" is already true structurally and you must not re-order anything.** The eleven stage names are frozen in `src/domain/stage.ts`: `… gates → services → data → probes → aggregate …`. `data` is position 7, `probes` position 8. `runPipeline` refuses a stage list that is not those eleven names in order. Renaming, reordering, adding or dropping one is **an ADR, not an edit**.
- **Data commands run in the worktree**, at `context.run.environment.worktreePath`, exactly like gates and services. When it is `null` and data commands are declared, **throw `InfraError`** — mirror `createGatesStage`'s `cwd === null` branch and its reasoning: falling back to the project root would run the operator's reset command against the wrong tree and could write into their working directory (AD-8, FR-19). **This is a destructive-command path** — a `data.reset` command plausibly drops tables — so getting the cwd wrong here is worse than getting it wrong anywhere else in the epic.
- **Evidence for data commands** goes through `commandEvidence` from `src/domain/evidence.ts`, with the data key as `commandId` and `commandText(command)` as `displayCommand`. Do not hand-build evidence and do not widen the union.
- **REDACTION IS FAIL-CLOSED — a security clause, not a style note.** `redactText`'s `{shellCommand: true}` option is **reserved for declared commands only**. Data command *output* is capture text and must be passed **undeclared** (the fail-closed default). Epic 3 retro §6 states this for all Epic 4 callers; §2 observation 7 records the six leak shapes behind the rule: shell context is *declared by the caller*, never inferred from text. Where you put captured output into an error *message*, call `redactText` yourself first — the gates stage does exactly that in its `spawn-failed` arm, and its comment explains why (an error reaches `printError`, which writes to stderr verbatim, so the persisted copy would be clean while the terminal showed the secret).

## Dev Notes

### Goal & Context

Reproducibility is what separates a verification gate from a test suite that happens to run. A suite that passes today and fails tomorrow with no code change teaches an operator to ignore it; a gate that does that is worse than no gate, because it was supposed to be the thing you could trust. AD-9 exists to make the failure mode unrepresentable, and its mechanism is blunt: **the values are decided once, at compile time, and written down.** Nothing at run time invents anything.

Your story is small in code and large in consequence. Most of it is a pure function and a stage that runs a few declared commands. The consequential parts are the two negatives: **no fresh data per run**, and **a data failure is infrastructure, not FAIL**.

The second one is worth dwelling on. A `data.reset` command that fails has told you nothing about the branch — the app may be perfect. Exit 1 would say "this branch has defects" on no evidence at all, and route repair automation at code that is fine. Exit 3 says "SpecWitness could not reach a conclusion", which is exactly what happened.

### Architecture compliance

- **AD-9 (determinism & flakiness) — your invariant.** Data resolved at compile time and stored in the plan; `Clock` and `Ids` injectable; `volatile` fields declared and excluded from reproducibility comparison.
- **AD-1 (layering).** A pure resolver in `src/domain/` imports nothing side-effectful — and with `tsPreCompilationDeps: true`, not even a type-only zod import. The stage lives in `src/pipeline/**` and constructs **no adapter**.
- **AD-3 (trusted commands).** Data commands are `DeclaredCommand`s from Project Config and nothing else, reaching `ProcessRunner` as binary + argv with no shell.
- **AD-6/AD-7 (classification).** Every data failure is a thrown `InfraError` (exit 3). Your stage never returns `stageProductNegative` and never writes `context.run.outcome`.
- **AD-8 (isolation).** Worktree cwd; pgids recorded before the run proceeds; `RunStore` the sole writer under `.specwitness/runs/`; nothing written into the project working tree.
- **AD-10 (evidence).** Redaction at capture, through the constructors, fail-closed.
- **Conventions.** ISO-8601 UTC; integer ms durations; `ERROR:` + `HINT:` pairs; prompt-free.

### Failure modes (what "wrong" looks like here)

- **Generating a value at run time** because it "needs to be unique". That is the exact defect AD-9 exists to prevent, and it will look reasonable in review.
- **A data failure reported as FAIL.** Blocks a mergeable branch, or sends someone hunting a defect that does not exist.
- **Running a `reset` command against the wrong tree.** The `cwd === null` fallback that seems harmless in gates is destructive here.
- **Reproducibility asserted once.** A test that resolves a single time proves nothing about run-to-run stability.
- **Volatile exclusion hardcoded by field name** rather than driven by the plan's declaration — works for the fixture, fails for every real plan.
- **A wider Plan schema in your branch.** Three peers built against what 4.2 merged; your widening does not reach them and will surface as a merge conflict in cohort 3.
- **Capture output redacted as a declared command** (`{shellCommand: true}`) — the fail-open direction.
