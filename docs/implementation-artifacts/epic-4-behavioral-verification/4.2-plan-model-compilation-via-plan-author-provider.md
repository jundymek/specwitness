From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** a frozen contract and the plan-author role

2. **Given** a provider draft containing an inline shell command string or an assertion-free probe

Clarifications (detail only, no weakening):

- **AC1 "by criterion id only" is AD-5 and it is structural, not stylistic.** A Plan references `E7-01`. It **never** embeds the criterion's statement text. Two reasons, both load-bearing: the statement is fingerprinted contract content, so copying it creates a second copy that can drift from the authority; and a renderer that reads statements from the plan would report what the *plan* thinks the criterion says rather than what the contract says. `deriveCriterionResult` already gets `statement` from `ContractCriterionRef`, recorded by the integrity stage from the verified contract. **Your schema must make embedding a statement impossible** — a strict object with no such field.
- **AC1 "referencing the contract version + fingerprint".** Store both. The fingerprint is what AC3 compares; the version is what a human reads. `contract.meta.schemaVersion`, the contract's integer `version` and its fingerprint all already exist — read `src/domain/contract.ts` and `src/schemas/contract.ts` for the exact shapes and reuse them. Do **not** re-implement fingerprinting: `src/schemas/canonical.ts` is the single hasher and `.dependency-cruiser.cjs` has a rule named `schemas-canonical-is-the-only-hasher` that will fail your build if you try.
- **AC1 "human criteria carried as needs-human with reviewer guidance", plus Q38's second trigger.** There are exactly **two** ways a criterion becomes `needs_human` (Q39), and you own the compile-time half of both:
  1. `verifiability: human` in the contract — carried into the plan as needs-human with the reviewer guidance the provider drafted.
  2. **The plan-author could not map the criterion to a safe probe** ⇒ compiled `needs_human` with reason **`not-safely-automatable`** (Q38, AD-5). **Never silently dropped, never guessed into a probe.** A criterion missing from a plan entirely is the failure mode this rule exists to prevent — it would simply disappear from verification.
  Your schema must be able to express both, and they are distinguishable: one is a fact about the contract, the other a fact about compilation.
- **⚠️ HUMAN CRITERIA ARE UNCONDITIONALLY NEEDS_HUMAN, AND A PROBE MAY NOT ADJUDICATE ONE.** `src/domain/contract.ts` states this unconditionally and `deriveCriterionResult` enforces it **before it even looks at attempts**. Epic 3 caught and reverted a well-meaning "floor" variant that applied it only when there were no attempts, reasoning that a future human-input surface might report a recorded judgement — review called it a silent redesign of a recorded decision. **Your compilation must never emit a probe for a `verifiability: human` criterion.** Pin it with a test: a contract containing a human criterion compiles to a needs-human entry with zero probes, and a *provider draft that tries to attach a probe to a human criterion is rejected*. If you believe a probe should ever adjudicate a human criterion, that is **an ADR in `docs/adr/`, not a branch** (Epic 3 retro §6).
- **AC2 IS THE SECURITY PROPERTY OF THIS EPIC AND IT IS YOURS.** It is also a roadmap exit criterion, worded slightly wider there than in the epic file — the roadmap says *"Malicious fake plan-author (inline shell string / **mutated assertion**) rejected at schema gate"*. Cover both:
  - **Inline shell string.** A shell probe references a config id (`command: seed-check`) plus an argument allowlist. There is **no field anywhere in your schema that accepts a command string.** Make the rejection structural: with a `z.strictObject`, a draft carrying `run: "rm -rf /"` fails as an unknown key. Then *also* test it, because the property you need proven is "this specific attack fails", not "strict objects reject unknown keys".
  - **Mutated assertion / assertion-free probe.** A probe with zero assertions must fail validation — `z.array(assertionSchema).min(1)`. An assertion-free probe is the quiet version of the attack: it executes, observes nothing, and `outcomeOf` in `criterion-result.ts` would reach its "nothing was adjudicated mechanically" branch. That branch returns `needs_human` rather than `pass` **precisely so this cannot mint a PASS out of nothing** — its comment says the compiled plan always gives a probe at least one assertion, "so in practice this is unreachable; it is here so that the unreachable case is safe rather than merely lucky". **You are the story that makes that sentence true.**
  - **Test with a malicious fake provider**, as the AC says. `src/providers/fake.ts` is a **shipped, config-selectable adapter** whose fixtures are JSON arrays of raw response strings under `<mode>/<role>.json`, deliberately allowed to be invalid. Write `tests/fixtures/providers/malicious-plan/plan-author.json` and drive the real gate.
- **AC2 "rejected (retry per FR-14)" — you call the ONE gate, you do not re-implement it.** `src/providers/invoke.ts` is AD-2's single schema gate and retry loop, named by path in the spine. It parses, validates, feeds errors back into the next prompt, counts attempts, classifies failures and derives a JSON Schema for CLIs that can constrain output. **You call `invoke()` or `attemptInvoke()` with your zod schema as `responseSchema` and do nothing else.** No validation in your module, no retry loop, no attempt counting. `maxRetries` counts retries *after* the first call (default 2 ⇒ at most 3 attempts). A budget exhausted throws `ProviderError` — exit 3, never a product FAIL: a provider that cannot draft a valid plan has not proved the epic wrong.
- **A plan draft is a DRAFT (AD-2).** It may not weaken an expectation. And record this in your module header for Epic 5's benefit: *runtime mechanics adaptation may alter probe **mechanics** fields only (locators, navigation) — assertion and expected-value fields are **structurally read-only** in that flow.* Design your shape so that separation is visible: mechanics and assertions in distinct sub-objects, so a future adaptation flow can be written to touch one and not the other.
- **AC3 is a REFUSAL AT VERIFY TIME, and you own the check while 4.7 owns the wiring.** Compare the plan's stored fingerprint against the loaded contract's. Mismatch ⇒ **`IntegrityError`** (the merged class in `src/domain/errors.ts`; exit 3) with `HINT: re-run specwitness plan`. **Read `src/authoring/verifiable.ts` and `src/schemas/contract.ts` first** — the contract already has a three-state refusal (absent / never frozen / tampered) with hard-won wording. ADR-005 exists because telling an operator their contract "no longer matches" invites `--freeze`, which launders the tamper and destroys the evidence. Your stale-plan hint must not fall into the same trap: the remedy for a stale *plan* genuinely is to recompile, and saying so precisely is the point. Export the check as a pure, testable function; 4.7 calls it from the edge.
- **AC4 "lowest adequate surface" is a PROMPT-AND-SPOT-CHECK rule, not an algorithm.** You cannot mechanically decide from a criterion statement whether HTTP suffices — that judgement is exactly what the plan-author provider is for (Q37). Your obligations are: (a) the prompt states the rule explicitly (brief §32: an HTTP-checkable criterion yields an HTTP probe, not a browser probe); (b) a fixture spot-check proves the compiled output for an obviously-HTTP criterion is `http`. **Do not build a classifier.** And note: `browser` is in the closed union so the schema accepts it, but **Epic 5 implements the browser executor** — a plan may name it; nothing executes it this epic.
- **`schemaVersion` and the registry.** `src/schemas/versions.ts` **already reserves your key by comment** ("Epic 2 adds `contract` and `plan`"). Add `plan: 1` to `SCHEMA_VERSIONS` — a genuine one-line diff, because `as const` widens `SchemaVersionKey` automatically. Read that file's header: versions evolve additively, never renumbered, never removed. It deliberately holds **no** assert/validate helper, because what a mismatch *means* is artifact-specific; your policy lives in your own schema module, like the contract's does.
- **Artifact format and location (AD-5).** Plans are **human-readable YAML** at `.specwitness/plans/<epic>.yaml`, committed to the target project's Git (Q11 — config, contracts and plans are reviewable product artifacts; only `runs/` and `scorecard.jsonl` are local-only). Story 3.8 wired provenance for contracts; **read `src/cli/contract/provenance.ts` and reuse rather than inventing a parallel shape.** Where a value is genuinely unknown, record `null` — `ProviderUsage` in `src/domain/run-result.ts` documents exactly this and explains why: *"a guessed model string in an audit field is worse than an honest null."*

## Dev Notes

### Goal & Context

**This is the first epic in which AI output becomes an executable artifact**, and you are the story where that happens. Until now a provider drafted a *contract* — text a human reads, reviews and freezes, with a person in the loop before it has any authority. From here a provider drafts a **plan**, and that plan drives probes that spawn processes and issue requests.

AD-2 and AD-3 stop being invariants about authoring and become invariants about execution. That is why AC2 is worded as a *schema-level* enforcement and why the roadmap lists it as an exit criterion. The defence is not that the provider is trustworthy; it is that **there is nowhere in the schema to put a command string**, so a hostile or merely sloppy draft cannot express the attack. `DeclaredCommand`'s module header states the same property from the other end: *"nothing a provider CLI authored can become an executable command. Provider-drafted plans reference executables by config id, never by command string."* You are the half of that sentence that has not been built yet.

The second reason this story is specified so tightly is the cohort structure. Everything you decide becomes law for four agents who cannot ask you anything.

### Failure modes (what "wrong" looks like here)

- **A field anywhere that accepts a command string.** The whole epic's security property, gone, and it would look like a convenience.
- **An assertion-free probe accepted.** It executes, observes nothing, and reaches the branch in `outcomeOf` that exists only because your schema is supposed to make it unreachable.
- **A criterion silently missing from a compiled plan.** It disappears from verification and nothing reports its absence. Q38 exists to prevent exactly this.
- **A probe attached to a human criterion.** Reverted once already in Epic 3; requires an ADR, not a branch.
- **Re-implementing validation or retry in your module.** Two gates disagree exactly once, in production.
- **Re-implementing the fingerprint.** A depcruise rule will stop you, but the deeper problem is two hashers.
- **Embedding criterion statements in the plan.** A second copy of fingerprinted content that can drift from its authority.
- **A stale-plan hint that invites recompiling over a real problem**, the ADR-005 mistake one artifact over.
- **A loose schema shipped fast.** Tempting, because you are the critical path. But four stories build on it and cannot change it, so a loose schema is worse than a late one. Tight and early is the target; tight beats early if you must choose.
