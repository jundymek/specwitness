# Story 3.8: Provider provenance wiring (`meta.provenance.model` / `providerCliVersion`)

Status: ready-for-dev

## Provenance (owner-decided story — read this first)

This story does not come from `epics.md`. It exists because Epic 2's retrospective raised **action item B6** as an explicit open owner decision — *"Decide whether `meta.provenance.model` / `providerCliVersion` wiring is an Epic 3 story or a follow-up"* — and the owner decided, on 2026-08-31, that it is **a separate small story in the Epic 3 cohort**.

**The gap, stated as fact rather than as a claim.** `src/cli/commands/contract.ts:405-406` passes two literal `null`s:

```ts
const { contract, hints } = await generateDraft({
  …
  model: null,
  providerCliVersion: null,
```

So `meta.provenance.model` and `meta.provenance.providerCliVersion` are `null` in **every contract SpecWitness has ever written**, on every path.

**Why it was left.** Story 2.6 (chuck) owns contract generation and its branch was cut **before** the two provider adapters merged, so the capability values it needed did not exist yet. `src/providers/claude-code-cli.ts:105` still carries the handover comment verbatim: *"Verbatim from `--version`, never parsed. Chuck fills `providerCliVersion` from it."* Nobody filled it.

**Why it is small.** Everything except the wiring already exists and is merged:

- `generateDraft` **already accepts** `model` and `providerCliVersion` as inputs (`src/authoring/contract.ts:89-98`), each documented and typed `string | null`.
- `ContractProvenance` (`src/domain/contract.ts:141-147`) already declares all four fields, all nullable, with the "an unknown value is written as an explicit `null`, never omitted" policy.
- The contract schema already validates and serializes them (`src/schemas/contract.ts:237-244, 497-501`).
- **Both adapters already probe `--version`** and expose it on their capability result (`src/providers/claude-code-cli.ts:105-106, 257-282`; `src/providers/codex-cli.ts:192-193, 317-326`).

This is a wiring story, not a design story. Resist making it anything more.

## Story

As someone auditing which model authored a verification contract,
I want `meta.provenance.model` and `meta.provenance.providerCliVersion` populated from the adapter that actually ran,
so that a contract records what generated it rather than four nulls (AD-5, Q65; Epic 2 retrospective action B6).

## Acceptance Criteria

Authored for this story (no `epics.md` entry — see Provenance above). Expand, never weaken.

1. **Given** a project whose `contract-author` role resolves to the `claude-code-cli` adapter
   **When** `specwitness contract <epic>` writes a draft
   **Then** `meta.provenance.providerCliVersion` carries the string the adapter read from `claude --version`, verbatim and unparsed, and `meta.provenance.model` carries the model the CLI reported — each written as an explicit `null` only when the CLI genuinely did not report it.
2. **Given** a project whose `contract-author` role resolves to the `codex-cli` adapter
   **When** a draft is written
   **Then** `providerCliVersion` carries the value from `codex --version`, and `model` is `null` — recorded as a genuine absence, because `--output-last-message` returns message text only and Codex reports no model on that path.
3. **Given** a provider whose `--version` probe failed, timed out, or was never run
   **When** a draft is written
   **Then** both fields are explicit `null` and **the draft is still written** — unknown provenance is recorded as data and never fails contract generation.
4. **Given** an existing contract written before this story
   **When** it is read, re-frozen, amended, or verified
   **Then** nothing breaks and no fingerprint changes: `meta` is never fingerprinted, so populating these fields must not alter any existing contract's integrity state.

Clarifications (detail only, no weakening):

- **AC4 is the one that could do real damage, and it is a fingerprint question.** AD-5 is explicit that a contract has exactly two top-level keys and that **freeze and integrity validation hash only `spec`** — `meta` is *never* fingerprinted. `meta.provenance` lives in `meta`. So this change **must not** move a frozen contract from `frozen` to `tampered`. **Prove it with a test**: take a frozen fixture (`tests/fixtures/contracts/epic-7-frozen.yaml` is merged), write provenance into its `meta`, and assert `contractState` still reports `frozen` with an unchanged fingerprint. If that test is red, stop — you have found something far more important than this story.
- **AC1 "verbatim and unparsed" for `providerCliVersion`.** `src/providers/claude-code-cli.ts` states the rule in its header: *"the version string is reported verbatim and never parsed"*. The codex adapter does pattern-match a version out of its output and **deliberately records nothing when the pattern does not match** (`src/providers/codex-cli.ts:252-255`: *"record a version we could not pattern-match would make the adapter fail for a…"*). **Do not change either behaviour** — read what each adapter already exposes and pass it through. Two adapters legitimately differ here; unifying them is out of scope and would be a change to merged, tested code.
- **AC1 `model` — establish where it actually comes from before wiring it, and record what you found.** `providerCliVersion` is unambiguous (both adapters expose it). `model` is not: `src/domain/contract.ts` says *"On the codex path `model` is routinely null, because `--output-last-message` returns message text only"*, and the claude adapter's `-p --output-format json` envelope is where a model name would live if anywhere. **Read the merged adapter and its tests first.** If the claude adapter does not currently surface a model, you have two honest options — (a) surface it additively from the JSON envelope it already parses, or (b) leave `model` null on both paths and wire only `providerCliVersion`. **Pick one, say which in your PR body, and do not invent a value.** A wrong model string in an audit field is worse than a null: null says "we do not know", a wrong string says something false.
- **`model` must never be inferred, defaulted, or read from config.** It is *"model as reported by the CLI"* (AD-5, Q65). A value from `ai.providers.<name>.mode`, from a constant, or from SpecWitness's own knowledge of what model is probably running is **not** provenance — it is a guess in a field whose only purpose is to be trustworthy.
- **Provenance is recorded at the CLI edge, where the provider actually runs.** `src/domain/contract.ts:128` says exactly that (*"Populated by story 2.6 at the CLI edge"*), and it is an AD-1 requirement rather than a preference: `src/authoring/` is application-layer and may not reach into `src/providers/` capability probing. Keep the wiring in `src/cli/commands/contract.ts` and pass values **down** into `generateDraft`, which already has the parameters.
- **Do not re-probe.** The adapters already probe capabilities per session and the result is available where the provider is constructed. Spawning `claude --version` a second time to fill a metadata field would add a subprocess to every contract generation for no gain — and Epic 2's learning 3 is precisely that a shared probe must also share the judgement over it. **Reuse the capability result the invocation already produced.**
- **AC3 "the draft is still written" is the fail-open direction, and it is correct here.** Everywhere else in this project the rule is fail *closed* — but provenance is a metadata record, not a gate. A contract whose provenance could not be determined is still a valid contract; refusing to write it would turn an unreadable `--version` into a broken product. Say this in your module header so a later reader does not "fix" it.
- **`meta.history` and the amend path.** Story 2.7's amend flow writes a new version referencing the superseded one. Check whether an amended contract's provenance should reflect the amending run or preserve the original, **decide, and state it** — the merged `src/authoring/amend.ts` is the source of truth for what happens today. Do not change amend semantics; if today's behaviour is already right, say so and add a test that pins it.
- **This story does not touch `RunResult.providerUsage`.** That is 3.3's (pamela), it is a *run*-level record of provider invocations, and Epic 3's verify path is AI-free so it ships empty. Her spec already says to leave room for these two fields without wiring them. **Different artifact, different story** — do not "helpfully" unify them.

AD-5 requires contract `meta` to record *"generation provenance (provider, model as reported by the CLI, CLI version, timestamp) for reproducibility"*, and Q65 restates it. Today two of those four fields are `null` everywhere, which means the reproducibility claim is half-true in every contract the product has ever written.

The value is audit, not function: when a contract is later disputed — a criterion looks wrong, a freeze looks premature — the question *"what generated this?"* should be answerable from the artifact rather than from memory. This story makes it answerable.

Keep it small. It is the one story in this cohort that could quietly grow into "improve the provider capability system", and it must not.

### Architecture compliance

- **AD-5.** Provenance lives in `meta`, never in `spec`. `meta` is never fingerprinted — AC4 is that invariant made testable.
- **AD-4.** Capabilities are probed at runtime and cached per session, never hardcoded beyond a tested minimum. You **consume** an existing probe result.
- **AD-1.** `src/authoring/` may not import `src/providers/`; the CLI edge resolves and passes down. That is why the wiring is at the edge.
- **AD-2.** Provenance is metadata about a draft, not content of one. Nothing here relaxes the schema gate: a provider still authors only schema-validated drafts.
- **Conventions.** ISO-8601 UTC (`generatedAt` already is); camelCase YAML keys; no `process.exit` outside `cli/exit.ts`.

- **The three provenance paths:** claude (version present), codex (version present, model null), and probe-failed (both null, **draft still written**).

### Failure modes (the ones that would matter in production)

- **A guessed model string.** The single worst outcome here. An audit field containing a plausible-but-unverified model name is worse than `null`, because `null` is honest and a wrong string is not — and nothing downstream can tell them apart later.
- **A fingerprint change.** If provenance somehow reached `spec`, every frozen contract in existence would report `tampered` the day this merges. AC4 exists for this and must be proven, not assumed.
- **Contract generation failing because `--version` failed.** Turns an unreadable version string into a broken product. Provenance is metadata; fail open, and say so in the header.
- **A second `--version` spawn per generation.** Silent cost added to every contract, for a metadata field, when the value is already in hand.
- **A breaking change to an adapter's capability result.** Two merged adapters and their test suites depend on it. Additive only.

### Security

- **AD-4 / NFR-1.** Provenance comes from the CLI's **own public surface** (`--version`, its JSON envelope) and from nowhere else. Nothing reads `~/.claude/`, `~/.codex/` or any credential store — `tests/unit/doctor/credential-boundary.test.ts` is the AST guard that enforces it across the scanned sources.
- **A version string is untrusted text.** It is written into a YAML document. Record it verbatim as a scalar; do not interpolate it into anything, and rely on the merged serializer rather than string-building YAML by hand.
- **AD-3.** Nothing in this story builds a command string or mints a `DeclaredCommand`. Provider binaries are trusted-tool spawns with fixed argv and deliberately **not** `DeclaredCommand`s; `tests/unit/config/boundary-scan.test.ts` rejects casts and deep imports across every source file outside `src/config/`.

- `tests/fixtures/contracts/` already holds hand-written frozen, draft, tampered and reformatted fixtures. Reuse them; hand-written fixtures are AD-12's rule and a generated one would be checking the code against itself.
