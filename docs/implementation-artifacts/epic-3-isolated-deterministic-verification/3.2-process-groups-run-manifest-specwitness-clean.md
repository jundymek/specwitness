## Story

As an operator whose machine must stay clean,
I want every spawned process tracked in process groups recorded in the run manifest, with teardown and a reaper command,
so that crashes never leak services or worktrees (FR-21 partial, NFR-9, AD-8).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** ProcessRunner
   **When** it spawns any command
   **Then** the child gets its own process group; the pgid and worktree path land in `manifest.json` (schema-versioned, fsynced before resource use — RunStore is the sole runs-directory writer per AD-8) before use; teardown kills the group (SIGTERM then SIGKILL after grace).
2. **Given** execa 10's process-group/detach semantics on macOS (flagged unverified by spine review)
   **When** integration tests run on macOS and Linux
   **Then** a spawned service's grandchildren are demonstrably killed at teardown (test with a shell that forks a child), or ProcessRunner falls back to explicit `process.kill(-pgid)` handling.
3. **Given** a previous crashed run left resources
   **When** I run `specwitness clean` (or `--all`)
   **Then** manifests are replayed: live pgids killed, stale worktrees removed, results reported; already-clean manifests are marked reaped.
4. **Given** a long-running command exceeding its timeout
   **When** the timeout fires
   **Then** the process group is terminated and the outcome classified InfraError or GateFailure per context — never a hang.

Your job is the **incremental append**: a pgid or worktree path must be written and fsynced *before* the process is spawned or the worktree is used — not after, and not batched at the end. Use the existing `#writeDurably` discipline; do not invent a second write path. - **AC1 does NOT bump `schemaVersion`.** `src/schemas/manifest.ts` states the policy in its own header: *"story 3.2 populates the reserved arrays and story 3.5 adds `result.json` alongside — neither bumps `schemaVersion`, because the shape already accommodates them."* `SCHEMA_VERSIONS.runManifest` stays `1`. A bump means every manifest written last week stopped being readable, and there is no such break here.
- **AC2 is the epic's single most important inherited fact, and it is a known open gap — not a hypothetical.** `src/infra/process-runner.ts` carries the reproduction in a comment block, verified against execa 10 / Node 22:
  ```
  sh -c 'while true; do sleep 3600; done'  → still unsettled after 8s
  sh -c 'exec sleep 3600'                  → timed-out in 759ms
  ```

  Story 2.3 fixed **detection** (`run()` now always settles and always classifies, via a grace period past `timeoutMs`) and deliberately left **reaping** to you: *"that needs the child in its own process group and a `kill(-pgid)`, which is AD-8's mechanism and Epic 3 story 3.2's scope."* The evidence that this matters is concrete: Epic 2's own forking-timeout test left **nine orphaned `sleep 3600` processes on this machine**, all reparented to PID 1, reaped by hand after somebody noticed (retro §5 debt 1, and the harness-defects record's closing section). Epic 3 gate commands — `npm test`, `pnpm build`, `docker compose up` — are precisely the child-spawning class.
- **AC2's test must spawn a shell that forks, kill at teardown, and assert the grandchild is gone.** Not the direct child — the grandchild. Assert by pid, after the teardown returns. **This is the acceptance criterion that closes the debt, so it is the one test in this epic that must be seen red first**: run it against the current merged runner, watch the grandchild survive, then make it pass.
- **AC2 "on macOS and Linux": macOS is yours; Linux is pending-owner.** Every gate in Epics 1 and 2 ran on macOS / Node 22.20; **CI has never executed a step** (Actions billing, Epic 1 action A1, still open after two epics) and no worktree has a Linux host. Write the test so it runs on both, run it on macOS, and **report the Linux half as pending-owner in your PR body — never as passed.** Epic 2's retrospective lists exactly this class of claim under "gates no agent could run", and reporting it honestly is the expected behaviour, not a failure.
- **AC2's fallback is explicitly permitted and is probably the answer.** The AC says "*or* ProcessRunner falls back to explicit `process.kill(-pgid)` handling". The spine's Stack table flags execa 10's process-group semantics on macOS as *"verified by Epic 3 story 3.2 tests"* — i.e. nobody has verified them and you are the one who will. **Probe the behaviour, then decide.** Spawn with `detached: true` (which is what puts the child in its own group and makes its pgid equal its pid), and kill the group with `process.kill(-pgid, signal)`. Do not assume execa's `cleanup`/`forceKillAfterDelay` reaches grandchildren — measure it. Record what you measured in the module header, the way 2.3 recorded its reproduction.
- **AC1 SIGTERM → grace → SIGKILL, on the GROUP.** Both signals go to `-pgid`, never to the pid alone. The grace period is a named constant with a comment justifying its value; make it injectable so a test does not have to wait it out in real time.
- **AC3 `specwitness clean` is prompt-free** (Conventions: agent-callable commands are prompt-free, and `clean` is exactly the command an operator scripts). No TTY assumptions, no confirmation prompt, even for `--all`.
- **AC3 "clean reaps resources, never results"** (Q51). V0 keeps every run: `clean` kills live pgids, removes stale worktrees and sets `reaped: true`. It **never deletes a run directory, a `result.json`, or evidence.** A `--prune` retention flag is deferred. Getting this wrong destroys the dogfooding data that is the entire point of Epic 7.
- **AC3 "live pgids" must be checked, not assumed.** A pgid recorded last week almost certainly belongs to something else today — pid reuse is real and killing a recycled pgid would take down an unrelated process tree on the operator's machine. **Decide and document how you establish liveness before signalling**, and prefer a check that cannot false-positive (recording the run's start time and the process's own start time, or `kill(pgid, 0)` combined with a recorded identity check). Say plainly in the module header what your check does and does not guarantee. **A `clean` that kills the wrong process group is the worst outcome available in this story** — worse than leaking, because leaking is visible and recoverable.
- **AC3 scope: `clean` = this project's unreaped runs; `--all` = every run including already-reaped ones** (re-verifying and reporting). State your reading in `--help` text and in the module header; make it unambiguous either way.
- **AC4 "InfraError or GateFailure per context" is the AD-6/AD-7 boundary, and the distinction is not yours to decide at the port.** `ProcessRunner` returns a **classified result** (`timed-out`) — it never throws and never decides a verdict. The *caller* decides: a provider adapter's timeout is a `ProviderError`; a **gate command's** timeout is 3.4's decision (arnold's story specifies it); a service readiness timeout is Epic 4's. Your job is that the outcome is always classified and never a hang. Say this in the port's header so no later story reads `timed-out` as "product FAIL".

### Failure modes (the ones that would matter in production)

- **`clean` kills the wrong process group.** Pid reuse means a pgid recorded last week may belong to the operator's editor today. This is the worst outcome in the story — worse than leaking, because leaking is visible and recoverable while a wrongly-killed process tree is neither.
- **Orphaned descendants after a timeout.** The current, documented behaviour. Nine processes on this machine are the evidence.
- **A manifest write batched to the end.** A `kill -9` between spawning and writing leaves a live process group nothing can find. The fsync-before-use ordering is the whole mechanism.
- **A `schemaVersion` bump.** Makes every existing manifest unreadable — including the ones a crashed run left behind, which is precisely when readability matters.
- **`clean` deleting results.** Destroys the dogfooding data Epic 7 exists to collect. Reap resources, never results.
- **A breaking change to `ProcessRunOptions`.** Two merged provider adapters call it. A required new field turns a wave-A merge into two red branches in wave B.

### Security

- **AD-3, restated because this story is where it would be easiest to break.** No `shell` option, no command string, no `sh -c` anywhere in `src/infra/process-runner.ts`. `binary` + `args[]` go to `execve` untouched. Your tests *may* spawn `sh` as a fixed binary with a fixed argv to produce a forking child — that is a test fixture, not a shell escape, and it belongs in `tests/`, never in `src/`.
- **NFR-1.** Nothing reads `~/.claude/`, `~/.codex/` or any credential store, and nothing in `src/infra/process-runner.ts` reads `process.env` **by name** — the environment is copied wholesale so callers can subtract from it. `tests/unit/doctor/credential-boundary.test.ts` scans this file and asserts an **exact** set of env names read across the scanned sources. If your change adds a name, extend that list deliberately with a comment explaining why — **never relax it to `toContain`**; Epic 2 kept it exact three times and it caught something each time.
- **Signals are sent only to process groups this run created**, recorded in this run's manifest. Never to a pgid derived from anything else.

### Debug Log References

**The red-first proof (AC2).** `tests/integration/process-runner-groups.test.ts`
was written and run against the MERGED runner before any implementation existed.
It failed exactly as the debt predicted:

```
FAIL  kills a forking child GRANDCHILD when the timeout fires
AssertionError: expected false to be true
      expect(await waitForExit(grandchild)).toBe(true);
```

The run classified `timed-out` correctly (story 2.3's detection works) and the
`sleep 3600` grandchild was still alive three seconds after teardown returned.

**The execa probe (AC2, Task 1).** Six configurations measured on macOS 15 /
Node 22.20.0 / execa 10.0.1, written verbatim into the header of
`src/infra/process-runner.ts`. Summary:

| configuration | grandchild | execa promise |
| --- | --- | --- |
| execa `timeout`, not detached | ALIVE | unsettled after 6.7s |
| `subprocess.kill('SIGKILL')`, not detached | ALIVE | unsettled after 6.7s |
| `detached` + `kill(-pgid,'SIGKILL')` | dead | settled in 428ms |
| `detached` + `kill(-pgid,'SIGTERM')` then SIGKILL | dead | settled in 426ms |
| `detached` + execa `timeout` | ALIVE | unsettled after 6.7s |
| `detached` + `timeout` + `forceKillAfterDelay` | ALIVE | unsettled after 6.7s |

So execa never signals the group even when it created one, and AC2's explicitly
permitted fallback — explicit `process.kill(-pgid, ...)` — is the answer.

**The guard that killed its own test runner.** The first version of
`assertSignallableProcessGroup` refused only `pgid <= 1`, `process.pid` and
`process.ppid`. The test asserting "never signals this process group" then
signalled the vitest worker's real pgid and **killed the whole run** (exit 144,
no output) rather than failing. Node has no `getpgid`, so the guard now reads the
real pgid from `ps` once and caches it. Recorded as D6 in `DECISIONS.md`; the
test comment says why the check cannot be `pgid === process.pid`.

**Orphans reaped by hand during development.** The red-first run and the probe
leaked eight `sleep 3600` processes (ppid 1) onto this machine before the
implementation existed. They were reaped, and the suite now asserts it leaves
none: `afterEach` RECORDS anything still alive before force-killing it, and
`afterAll` asserts the recording is empty, so the safety net cannot be what makes
the assertion pass.

**Two defects found by Codex review, both accepted and fixed (D16, D17).** Both
were the same class, and it is the class this story exists to prevent —
reporting a clean sweep over a resource that is still there:

- **P1:** `clean` skipped worktree removal whenever the recorded directory was
  absent. A crashed run can delete a checkout while its git registration
  survives, so the run was marked reaped with the stale registration left
  behind. `worktreeExists` is gone from the seam; removal is now called for
  every recorded path, because only the removal effect can see the
  registration. Regression test added, deterministically red against the old
  code.
- **P2:** the `ps` parser silently dropped lines it could not read, so a live
  member with an unreadable `lstart` made its group look empty and read as
  `gone`. Now `kill(-pgid, 0)` is asked directly and is the only thing allowed
  to conclude `gone`, and every parse failure is recorded rather than dropped.
  Rule, now in the module header: absence is never inferred from silence.

**Three more from a third Codex pass (D22-D24).** Two accepted outright, one
adopted with its rationale corrected:

- **P1, accepted:** `#writeDurably` opened with `'w'`, truncating. Harmless when
  story 1.6 only CREATED files with it; destructive once this story made it the
  path that rewrites the manifest on every append, because a `kill -9` between
  the truncate and the fsync leaves malformed JSON and `clean` can no longer
  discover what the run had recorded. Now staged and renamed, so a reader sees
  either the previous complete file or the new one. Still ONE durability
  discipline — not a second write path, and not story 3.5's reserved
  `result.json` finalize.
- **P1, adopted but rationale corrected:** `recordProcessGroup` now holds the
  mutation queue for both its writes. **The symptom the finding described —
  `markReaped` overtaking the pair so a later `clean` skips the run — is not
  actually prevented by grouping**, since a `markReaped` running entirely after
  leaves `reaped: true` just the same; that is a caller-ordering question. The
  change is kept because it is free and makes a half-recorded process group
  unobservable, and the test and comment state the accurate guarantee rather
  than the asserted one.
- **P2, accepted:** the evidence containment check was purely lexical, so a
  symlinked component inside the run directory would carry a write outside it
  while every string still looked contained. Now `realpath`-checked on both
  sides, with a real-symlink regression test.

**Two more from a second Codex pass, both accepted and fixed (D18, D19).**
Both were about a guarantee being weaker than it read:

- **P1:** the timeout timer was armed AFTER awaiting `onProcessGroup`, so a
  stalled fsync left the child running with no timer at all — `timeoutMs` was
  conditional on the caller's hook. Both timers are now armed immediately after
  spawn, and the hook is raced against the watchdog so a hook that never settles
  cannot make `run` never settle.
- **P2:** `terminateProcessGroup` resolved when SIGKILL was *delivered*, not when
  the group had exited. `clean` removes a worktree the instant teardown resolves,
  so a member still holding files inside it turned a successful kill into a
  spurious removal failure. Teardown now polls for ESRCH with a bounded deadline
  and raises if the group survives SIGKILL.

**A fixture that made one of my own waits a silent no-op.** The
SIGTERM-ignoring script signalled readiness with `touch`, which creates an EMPTY
file, while `waitForFile` only accepts non-empty content — so the wait could
never succeed, and the test swallowed it with `.catch(() => undefined)`. The
fixture now writes content and the wait is asserted properly. Found by writing a
second test against the same fixture.

**A regression I introduced, found by a flake and fixed (D14).** Taking the
timeout over from execa meant replacing a REF'D timer with my own, and the first
version unref'd every replacement — copying the existing watchdog's `unref`
without noticing the watchdog was the outer net rather than the thing keeping
the loop alive. `src/cli/main.ts` ends in a top-level `await`, so an event loop
that empties while a run is pending makes Node exit **13**
(`ERR_UNFINISHED_TOP_LEVEL_AWAIT`) — a code that is not in the frozen table at
all, printed with no output and no ERROR/HINT pair. It surfaced once as
`doctor > names the variable and still exits 0` failing with `expected 13 to be
+0`.

Fixed by a rule now stated in the module: any timer whose expiry a run's
settlement depends on is REF'D and CLEARED, never unref'd. Clearing gives back
what unref'ing was for. Guarded by
`tests/integration/process-lifecycle-exit.test.ts`, whose header records the
honest limit — the original failure was load-dependent and re-introducing the
`unref` did not reproduce it on demand, so that file is a guard against an
off-table exit code rather than a proven reproducer.

**A race in one of MY tests, and a documentation claim it corrected (D15).**
`clean.test.ts` read the manifest as soon as the child's grandchild appeared and
intermittently found the pgid not yet written. The test was wrong, and so was a
sentence I had written: the unrecorded window is not "one spawn syscall wide" —
the child is ALREADY RUNNING, and may fork, while the record is being fsynced.
What the ordering actually guarantees is that the record is durable before the
run PROCEEDS. Both headers now say that, and the test awaits the record.

**Temp-directory hygiene, measured after alice raised it.** She saw leftover
directories containing `forks.sh` and traced them to my crashed-run fixtures.
The attribution was off by one file: they came from the hand-run manual-test
script, which deliberately builds a crashed run and exits without tearing
anything down, and which I ran twice without cleaning up after myself. Measured
per prefix afterwards, every fixture directory this story creates is reaped —
`specwitness-groups-`, `-clean-`, `-clean-int-`, `-clean-fixture-`,
`-clean-bare-`, `-runstore-`, `-identity-`, `-lifecycle-` all at zero — and the
delta across a full `pnpm test` is **0**. Noted for the retro rather than fixed
here: an earlier count found 12,529 leftover `specwitness-*` directories in
tmp (5,656 from doctor fixtures, 3,333 from config, 2,958 from amend, 174 from
gates), none of them from this story. They are gone and the suite no longer
accumulates them, but the number is worth someone knowing existed.

**One pre-existing flake, investigated and left alone.**
`tests/unit/providers/claude-shim.test.ts` > "hanging: does not exit, and is
killed by the caller timeout" failed twice during full-suite runs on a machine
running eight agents' suites at once, with `shim recorded no invocation at index
0` — the shim was killed before it could append its record. It passes in

**It cannot be affected by this story:** that test calls `execa` DIRECTLY with
