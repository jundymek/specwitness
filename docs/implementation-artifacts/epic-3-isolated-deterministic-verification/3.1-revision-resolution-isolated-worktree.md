## Story

As a supervisor invoking verify from my own worktree,
I want SpecWitness to resolve root/base/head explicitly and execute in a detached temp worktree,
so that my workspace and the source repo are never touched (FR-19, AD-8; UJ-2).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** `--root <dir>` (or CWD containing the repo), `--base <ref>`, `--head <ref>` (head may be a remote-only ref like `origin/epic/7-slug`; defaults from config; epic-id normalization applied)
   **When** verify starts
   **Then** head is resolved to a SHA (fetching if needed is NOT done implicitly — a missing ref yields a named error with `HINT: git fetch`), and a detached worktree is created under the OS temp dir.
2. **Given** any run end — success, failure, or SIGKILL mid-run
   **When** the source repo is inspected afterward
   **Then** `git status` is unchanged and no worktree remains registered after cleanup/`clean` (integration test kills the process mid-run).
3. **Given** an ambiguous or unresolvable root
   **When** verify starts
   **Then** it refuses with a named error rather than guessing (house rule from harness survey).

Clarifications (detail only, no weakening):

- **AC1 "never implicitly fetch" is a security and correctness rule, not a convenience choice.** An implicit fetch would make verify's result depend on network state and would mutate the source repo's refs — a write, in a story whose whole point is that the repo is read-only. A missing ref is an `InfraError` (exit 3) naming the ref, with `HINT:` telling the operator to run `git fetch` themselves. Test both halves: the error names the ref, and **no fetch occurred** (assert the source repo's refs are byte-identical after the failure).
- **AC1 ref resolution uses `git rev-parse --verify <ref>^{commit}`.** The `^{commit}` peel matters: without it an annotated tag resolves to the tag object's SHA rather than the commit's, and the worktree would be created at a different revision than the one reported in `RunResult`. `--verify` makes a missing ref a non-zero exit rather than an echo of the input.
- **AC1 `--base` is resolved and recorded but not checked out.** V0 runs one worktree, at head. Base exists in the model because differential BASE/HEAD verification is a v2 feature the run record must already accommodate (spine Deferred, Q67) — so resolve it, record its SHA, and do nothing else with it. A base ref that does not resolve is still an error: recording a null base would silently disable the future feature.
- **AC1 defaults come from Project Config, never from a guess.** `project.baseBranch` is **required** by the merged schema (no default — `src/config/schema.ts` is explicit that the base branch is never assumed). `project.epicBranchPattern` is optional; when present it derives a head ref from the normalized epic id, when absent `--head` is required. Real harnesses vary — the first-client survey found `epic/<n>-<slug>` branches, per-project base branches including `master`, and invocation from worktrees where CWD-guessing fails (FR-19). **Guessing a branch name is the failure this AC exists to prevent.**
- **AC1 epic-id normalization is the merged `normalizeEpicId`** in `src/domain/ids.ts` (`7` ≡ `epic-7` ≡ `epic-07` → `epic-7`). One implementation, already tested. Do not write a second.
- **AC2 is the epic's strongest safety property, and it is testable three ways.** Assert all three:
  1. a **clean run** — `git status --porcelain` in the source repo byte-identical before and after;
  2. a **failing run** — same;
  3. a **SIGKILL mid-run** — same, plus no worktree left registered after `specwitness clean` replays the manifest. The kill test is yours at the unit/integration level (kill your own harness process mid-worktree); **3.7 owns the end-to-end version** through the built binary. Say which is which in your PR body so the supervisor is not told the same thing twice.
- **AC2 "no worktree remains registered"** means `git worktree list --porcelain` in the source repo shows none of yours. A removed directory with a live registration is the leak that matters — git keeps administrative files under `.git/worktrees/<name>` and they survive an `rm -rf` of the checkout. Use `git worktree remove --force`, and treat `git worktree prune` as the recovery path rather than the primary one.
- **AC2 the reaping half belongs to 3.2 (bob), and the seam between you is the manifest.** You record the worktree path into the run manifest **before** the worktree exists-in-use (AD-8); bob's `clean` replays it and removes it. Neither of you owns both halves. **Publish the exact shape you write during intent-sync** — `RunManifestSchema.worktrees` is already `z.array(z.string().min(1))` in the merged `src/schemas/manifest.ts`, so the shape is fixed; what you must agree with bob is *who calls the RunStore method* and *what it is named*. bob owns `src/infra/run-store.ts` this wave — **you do not edit that file**; you call the method he publishes.
- **AC3 "ambiguous or unresolvable root":** refuse, name what was ambiguous, and hint at `--root`. Cases to handle explicitly — a `--root` that does not exist; a `--root` that is not a git repository; a CWD with no repository above it; and **a CWD inside a git worktree of another repository**, which is the case the harness actually produces (this project's own agents each work in `/Users/jundymek/dev/specwitness-agents/<agent>`, a linked worktree). Decide and document what "the repo root" means when invoked from a linked worktree — the common-dir's main worktree, or the linked worktree itself — and test it. **Getting this wrong silently verifies the wrong tree.**
- **Probe git capabilities, do not assume them.** The features this story depends on — `git worktree add --detach`, `git worktree list --porcelain`, `git worktree remove --force`, `git rev-parse --verify <ref>^{commit}` — are all present in git 2.50.1 (verified on the development machine, 2026-08-31). A missing or too-old `git` must produce a named `InfraError`, never a crash or a wrong answer. `src/cli/doctor/checks/git-present.ts` already establishes the "is git usable" diagnosis; reuse its vocabulary rather than inventing a second one.

### Failure modes (the ones that would matter in production)

- **Verifying the wrong tree.** Invoked from a linked worktree, a naive root walk finds the linked worktree's `.git` file rather than the main repository. A verify that silently checks out the wrong revision reports a verdict about code nobody asked about — and it would look completely normal. This is the highest-consequence bug available in this story.
- **A worktree registration that outlives its directory.** `rm -rf` on the checkout leaves `.git/worktrees/<name>` behind, and the next `git worktree add` at the same path fails with a confusing error. Always `git worktree remove --force`.
- **An implicit fetch.** Makes the verdict depend on network state and writes to the source repo. Never.
- **A tag resolved to the tag object.** The worktree is created at a SHA that is not the one recorded in `RunResult`, so the evidence describes a revision that was never verified.
- **A temp worktree under the source repo.** `mkdtemp` inside the repo would put SpecWitness files in the project working tree, violating AD-8 and showing up in the operator's `git status` — the exact thing AC2 forbids.

### Debug Log References

Three findings came from measuring rather than reasoning; two of them changed the
implementation.

1. **`git rev-parse --verify` does NOT fail on an ambiguous ref.** Found by a failing
   test, not by review. With a branch `release` and a tag `release` at different
   commits, git 2.50.1 prints `warning: refname 'release' is ambiguous.` to stderr,
   **exits 0**, and silently returns the tag's commit by its precedence rules. Trusting
   the exit code would have handed the operator a verdict about a revision they never
   named — the exact "verifies the wrong tree" failure this story exists to prevent.
   The adapter now decides ambiguity itself, by enumerating the candidate refs over the
   six namespaces `gitrevisions(7)` documents and refusing when they resolve to more
   than one distinct commit. Deciding on resolved commits rather than on git's warning
   text also means a branch and its remote-tracking ref at the same commit stay
   unambiguous instead of failing a run for no reason. Both behaviours are tested.

2. **The annotated-tag peel is real, and measured.** `git rev-parse v1` returned
   `f043638…` (the tag object) while `git rev-parse v1^{commit}` returned `04f090d…`
   (the commit). The fixture asserts the two genuinely differ, so the peel test cannot
   quietly become vacuous if a future git changes behaviour.

3. **`os.tmpdir()` is a symlink on macOS.** A `mktemp -d /tmp/x` came back from
   `git worktree list` as `/private/tmp/x`. Every containment check (`under tmpdir`,
   `not under the source repo`) realpaths both sides; comparing raw strings silently
   answers the wrong question.

4. **The declared git floor was wrong, and the security pass caught it.** The first
   draft set `MIN_GIT_VERSION = '2.17.0'`, counting only the worktree features
   (`worktree list --porcelain` is 2.7, `worktree remove --force` is 2.17). But
   `revParseCommitArgs` passes **`--end-of-options`**, which is git **2.24**. On a git
   between 2.17 and 2.23 the probe would have said "usable" and then every ref
   resolution would have failed on an unknown option.

   The separator is not decoration: `--head` is operator input and a git refname may
   begin with a dash, so without it a ref named `--upload-pack=…` would be parsed as an
   OPTION to `rev-parse` rather than as a revision. Dropping the guard to keep
   compatibility with releases from before 2019 would have traded a security property
   for nothing anyone asked for, so the floor moved instead. Regression test added, so
   the next flag that outranks the floor moves it too.

5. **The Codex review pass found four real defects, all in failure paths, and each was
   reproduced with a failing test before being fixed**
   (`tests/unit/vcs/failure-classification.test.ts`). They shared one shape — the
   adapter reporting success, or a confident wrong diagnosis, while the environment was
   broken — which is the failure class this project treats as first-order:

   - **A failing `git worktree list` read as "nothing is registered".** `listWorktreesIn`
     turned a timeout or spawn failure into `[]`, so `removeWorktreeAt` treated every
     recorded worktree as already-absent and returned successfully. Story 3.2's `clean`
     would have reported a clean sweep while the checkout and its registration were
     still there. An empty list and an unanswerable question are different facts, and
     only one of them means "nothing to reap". It now raises `InfraError`.
   - **A `worktree add` that failed AFTER registering left the registration behind.** A
     timeout arriving once `.git/worktrees/<name>` was written meant the failure path
     deleted only the container, leaving a registration whose directory was gone — and
     the next add at that path then fails confusingly. The registration is now cleared
     first, best-effort, with the original error still thrown.
   - **Every non-zero `rev-parse` was classified `not-found`.** A repository that became
     unreadable after root resolution (a deleted `.git`, a permission change, an
     unmounted filesystem) therefore received the `git fetch` hint — a confidently wrong
     diagnosis, the same mistake `isBinaryNotFound` was fixed twice to avoid. The
     repository is re-probed now, which is also what makes `resolveRef`'s `not-a-repo`
     arm reachable at all; an arm no code path could produce was a sign the
     classification was wrong, not that the arm was spare.
   - **SHA-256 repositories were rejected.** The object-id validator accepted only 40 hex
     characters, so in a repository created with `git init --object-format=sha256` an
     existing ref was reported as missing.

   A second review pass over the fixes found two more, of the same family — the
   ambiguity check itself degrading into `resolved`:

   - **A failing `for-each-ref` read as "no candidates".** The ambiguity check would
     then return `resolved` carrying git's precedence pick — accepting a possibly
     ambiguous answer *because* the check that guards against it had failed. Exactly
     backwards; it now fails closed as `git-unavailable`.
   - **Pseudorefs were invisible to the check.** Git's lookup order starts at
     `$GIT_DIR/<name>`, one step before `refs/`, so a branch named `FETCH_HEAD`
     alongside a real `.git/FETCH_HEAD` at another commit is two answers to one name —
     and an enumeration walking only `refs/**` calls it unambiguous. The comment
     claiming those patterns were "exactly the six namespaces" was simply wrong, and is
     corrected.

   A third pass found the same mistake once more — a timed-out `rev-parse` during root
   resolution reporting **`not-a-repo`**, telling an operator that their perfectly good
   repository is not one. At that point it was clearly a class rather than three
   coincidences, and the root cause was a single helper: `query()` returned
   `string | null`, so **every** caller had to read `null` as "git said no". The fix is
   structural rather than another patch — `query()` now returns a three-armed outcome
   (`ok` / `said-no` / `unavailable`), so a caller has to name the case it is handling
   and the collapse is no longer spellable. `queryText()` remains for the two callers
   that genuinely cannot act on the difference.

   That refactor immediately paid for itself: re-reading the result surfaced one more
   site nobody had flagged — a failed `worktree list` inside `resolveRoot` still
   reporting `not-a-repo`. It stood out precisely because every other caller now had to
   name its case, which is the argument for fixing a class at the helper rather than at
   the call sites one review pass at a time.

   A fourth pass then found two more. One was **self-inflicted by the refactor**: the
   re-probe in `resolveRef` tested `kind !== 'ok'`, which lumps `unavailable` back in
   with `said-no` — the exact collapse the three-armed type exists to prevent, re-created
   in the commit that introduced it. Worth recording plainly, because it shows a type
   only helps where a caller actually distinguishes the arms.

   The other was **the most consequential defect in the story, and nothing to do with
   error handling**: `git worktree list --porcelain` writes paths VERBATIM, and a newline
   is a legal POSIX filename character — so a worktree path containing one was split
   across lines and its tail read as another attribute. Since `mainWorktreeRoot` is taken
   from the first record, a corrupted parse means **verifying a tree nobody asked about**,
   and the registration checks guarding removal silently stop finding the worktree they
   are meant to reap. Both are the failure modes this story's Dev Notes name as the
   highest-consequence ones available, reached by a route I had not considered. Fixed
   with `-z` (NUL-terminated fields, empty field ends a record), with a test that creates
   a worktree at a path containing a real newline.

   That moved `MIN_GIT_VERSION` a second time, 2.24 → 2.36. Both moves were a correctness
   guard outranking the floor, and the trade was the same each time: keeping compatibility
   with a git from 2019 or 2022 is not worth dropping a guard in a tool whose only job is
   to be right about what it verified.

   A fifth pass made the sharpest point of the lot, and it was about **an over-claiming
   comment rather than a broken line**. `addWorktree` took its manifest hook as an
   OPTIONAL parameter while the module header asserted that "a worktree cannot come into
   existence unrecorded". Any caller could write `addWorktree(root, sha)` and register a
   worktree whose path was never persisted — after which a `kill -9` leaves a
   registration `clean` has no manifest entry to discover, which is precisely the
   crash-recovery guarantee this story exists to provide. An optional parameter cannot
   enforce an invariant; the claim was true only by convention. The recorder is now a
   REQUIRED argument (`RecordWorktreePath`), so the type says what the comment said, and
   tests with nothing to record pass a named `recordNothing` that reads as the deliberate
   choice it is.

   Worth noting how that finding was phrased: *"make recording mandatory in the creation
   API **or** add the required worktree stage before marking this story for review."*
   The second option was not available to me — the stage file is pamela's to create and
   she chose the sequencing — so I took the first, which is the stronger fix anyway
   because it constrains every future caller rather than the one I would have written.

   A sixth pass found the last two, and one is the most serious defect in the story:

   - **`removeWorktreeAt` would force-remove ANY registered worktree.** `clean` feeds it
     paths read out of a crash-recovery manifest — a file `parseRunManifest`'s own header
     warns "may have been edited by hand" — and `git worktree remove --force` deletes a
     **dirty** checkout without complaint. One stale or tampered entry naming a real
     workspace was unrecoverable data loss; on this machine, nine agent worktrees full of
     uncommitted work. Ownership is now checked: the path must be `<container>/worktree`
     with the container named `specwitness-worktree-*`, the exact shape `addWorktree`
     mints and nothing else has.

     The **ordering** of that check turned out to be the whole design, and three existing
     tests caught it. Checking ownership first broke the promise made to bob that an
     already-absent path is a no-op — which is what lets `clean` keep replaying entries
     that were already reaped. Checking it only once the registration lookup says there
     is something to *destroy* satisfies both: an unregistered path destroys nothing, so
     it is a no-op whatever its shape, while a registered path that is not ours is
     refused loudly. Deliberately NOT part of the check: whether the path lies under
     `os.tmpdir()`. `TMPDIR` can differ between the run that created a worktree and the
     `clean` that reaps it, and a reaper that stopped recognising its own worktrees
     because an environment variable moved would be worse than the problem it solves.

   - **The location guard protected only the MAIN worktree.** Invoked from a linked
     worktree — how every agent on this machine works — with `TMPDIR` resolving inside
     that checkout, SpecWitness would have created its container in the operator's own
     workspace, visible in their `git status`. That is exactly what AC2 forbids and what
     FR-19 is written about, so the guard now covers `worktreeRoot` as well as
     `mainWorktreeRoot`.

   Fixing the pseudoref finding took two attempts, and the intermediate failure is the
   interesting part. Refusing whenever git warns is too aggressive: git warns even when
   the candidates sit at the **same** commit, so a branch and its remote-tracking ref —
   an everyday, entirely unambiguous state — started failing. My own earlier test caught
   it. The right question is not "did git see several candidates" but **"did git resolve
   to something this module cannot account for"**: if the returned sha is one of the
   commits the enumerated refs point at, the name has one meaning whatever git warned;
   if it is not, git resolved through a namespace invisible here and refusing is the only
   safe answer.

Also worth recording, because it was briefly misleading: `tests/unit/vcs/port.test.ts`
went **green against a `src/domain/vcs.ts` that did not exist**. vitest erases type-only
imports, so the type-level exhaustiveness guard lives in `pnpm typecheck`, not
`pnpm test` — under `tsc --noEmit` the same file failed three ways (TS2307, TS2322 ×2).
The test header now says so.

And one self-inflicted defect, found by checking rather than assuming: the first
revision of the unit suite left **nine empty `specwitness-worktree-*` containers** under
`os.tmpdir()` after a single `pnpm test` — the same shape as Epic 2's nine orphaned
`sleep 3600` processes (retro §5 debt 1). The product behaviour was correct
(`removeWorktreeAt` deliberately does not touch a container, agreed with bob so that
`clean` never guesses at deleting a temp directory it did not create); the tests simply
did not own their leftovers. Fixed, and `tests/integration/worktree.test.ts` now asserts
the no-leak property on the exact paths it created — never by sweeping `os.tmpdir()`,
which would be flaky under H-8 since the harness runs `pnpm test` concurrently.

**Key decisions:**

- **The linked-worktree case.** `RepoRoot` keeps both `worktreeRoot` (where you
  invoked from) and `mainWorktreeRoot` (the repository, found as the first entry of
  `git worktree list --porcelain`). Measured from this agent's own checkout:
  `--show-toplevel` answers `…/specwitness-agents/alice` while the repository is
  `/Users/jundymek/dev/specwitness`. This project is itself the case the story warns
  about, and it has a test.

  **Scoped precisely, because calling this one "verifying the wrong tree" overstates it.**
  predator (3.7) put it better than I had, reviewing the published contract: what gets
  verified is whatever `--head` resolves to, and that is a SHA out of the object store the
  two trees SHARE — so it is identical from either. What this decision actually governs is
  which repository is *named* in an error and which one AD-8 claims untouched, and the main
  worktree is the right answer to both, because the linked tree is a view of it. The
  genuine wrong-tree failures in this story are elsewhere: an inherited `GIT_DIR` (a
  different repository entirely) and a newline in a worktree path (a mis-parsed first
  record, hence a wrong `mainWorktreeRoot`). Worth recording so a later reader weighing a
  change here knows which risk is which — and worth noting that it took a second reader of
  the published interface to separate them.
- **Spawning through the merged `ProcessRunner`** rather than a second execa call site,
  so the ENOENT-vs-invalid-`cwd` classification that Epic 2 fixed twice exists in one
  place. The doctor's failure vocabulary is mirrored, not imported
  (`nothing-imports-cli`), and the module header says so.
- **AD-8's record-before-use ordering is structural:** `addWorktree` awaits an
  `onPathReserved` hook before any git write, and a rejecting hook aborts creation, so a
  worktree cannot exist unrecorded. The residual one-syscall `mkdtemp` window is
  documented rather than papered over.

  `WorktreeRecorder` port, so neither branch depends on the other's merge order; he also

  wrapper so `clean` stays a dumb, robust reaper, and it ships here.
