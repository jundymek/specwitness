## Story

As a cost-conscious operator,
I want configured gates to run in order with captured evidence and early stop,
so that a broken branch fails fast before any AI/browser spend (FR-20, FR-28 partial; ADR-003).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** ordered gates in config (e.g. install, lint, typecheck, unit, build)
   **When** all pass
   **Then** each gate's duration and truncated output land as gate evidence and the pipeline proceeds.
2. **Given** a failing gate
   **When** it exits non-zero
   **Then** the run ends with Verdict FAIL + `gateFailed: <id>`, remaining gates and all criteria reported `skipped`, the gate's stdout/stderr stored as evidence (bounded inline, full in run dir), exit code 1 (ADR-003 semantics; Golden Corpus fixture 7).
3. **Given** a gate command that cannot start (missing binary)
   **When** execution is attempted
   **Then** the outcome is InfraError (exit 3), not FAIL (classification test).

Clarifications (detail only, no weakening):

- **AC2 and AC3 together are the product promise of this epic, and each needs its own test that can actually produce the state.** A gate that *runs and exits non-zero* is a product FAIL (exit 1) — the branch demonstrably does not build. A gate that *cannot start at all* is infrastructure (exit 3) — SpecWitness could not reach a conclusion. The merged `ProcessRunner` already hands you exactly this distinction as a closed `ProcessOutcome`:
  - `completed` with a non-zero `exitCode` ⇒ **gate `fail`** ⇒ FAIL + `gateFailed`
  - `not-found` (binary missing) ⇒ **InfraError** — `'infra'` classification, exit 3
  - `spawn-failed` (e.g. an invalid `cwd`) ⇒ **InfraError**, exit 3
  - `timed-out` ⇒ **your decision, stated explicitly** (see below)
  Map every arm of that union with a `never` exhaustiveness check, so a future `ProcessOutcome` value cannot silently fall through to "gate passed". **This is the mapping the whole exit-code contract rests on.**
- **AC3's `not-found` distinction has a merged, hard-won subtlety — do not re-derive it.** Under execa 10 with `reject: false` a missing binary **resolves** rather than throwing, and an **invalid `cwd` raises the identical ENOENT**. `src/infra/process-runner.ts` already resolves this by asking the filesystem whether `cwd` is a directory rather than sniffing execa's message. You consume `ProcessOutcome`; you do not re-classify ENOENT. (Epic 2 retro learning 4: a first fix made this *worse* — a vague wrong answer became a confident one, telling operators to install a `git` they already had.)
- **A gate timeout: decide, state it, test it.** Recommendation: **InfraError**, not FAIL. A gate that hung tells you nothing about whether the branch is mergeable — SpecWitness failed to reach a conclusion, which is exactly what exit 3 means, and exit 1 would tell the harness "this branch has defects" on no evidence. Whatever you choose, put the reasoning in the module header and pin it with a test. Note this is *your* decision to make: `src/domain/process-runner.ts` deliberately classifies the outcome without verdicting it, and story 3.2's spec says so explicitly.
- **AC2 "remaining gates and all criteria reported `skipped`"** — `skipped` is the merged `GateStatus`/`CriterionStatus` value and is documented as *inert*. Produce a `GateResult {gateId, status: 'skipped'}` for every gate after the failing one, in declaration order, so the report shows what did not run. Do not omit them: a missing gate and a skipped gate look identical in a report, and only one of them is true.
- **AC2 does NOT re-implement aggregation.** `aggregate(gates, criteria)` in `src/domain/verdict.ts` (merged, with a property suite) already returns `{verdict: 'FAIL', gateFailed: <failing gate's id>}` when any gate has `status: 'fail'`. Your stage produces `GateResult[]`; pamela's aggregate stage calls `aggregate`. **You never construct a `RunOutcome` and you never touch an exit code.**
- **AC2 `gateFailed` carries the gate ID as a string, not a boolean.** `ADR-003`'s prose says `gateFailed: true`; the merged `src/domain/run-outcome.ts` implements `gateFailed?: string` carrying the failing gate's id, because the presence *is* the boolean signal and the id routes repair automation to "fix the build". **Follow the code.** (This is carried action item A3 — the ADR wording is the thing that is stale, not the implementation.)
- **AC1/AC2 evidence is produced through pamela's constructors, never hand-built.** `domain/evidence.ts` (3.3) owns the typed `gate`/`command` evidence and applies **redaction at capture** (AD-10). You call the constructor; you do not redact, and **3.6's renderers never re-redact**. Bounded inline output plus the full file in the run directory, with a truncation marker pointing at it (Q49). The cap and the marker's shape are pamela's to define and publish; use them.
- **Full gate output goes into the run directory through `RunStore`, which is the sole writer under `.specwitness/runs/`** (AD-8, enforced as a grep-level rule: outside `src/infra/run-store.ts` no module may construct a path under `.specwitness/runs`). **Check what bob (3.2) merged before you write anything** — he adds manifest lifecycle methods to that file in wave A, and rambo (3.5) adds the `result.json` finalize in your wave. If RunStore has no method for writing an evidence file when you get there, that is a message to rambo and a coordination point, not a reason to write the file yourself.
- **AC1 "gates run in order" is config declaration order**, and the merged schema guarantees it: `gates` is `z.array(gateSchema)` (ordered) with **cross-field uniqueness on `id`** enforced at load time. So you may rely on ids being unique and the order being meaningful — and you must **not** re-validate either.
- **Early stop is the point of the story.** FR-20: a failing gate stops the pipeline *before any Provider or browser cost*. Assert it mechanically: after a gate fails, no later stage executed and no further command was spawned.
- **Gates execute in the worktree**, not in the source repo — the cwd is 3.1's temp worktree path, handed to you. Nothing is written into the project working tree (AD-8).

### Failure modes (the ones that would matter in production)

- **A missing binary reported as FAIL.** The single most damaging bug available in this story: a mergeable branch blocked, or a developer sent hunting a defect that does not exist. Exit 3 says "fix your environment and rerun"; exit 1 says "your code is broken". They are not interchangeable.
- **A gate that cannot start reported as PASS.** The mirror image, and worse: `ProcessOutcome` has four arms, and a `switch` without a `never` check that only handles `completed` would treat a `not-found` gate as "no failure seen". Exhaustiveness is not a style preference here.
- **A thrown gate failure.** Turns exit 1 into exit 3 and tells the harness to retry a branch that will never build.
- **Missing `skipped` entries.** A report that omits the gates after the failure is indistinguishable from one where they passed.
- **Unbounded gate output in the terminal.** `npm test` output can be megabytes; the caller is often an agent context (NFR-8). Bounded inline plus a pointer is the requirement, not a nicety.
- **A gate spawned in the source repo instead of the worktree.** Silently verifies the wrong tree and may write into the operator's working directory.

### Security

- **You are the first module in the product to execute a project-declared command.** The AD-3 boundary has been theoretical until this story; from here it is load-bearing at runtime. What makes it safe: `DeclaredCommand`s come only from `.specwitness/config.yaml`, they reach `ProcessRunner` as a binary plus an argv array, and there is no `shell` option anywhere in the port. Do not add one, do not build a command line, do not pass a gate's `run` string through `sh -c`.
- **Never mint or cast a `DeclaredCommand`.** The brand's symbol is unexported; the only remaining route is a deliberate cast, which the AST scan rejects mechanically.

### Debug Log References

Four findings worth keeping, all of which changed code rather than only a test.

**1. Two defects in story 3.3's published shapes, found by building against them (raised, accepted, fixed by pamela).**

- `RunResult.evidence` / `RunAccumulator.evidence` were `EvidenceRef[]` (`{kind, path}`), but `gateEvidence()` returns a `GateEvidence` carrying `stdout: BoundedText`. The redacted, bounded inline output was therefore discarded at the moment of construction. That made AC1 ("duration and **truncated output** land as gate evidence") and AC2 ("**bounded inline**, full in run dir") unsatisfiable, and also story 3.6's renderer AC — its published signature is `renderTerminal(result: RunResult): string` with no filesystem access, and AD-11 forbids a renderer computing its own facts. AD-10 and Q47 both describe evidence as the closed *union*; 3.3 changed `evidence` to `Evidence[]`.
- **A secret-persistence hole.** AD-10 requires redaction *before any persistence*, but the only redactor exposed was `boundedText()`, which redacts **and truncates** — and the full file must not be truncated. As published there was no way to redact the full copy, so the inline evidence would have been clean while the file written beside it in the run directory held the credential verbatim. The obvious seeded-secret test, which inspects only the inline evidence, **passes green over exactly that hole** — a test that certifies the defect. 3.3 now exports `redactText(raw, options?)`; this stage calls it on every byte handed to the evidence writer, and the test asserts on those exact bytes as well as on the evidence.

**2. A cross-module disagreement found by a property test, on its first run.**

`splitCommandLine().binary` is pinned against the merged `firstToken()` in `src/cli/doctor/checks/commands-resolvable.ts`, because if those two disagree about which token is the executable, doctor's verdict stops predicting whether a gate can run — it would pass a command that cannot start, or fail one that runs perfectly well. fast-check found `'''`: an earlier tokenizer checked quote balance across the **whole line** and fell back to a plain whitespace split, while `firstToken` looks only at the first token. An unclosed quote must degrade only its own token. Counterexamples (`'''`, `"""`, `'`, `''`, `node "ok" "dangling`) are kept as named regressions rather than left to 500 random runs to rediscover.

**3. An integration test that passed for the wrong reason.**

The `node()` fixture helper built command lines with `JSON.stringify`, whose escaped inner quotes the splitter deliberately does **not** interpret — there is no shell on this path to define what an escape would mean, which is the AD-3 boundary showing through rather than a defect. A script containing double quotes therefore became a different command. The early-stop test consequently passed because the side effect it looked for could never have happened, for a second and unrelated reason. `node()` now rejects a script containing a double quote, and the early-stop test carries a **positive control** proving the same command *does* create its marker file when allowed to run.

**4. Guards verified red, not assumed.**

- **AD-3 boundary scan (Task 5).** A probe containing `x as DeclaredCommand` was planted in `src/pipeline/`; `tests/unit/config/boundary-scan.test.ts` failed with the named `as-assertion at line 2` in `src/pipeline/__probe-boundary.ts`. Coverage of `src/pipeline/**` is confirmed; the probe was removed and the scan is green. The scan needed no edit — its owner is story 1.3.
- **No-orphans assertion.** Verified red with a planted survivor; it reports the leaking pgids by name. It additionally asserts that at least one process group was *recorded*, because "no survivors" would otherwise be true for the wrong reason if `onProcessGroup` ever stopped reaching the runner. The detector itself (`groupAlive`) is tested against a group the suite creates and kills, since one that always returned `false` would report a clean run no matter how many processes were left behind.

**Harness interaction, worked around rather than fixed (not my story).** The agent harness's secret scanner refuses any file write containing an `sk-…`-shaped literal. That refusal is correct — this project's own rule is that nothing credential-shaped may exist in the repository. The spec nonetheless requires seeding `ANTHROPIC_API_KEY=sk-ant-example` into gate output. Resolved by assembling the token at run time in `tests/unit/pipeline/stages/gates.secrets.ts`, with the reasoning in that file's header: the string reaching the gate is exactly the shape a real leak would take, so the redaction under test faces the real pattern while nothing credential-shaped is stored on disk. No assertion is weakened.

### Completion Notes List

- **The classification table is the story.** `completed`+0 ⇒ `pass`; `completed`+non-zero ⇒ `fail` ⇒ **product-negative stage result** (never thrown); `not-found` / `spawn-failed` / `timed-out` ⇒ **`InfraError` thrown, and no `GateResult` at all**. `switch` is exhaustive over `ProcessOutcome` with a `never` binding, so a fifth arm cannot silently become "gate passed".
- **A timeout is InfraError (exit 3), not FAIL** — my decision, stated in the module header and pinned at both stage and pipeline level. A gate that hung says nothing about whether the branch is mergeable; exit 1 would assert defects on no evidence and route repair automation at a build that may be fine. Story 3.2's port classifies `timed-out` without verdicting it precisely so this call site owns the choice; 3.3 and 3.7 agreed independently.
- **`gateFailed` carries the gate id string**, following the merged `src/domain/run-outcome.ts`. ADR-003's prose says `gateFailed: true`; the code is the contract and the ADR wording is the stale half (carried action item A3). Three agents reached this independently from merged source. **This remains an unresolved divergence in a finalized planning artifact and is flagged for the owner** — a story branch does not edit `docs/adr/`.
- **`tests/unit/pipeline/stages/gates-pipeline.test.ts` drives the real stage through the real `runPipeline`.** Story 3.3's own gate-failure test substitutes a hand-written fake gates stage, so the real one had never met the real state machine — the seam between two agents' code, which is exactly the seam neither agent's unit tests cover. Written in direct response to 3.3's request that consumers assert the properties they depend on. It confirms: a failing gate ⇒ `{verdict:'FAIL', gateFailed:'lint'}` with the `gates` stage `failed` (not `error`), aggregate/persist/teardown reached, `services`/`data`/`probes` skipped; an unstartable gate ⇒ `{infraError:'infra'}` with **no verdict at all** and an empty `gates` array.
- **Evidence.** One file per stream per executed gate, `evidence/gate-<NN>[-<slug>].{stdout,stderr}.txt`. Two files rather than one because 3.3's review found a single shared `fullPath` made both truncation markers claim their own content lived in the same file. The combined-file option 3.3 left open was declined for the same reason: interleaving reintroduces the ambiguity one layer down, where the pointer is valid but the artifact is no longer separable. Nothing is written for an empty stream or a skipped gate.
- **The filename is derived, and total.** Gate ids are only `nonEmptyString` in the merged schema — no charset and no length constraint — so an id containing `..` would trip `RunStore`'s containment rule and an over-long one would raise `ENAMETOOLONG`. **Both mean exit 3 for a schema-valid config**: infrastructure blamed for something that is not infrastructure, which is the exact failure class AC3 exists to prevent, arriving from the side nobody was watching. Slug: unsafe characters substituted, dot runs collapsed so `..` cannot appear anywhere, edges trimmed, truncated to 64 characters, segment dropped entirely when it normalizes to nothing. The zero-padded declaration index keeps names unique after slugging *and* after truncation, and makes a run directory sort in execution order. `RunStore`'s containment rule is unchanged and remains the guarantee that escape is impossible — this only ensures the call sites never need it to fire. Agreed in writing with 3.2 and 3.5; the length case was 3.5's catch.
- **A gate that could not start still contributes `command` evidence when it printed anything**, because 3.2's runner returns the child's captured output on a timeout. Deliberately `command` and not `gate`: `GateEvidence` carries a `GateStatus`, and a gate that could not be judged has none of `pass`/`fail`/`skipped` truthfully available. Inventing one would put a wrong value in a field aggregation reads.
- **AD-3.** This is the first module in the product that executes a project-declared command; the module header says so and says what makes it safe. The command reaches `ProcessRunner` as a binary plus an argv array with no shell. Nothing mints, casts, or imports the brand — only `commandText()`, the sanctioned read direction. Shell syntax (`a && b`, `FOO=bar cmd`) does not run as written, which is not a regression: doctor already reports such a command's first token as unresolvable, so **doctor and the gate runner agree**, and that agreement is pinned by a property test rather than asserted in a comment.
- **AD-8.** The stage never imports `RunStore` and never constructs a path under the run directory — the string `.specwitness/runs` does not appear in `src/pipeline/` at all, so the grep-level rule holds by construction. Full output goes through an injected writer with the run id bound at composition, so the stage cannot address another run's directory even by mistake.
- **`ChildEnvironment` is `{inherit: true}` and names no variables**, so `tests/unit/doctor/credential-boundary.test.ts` needs no extension — and it scans only `src/cli/doctor/**` plus the doctor command, verified rather than assumed. FR-15's withholding is for provider invocations (AD-4), not for a project building itself.
- **An unwired assembly says so.** `createUnwiredGatesStage` reports "no gate runner was wired into this run" rather than reusing the "not implemented yet" placeholder, which stopped being true. A run in which nothing was checked must never read like one in which everything passed. Story 3.7 asserts that string appears nowhere in a wired run.
- **`src/pipeline/stages/index.ts` gained an optional `gates?: GatesStageDeps`** — the additive extension point story 3.3 designed and named 3.4 in. Stories 3.1 and 3.5 extend the same interface; whoever merges last takes a small rebase there.
- **Not done, deliberately:** `setup.install` (not in these ACs — the placeholder is untouched); a config-declared per-gate timeout (`gateSchema` has no timeout key, and adding one is a change to a schema this story does not own — named as a follow-up); Golden Corpus fixtures (Epic 6 — inline fixtures only, and the PR body says so).
