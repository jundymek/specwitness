## Story

As a cost-conscious operator,
I want configured gates to run in order with captured evidence and early stop,
so that a broken branch fails fast before any AI/browser spend (FR-20, FR-28 partial; ADR-003).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** ordered gates in config (e.g. install, lint, typecheck, unit, build)
   **When** all pass
   **Then** each gate's duration and truncated output land as gate evidence and the pipeline proceeds.
2. **Given** a failing gate
   **When** it exits non-zero
   **Then** the run ends with Verdict FAIL + `gateFailed: <id>`, remaining gates and all criteria reported `skipped`, the gate's stdout/stderr stored as evidence (bounded inline, full in run dir), exit code 1 (ADR-003 semantics; Golden Corpus fixture 7).
3. **Given** a gate command that cannot start (missing binary)
   **When** execution is attempted
   **Then** the outcome is InfraError (exit 3), not FAIL (classification test).

Clarifications (detail only, no weakening):

- **AC2 and AC3 together are the product promise of this epic, and each needs its own test that can actually produce the state.** A gate that *runs and exits non-zero* is a product FAIL (exit 1) — the branch demonstrably does not build. A gate that *cannot start at all* is infrastructure (exit 3) — SpecWitness could not reach a conclusion. The merged `ProcessRunner` already hands you exactly this distinction as a closed `ProcessOutcome`:
  - `completed` with a non-zero `exitCode` ⇒ **gate `fail`** ⇒ FAIL + `gateFailed`
  - `not-found` (binary missing) ⇒ **InfraError** — `'infra'` classification, exit 3
  - `spawn-failed` (e.g. an invalid `cwd`) ⇒ **InfraError**, exit 3
  - `timed-out` ⇒ **your decision, stated explicitly** (see below)
  Map every arm of that union with a `never` exhaustiveness check, so a future `ProcessOutcome` value cannot silently fall through to "gate passed". **This is the mapping the whole exit-code contract rests on.**
- **AC3's `not-found` distinction has a merged, hard-won subtlety — do not re-derive it.** Under execa 10 with `reject: false` a missing binary **resolves** rather than throwing, and an **invalid `cwd` raises the identical ENOENT**. `src/infra/process-runner.ts` already resolves this by asking the filesystem whether `cwd` is a directory rather than sniffing execa's message. You consume `ProcessOutcome`; you do not re-classify ENOENT. (Epic 2 retro learning 4: a first fix made this *worse* — a vague wrong answer became a confident one, telling operators to install a `git` they already had.)
- **A gate timeout: decide, state it, test it.** Recommendation: **InfraError**, not FAIL. A gate that hung tells you nothing about whether the branch is mergeable — SpecWitness failed to reach a conclusion, which is exactly what exit 3 means, and exit 1 would tell the harness "this branch has defects" on no evidence. Whatever you choose, put the reasoning in the module header and pin it with a test. Note this is *your* decision to make: `src/domain/process-runner.ts` deliberately classifies the outcome without verdicting it, and story 3.2's spec says so explicitly.
- **AC2 "remaining gates and all criteria reported `skipped`"** — `skipped` is the merged `GateStatus`/`CriterionStatus` value and is documented as *inert*. Produce a `GateResult {gateId, status: 'skipped'}` for every gate after the failing one, in declaration order, so the report shows what did not run. Do not omit them: a missing gate and a skipped gate look identical in a report, and only one of them is true.
- **AC2 does NOT re-implement aggregation.** `aggregate(gates, criteria)` in `src/domain/verdict.ts` (merged, with a property suite) already returns `{verdict: 'FAIL', gateFailed: <failing gate's id>}` when any gate has `status: 'fail'`. Your stage produces `GateResult[]`; pamela's aggregate stage calls `aggregate`. **You never construct a `RunOutcome` and you never touch an exit code.**
- **AC2 `gateFailed` carries the gate ID as a string, not a boolean.** `ADR-003`'s prose says `gateFailed: true`; the merged `src/domain/run-outcome.ts` implements `gateFailed?: string` carrying the failing gate's id, because the presence *is* the boolean signal and the id routes repair automation to "fix the build". **Follow the code.** (This is carried action item A3 — the ADR wording is the thing that is stale, not the implementation.)
- **AC1/AC2 evidence is produced through pamela's constructors, never hand-built.** `domain/evidence.ts` (3.3) owns the typed `gate`/`command` evidence and applies **redaction at capture** (AD-10). You call the constructor; you do not redact, and **3.6's renderers never re-redact**. Bounded inline output plus the full file in the run directory, with a truncation marker pointing at it (Q49). The cap and the marker's shape are pamela's to define and publish; use them.
- **Full gate output goes into the run directory through `RunStore`, which is the sole writer under `.specwitness/runs/`** (AD-8, enforced as a grep-level rule: outside `src/infra/run-store.ts` no module may construct a path under `.specwitness/runs`). **Check what bob (3.2) merged before you write anything** — he adds manifest lifecycle methods to that file in wave A, and rambo (3.5) adds the `result.json` finalize in your wave. If RunStore has no method for writing an evidence file when you get there, that is a message to rambo and a coordination point, not a reason to write the file yourself.
- **AC1 "gates run in order" is config declaration order**, and the merged schema guarantees it: `gates` is `z.array(gateSchema)` (ordered) with **cross-field uniqueness on `id`** enforced at load time. So you may rely on ids being unique and the order being meaningful — and you must **not** re-validate either.
- **Early stop is the point of the story.** FR-20: a failing gate stops the pipeline *before any Provider or browser cost*. Assert it mechanically: after a gate fails, no later stage executed and no further command was spawned.
- **Gates execute in the worktree**, not in the source repo — the cwd is 3.1's temp worktree path, handed to you. Nothing is written into the project working tree (AD-8).

### Failure modes (the ones that would matter in production)

- **A missing binary reported as FAIL.** The single most damaging bug available in this story: a mergeable branch blocked, or a developer sent hunting a defect that does not exist. Exit 3 says "fix your environment and rerun"; exit 1 says "your code is broken". They are not interchangeable.
- **A gate that cannot start reported as PASS.** The mirror image, and worse: `ProcessOutcome` has four arms, and a `switch` without a `never` check that only handles `completed` would treat a `not-found` gate as "no failure seen". Exhaustiveness is not a style preference here.
- **A thrown gate failure.** Turns exit 1 into exit 3 and tells the harness to retry a branch that will never build.
- **Missing `skipped` entries.** A report that omits the gates after the failure is indistinguishable from one where they passed.
- **Unbounded gate output in the terminal.** `npm test` output can be megabytes; the caller is often an agent context (NFR-8). Bounded inline plus a pointer is the requirement, not a nicety.
- **A gate spawned in the source repo instead of the worktree.** Silently verifies the wrong tree and may write into the operator's working directory.

### Security

- **You are the first module in the product to execute a project-declared command.** The AD-3 boundary has been theoretical until this story; from here it is load-bearing at runtime. What makes it safe: `DeclaredCommand`s come only from `.specwitness/config.yaml`, they reach `ProcessRunner` as a binary plus an argv array, and there is no `shell` option anywhere in the port. Do not add one, do not build a command line, do not pass a gate's `run` string through `sh -c`.
- **Never mint or cast a `DeclaredCommand`.** The brand's symbol is unexported; the only remaining route is a deliberate cast, which the AST scan rejects mechanically.
- **NFR-1.** Nothing reads `~/.claude/`, `~/.codex/` or any credential store. If your child-environment construction names variables, expect `tests/unit/doctor/credential-boundary.test.ts`'s exact-list assertion to need a deliberate, commented extension — **never relax it to `toContain`**.
- **Gate output is untrusted text** and may contain secrets from the project's own environment. That is why capture-time redaction exists and why your evidence path must go through pamela's constructors rather than around them.
