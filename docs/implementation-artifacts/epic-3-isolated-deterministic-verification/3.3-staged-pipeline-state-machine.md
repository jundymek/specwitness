## Story

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** the stage sequence (resolve → integrity → worktree → setup → gates → services → data → probes → aggregate → persist → teardown)
   **When** any stage fails
   **Then** later stages are skipped (teardown always runs), the failure is classified through the AD-7 hierarchy, and the stage timeline (per-stage status + duration) appears in the RunResult.
2. **Given** the integrity stage
   **When** the contract fingerprint mismatches
   **Then** the run ends as IntegrityError (exit 3) with zero commands executed in the worktree (FR-9 runtime).
3. **Given** stage results
   **When** unit tests exercise the state machine with faked stages
   **Then** every early-stop path and the always-teardown guarantee are covered without real I/O.

Clarifications (detail only, no weakening):

- **AC1 the eleven stage names are frozen by the spine's Structural Seed and by this AC.** Declare them once as a `const` tuple in `src/domain/`, in exactly this order, and derive `StageName` from it. Renaming, reordering, adding or dropping one is an ADR — four other stories key their stage entries off these strings.
- **AC1 "any stage fails" is a STAGE RESULT, not a thrown exception, for gate failure specifically.** AD-6 is explicit: `GateFailure` is a stage result and the **aggregate stage is the only converter** from stage results to a `RunOutcome`. Your runner must therefore distinguish two different kinds of "not ok":
  - a stage that produced a **product-relevant negative outcome** (gates failed) — the pipeline stops early, but the run proceeds through aggregate → persist → teardown and ends with a `Verdict`;
  - a stage that hit an **infrastructure problem** (a thrown AD-7 error) — the run cannot reach a product conclusion and ends with an `{infraError}` outcome.
  Both skip the intervening stages; both still run teardown. Conflating them is the defect this epic exists to prevent, and the type system should make the distinction unavoidable rather than a convention.
- **AC1 "teardown always runs"** means: after any early stop, after any thrown error, and after an error thrown *by teardown itself*. A teardown that throws must not replace the run's outcome with its own failure — record it, classify it, and keep the outcome that was already decided (a run that FAILed on a gate and then failed to remove a worktree is still a FAIL; a run that PASSed and then leaked a worktree is a PASS with a recorded teardown problem, and 3.2's `clean` is the remedy). State your choice in the module header and test it.
- **AC1 "the failure is classified through the AD-7 hierarchy":** call the merged classification. `exitCodeForError` in `src/cli/exit.ts` maps thrown errors, and it already fails closed (anything unrecognised → infra). Your pipeline maps a **thrown AD-7 error** to an `InfraErrorClassification` from `src/domain/run-outcome.ts` — `ConfigError → 'config'`, `IngestError → 'ingest'`, `IntegrityError → 'integrity'`, `ProviderError → 'provider'`, `InfraError → 'infra'`, **anything else → `'infra'` (fail closed)**. `UsageError` is deliberately absent from that enum: it is raised at the CLI edge before a run exists. If one reaches your runner, that is a programming error — let it propagate rather than inventing a classification for it, and say so in a comment.
- **AC1 stage timeline entries carry `durationMs` from the injected `Clock`** (AD-9), never `Date.now()`. `src/domain/ports.ts` is merged and its header says Epic 3 brings its ports here. `FixedClock` in `tests/fakes/ports.ts` makes durations exact integers rather than "greater than zero", which is the assertion that passes even when the clock is read once and reused.
- **AC2 "zero commands executed in the worktree" is an assertion you own, mechanically.** Inject a `ProcessRunner` that throws on any call, drive an integrity-mismatch run, and assert it was never reached. Do not assert this in prose. Note the ordering this AC pins: **integrity precedes worktree**, so a tampered contract costs nothing — not a worktree, not a spawn.
- **AC2 uses the merged guard, it does not re-implement it.** `assertVerifiableContract` in `src/authoring/verifiable.ts` (story 2.6, merged) already refuses absent / never-frozen / tampered contracts with three distinct hints, and `contractState` in `src/schemas/contract.ts` is the single integrity comparison. Your integrity stage **calls** them. Two implementations of "does this content match its fingerprint" would eventually disagree, and the disagreement would surface as a contract that verifies in one code path and reports tampering in another.
- **AC3 "without real I/O"** is a property of your whole suite, not of one test: `src/pipeline/**` and `src/domain/**` unit tests spawn **zero** subprocesses, touch **zero** files, and read neither the wall clock nor randomness. Enforce it — inject a `ProcessRunner` that throws (`forbiddenProcessRunner` already exists in `tests/fakes/agent-provider.ts`, merged by story 2.3 — reuse it rather than writing a second one).
- **`domain/evidence.ts` is yours** (see Project Structure Notes). 3.4 needs typed `gate`/`command` evidence to produce; 3.6 needs a bounded thing to render. Shipping it in wave A is what stops those two stories inventing two evidence shapes in parallel branches.
- **`domain/criterion-result.ts` is yours too, as AD-13's seam** — the `SurfaceExecutor` and `ProbeAttempt` types plus the single derivation function. Epic 4/5 fill it; you land it. Keep it minimal: for a gates-only run, every criterion is `skipped`, so the function must be *correct* for the trivial case and *shaped* for the real one.

### Failure modes (the ones that would matter in production)

- **A thrown gate failure.** If the gates stage throws instead of returning a stage result, gate failure becomes exit 3 rather than exit 1 — the harness reads "environment broken, retry" for a branch that simply does not build, and a broken branch merges after a retry. The type system should make this unrepresentable.
- **A teardown that swallows the outcome.** A teardown error overwriting a decided verdict turns a legitimate FAIL into an infra error, and the branch looks retryable.
- **A `default:` that silently PASSes.** Any switch over `CriterionStatus`, `Verdict` or `StageName` gets a `never` exhaustiveness check — `verdict.ts` and `exit.ts` both show the pattern. Fail closed, never fall through.
- **A `RunResult` field that a renderer computes instead.** Watch for 3.6 needing counts, durations or "which gate failed" — all of those are facts, and facts live in the model.

### Follow-up after merge (2026-09-01)

Two owner-directed changes to `src/domain/evidence.ts`, in one review cycle.

**The redaction path was quadratic** in the length of an unbroken run of identifier
characters - 24/87/345/1472 ms at 4/8/16/32 KB, quadrupling per doubling, roughly half an
hour extrapolated to 1 MB. Reported by story 3.6's agent with measurements, confirmed
independently by story 3.4's agent on a different fixture generator, reproduced here
before anything was changed. Reachable in production rather than only in a fixture:
ordinary logs stay fast because whitespace terminates the backtracking, but a bundler
emits one-line base64, and `verify` would appear to hang inside capture - in the stage
whose whole purpose is failing fast, with no output, because the hang is inside the code
that produces output.

Fixed with a `{0,255}` bound on the name (linear; nothing changes about what is matched).
**A lookbehind was tried first and rejected**: asymptotically better, but `-` is a name
character, so it stopped `psql --password=hunter2` matching at all and the seeded-secret
test went red immediately. Speed bought by scanning less is not a fix. `SENSITIVE_HEADER_LINE`
was measured on the same input and is unaffected - the half neither reporter had checked.

**`GateEvidence.displayCommand`** added, required and redacted, at story 3.4's request and
the owner's approval: without it a run directory is not a self-contained record, since a
reader has a gate id plus 8 KB of output and must recover the config as it was at that
revision to learn what ran.

**That field cost three redaction leaks before it was right, and they are the most useful
thing in this record.** Because a declared command is a single line, a header value could
no longer be redacted to end of line - that swallows the command's URL. Every regex written
for the new extent leaked, each in the shape story 3.6's agent named exactly: output
containing `[REDACTED]` with the secret still beside it, which survives review in a way a
raw leak does not.

  - stopping at the next quote leaked `Cookie: session="secret"; HttpOnly`;
  - requiring a quoted unit leaked a truncated `Authorization: "Bearer secret`;
  - the `{0,255}` bound, applied to a QUOTED name, leaked `"<300 chars>_API_KEY":"secret"`
    - a regression the performance fix itself introduced;
  - consuming the value to end of line meant `String.replace` resumed past it, so every
    sensitive header AFTER the first on a line was never examined - a curl smoke gate with
    an auth header and an api-key header redacted only one. Found by re-reading the code,
    prompted by story 3.5's agent reporting that he had VERIFIED an assumption rather than
    taking my word for it;
  - and once it was a scan, an ESCAPED quote ended the value early:
    `curl -H "Authorization: prefix\"Bearer SECRET"` treated the `\"` as the argument's
    close. The closing-quote search now skips escaped delimiters and the quote tracker
    carries an escape flag across calls.

The cause the first three share is that every pattern APPROXIMATED THE QUESTION. "Is there a
quote in the value" is not the question; "was this header written inside a quoted shell
argument" is, and the surrounding text answers it exactly. The fourth settled the mechanism:
a regex `replace` cannot skip a different amount than it matched, so the extent has to be
decided outside the pattern. The pattern now matches only `name:` and a hand-written scan
consumes what follows - the whole value when no quote is open (a quote inside a header value
is an ordinary character), up to the closing quote when the header sits inside a quoted shell
argument, and the whole line when that quote is never closed. Line and quote state are
tracked incrementally rather than searched backwards per match, keeping k headers on a line
of length L at O(L) rather than O(k*L) - this file has already paid the quadratic tax once.
