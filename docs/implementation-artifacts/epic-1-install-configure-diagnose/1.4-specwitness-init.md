## Story

As a developer adopting SpecWitness,
I want `specwitness init` to scaffold `.specwitness/` with a commented config skeleton,
so that onboarding is one command in any Git repository (FR-1).

## Goal & Context

First real command: one-command onboarding in ANY repository — explicitly including non-Node stacks (FR-4; the target repo needs no package.json). Init scaffolds `.specwitness/` (config skeleton + `contracts/`, `plans/`, `runs/` directories), writes the git-ignore entries for local-only data (questions doc Q11), never destroys existing configuration, and refuses politely outside a Git repository. It realizes the first half of UJ-4 (install → init → doctor).

Wave C story: runs in parallel with 1.5 (doctor) and 1.6 (run storage) on top of merged waves A+B. **You own `src/cli/commands/init.ts` (replacing the 1.1 stub), the `templates/` content, and any new scaffold helper file; do not touch `doctor.ts`, `report.ts`, `src/infra/run-store*`, or anything 1.5/1.6 own this wave.**

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** a Git repository without SpecWitness (any stack, no Node project required)
   **When** I run `specwitness init`
   **Then** `.specwitness/` is created with `config.yaml` skeleton (commented examples for gates/services/observations/ai) and `contracts/`, `plans/`, `runs/` directories, and the command reports what was created.
2. **Given** an existing `.specwitness/config.yaml`
   **When** I run `specwitness init` again
   **Then** nothing is overwritten without explicit `--force`, and the command says so with exit 0.
3. **Given** a directory that is not a Git repository
   **When** I run `specwitness init`
   **Then** it refuses with a named error and `HINT:` (exit 3).

Clarifications (detail only, no weakening):

- AC1: also write `.specwitness/.gitignore` containing `runs/` and `scorecard.jsonl` — this satisfies Q11 ("committed: config/contracts/plans; local-only: runs/scorecard; init writes the ignore entries") without mutating the project's own root `.gitignore`. Report it among created items.
- AC1 "reports what was created": one line per created path on stdout; ISO-8601 UTC timestamps if any are printed.
- AC2: `--force` overwrites ONLY `config.yaml` (never deletes `contracts/`/`plans/`/`runs/` contents); re-run without `--force` still creates any MISSING directories/files (idempotent completion) and clearly says config was left untouched; exit 0.
- AC3: "named error" = message identifying the checked directory and that it is not a Git repository; classify as `InfraError` (environment precondition — NOT `UsageError`: the invocation is well-formed; epics pins exit 3). `HINT: run inside a Git repository or 'git init' first.`
- Prompt-free: init in V0 never prompts (agent-callable; the conventions' "init confirm" TTY allowance is unused — `--force` is the only overwrite path). No TTY reads.

## Dev Notes

### Exact scope

- `src/cli/commands/init.ts` (stub replacement), `src/infra/scaffold.ts` (optional helper), `templates/config.yaml`, tests.

### Out of scope (do NOT build)

- Interactive prompts of any kind. Doctor checks (1.5). Run-id/manifest logic for `runs/` (1.6 owns run storage; init only creates the empty directory). Any git subprocess usage (detection is filesystem-only). Project root resolution flags (`--root` is Epic 3); init operates on CWD.
- Do not append to the project's root `.gitignore` (the nested `.specwitness/.gitignore` is the chosen mechanism).

### Dependencies & upstream contracts

- Requires merged: 1.1 (CLI skeleton, stub file to replace, `InfraError`, exit table), 1.3 (config schema — the template must validate against it).
- Binding: FR-1 (+ testable consequences), FR-4 (no Node required in target), Q11 (git vs local artifacts), AD-8 spirit (SpecWitness writes only into `.specwitness/`), Consistency Conventions (prompt-free agent-callable commands, `ERROR:`/`HINT:` stderr, ISO-8601 UTC).

### Architecture compliance

- AD-1: command module lives in `cli/` (edge — may import config/infra); scaffold helper in `infra/` may use `fs`. Nothing here touches `src/domain` beyond importing error classes.
- All filesystem writes are confined to `.specwitness/` inside the target project — nothing else in the user's repo is modified.

### Testing requirements

- Unit: scaffold function (created/skipped/force matrix) against tmp dirs; template-validates-against-schema test.
- Integration: built-CLI spawns per Task 4 (this story's behavior is primarily CLI-observable; integration coverage is the priority). Hermetic — tmp dirs only.

### Integration expectations

- `doctor` (1.5) will validate the config your template writes — a fresh `init` followed by `doctor` should produce warnings at most, not required-check failures, for the config-validity check (placeholder `baseBranch` may legitimately warn/fail the base-branch-exists check; that's doctor's concern, not yours).
- Epic 2 commits `contracts/`/`plans/` content into these directories; Epic 3+ writes runs. Directory names are contract — exactly `contracts`, `plans`, `runs`.

### Failure modes to consider

- Running from a subdirectory of the repo: V0 scaffolds at CWD — document in help text that init should run at the project root (refuse-to-guess house rule; no upward search).
- Partially existing layout (dirs exist, config missing or vice versa) — complete the missing pieces, never clobber.
- Template file missing from a broken install → `InfraError` with a reinstall hint (don't crash with a raw ENOENT).
- Read-only filesystem / permission errors → `InfraError` with the failing path.

### Security

- Init writes files with normal permissions inside the target repo only. No secrets, no env reads, no subprocesses, no network. Blanket NFR-1 applies.

### Project Structure Notes

- Story branch `story/1.4-specwitness-init`; Conventional Commits (e.g. `feat(cli): implement specwitness init scaffolding`).

### Debug Log References

- **Codex review found two real defects, both fixed and pinned by tests watched
  failing first.**
  1. *YAML coercion of the branch name.* Git permits branches called `true`,
     `false`, `null`, `123`, `1.0`. Interpolating one raw produced a non-string
     YAML scalar, so the generated skeleton failed `loadConfig` on the very
     first `doctor` run — in a repository whose only sin was its branch name.
     Reverting the fix reproduced it exactly: `expected true to be 'true'`,
     `expected null to be 'null'`, `expected 123 to be '123'`,
     `expected 1 to be '1.0'` — 6 failed / 30 passed. Now serialized with
     `yaml.stringify` (quotes only when required, so `main`/`master` stay
     unquoted) and substituted with a replacement *function*, since `$&`,
     `` $` `` and `$'` are special in a string replacement and a branch name may
     contain `$`.
  2. *Wrong filesystem entry type accepted as success.* An existing
     `.specwitness/contracts` that was a regular **file** was reported as
     "already there" and `init` exited **0**, having produced a layout later
     commands cannot write into — an infra failure disguised as success, which
     is the one thing this product must never do. Entry types are now checked
     for the project dir, the three subdirectories, `config.yaml` and
     `.gitignore`; a mismatch raises `InfraError` naming the path with a remedy.

- **A shared-file defect surfaced by this story, fixed here at the file author's
  request.** `runCli` in `tests/integration/cli.test.ts` hardcoded
  `cwd: REPO_ROOT`. Harmless while every command was a stub that touched
  nothing; wrong the moment one did real work — `init` scaffolded a live
  `.specwitness/` into the SpecWitness repository on every `pnpm test`. I
  initially judged this cosmetic because the files were untracked; story 1.1's
  author corrected me with evidence (`git add -A --dry-run` stages
  `.specwitness/config.yaml`, since only `runs/` and `scorecard.jsonl` are
  ignored — in a *target* project config.yaml, contracts/ and plans/ are meant
  to be committed). `runCli` now defaults to a throwaway directory; callers
  needing the repository pass `cwd` explicitly.

- **Template path resolution could not be a fixed relative path.** tsup bundles
  to `dist/cli.js` (`templates/` one level up) while vitest runs the TypeScript
  sources (`src/infra/scaffold.ts`, two levels up). Resolution walks up from
  `import.meta.url` instead. Verified against a real packed tarball: pack →
  `npm install` the tarball → run the installed binary in a fresh
  `git init --initial-branch=main` repo → correct scaffold, `baseBranch: main`,
  exit 0; second run idempotent, exit 0.

- **One test of mine was vacuous and was replaced, not kept green.** A first
  attempt at "leaves the repository untouched when the config cannot be
  rendered" asserted nothing about the failure path it named. Replaced with a
  test that forces the failure and asserts no partial layout survives.

- **A second over-clever test was replaced rather than tuned.** "Uncomment the
  whole template and validate it" mostly exercised its own un-commenting regex —
  the template interleaves prose comments with commented-out YAML and no regex
  separates them reliably. Replaced by a hand-authored fully-configured fixture
  mirroring every example the template ships (project fixture culture: the
  expectation is authored, not generated), plus a guard test asserting the
  template still documents each key the fixture uses, so the duplication cannot
  silently drift.

- **Rebased four times** as 1.1, 1.2, 1.3 and 1.6 merged. The only conflict was
  `tests/integration/cli.test.ts`, twice — see Completion Notes.

- CI could not be used at all: see the CI note in Completion Notes.

### Completion Notes List

**Delivered**

- `specwitness init [--force]` (FR-1): scaffolds `.specwitness/` with a
  commented `config.yaml`, `contracts/`, `plans/`, `runs/` and a nested
  `.gitignore`; reports one line per created/replaced/skipped path on stdout;
  exit 0 on both the created and the nothing-overwritten path.
- Works in any repository including non-Node ones (FR-4) — covered by an
  integration case whose fixture has no `package.json` at all.
- Outside a Git repository: `InfraError` naming the checked directory, rendered
  as exactly one `ERROR:`/`HINT:` pair on stderr, **exit 3** (not `UsageError`
  /64: the invocation is well-formed, the environment is not ready).
- Prompt-free; no subprocess, no network, no environment reads.

**Deviations from the spec, each deliberate**

- **`project.baseBranch` is read from `.git/HEAD`, not hardcoded.** The spec
  says "placeholder"; a literal `master` is wrong for every `main` repository,
  and story 1.5's `base-branch-exists` check is REQUIRED and exits 3 when the
  branch does not resolve — so a bad placeholder would make UJ-4 red out of the
  box on most modern repositories. Proposed independently by the owners of 1.5
  and 1.3 before any code was written. Still filesystem-only: detached HEAD,
  unreadable HEAD, or an unclean `gitdir:` hop all fall back to `master`.
- **`package.json` was not modified**, though Task 1 mentions it. Story 1.1
  already shipped `files: ["dist", "templates"]` and `templates/.gitkeep`, so
  the requirement (templates ship in the package) was already satisfied — and
  was verified against a real packed tarball rather than assumed.
- **`tests/integration/cli.test.ts` was modified**, which is story 1.1's file.
  Two changes, both requested by its author after she had merged and could no
  longer make them herself: the `cwd` fix above, and converting the shared
  `it.each` stub arrays into one `it` per command. The arrays guaranteed that
  every wave-C story edited the same two lines; the per-command shape lets each
  story delete lines nobody else touches.

**Divergence from a planning artifact, flagged rather than silently followed**

- `architecture-questions.md` Q11 says the *project's* `.gitignore` excludes
  `.specwitness/runs/` and `.specwitness/scorecard.jsonl`. This story's AC1
  clarification instead mandates a nested `.specwitness/.gitignore` and
  explicitly forbids mutating the project's root `.gitignore`. Spec wins per
  `CLAUDE.md`, and it is also the better behaviour: it achieves Q11's outcome
  without editing a file the user owns (AD-8 spirit), and stays idempotent
  across re-runs and `--force`. Confirmed compatible by the owner of 1.6.

**AD-8 boundary**

- `init` creates `.specwitness/runs/` as an empty directory and writes nothing
  inside it; it never constructs a path *below* `runs/`. Confirmed with the
  owner of story 1.6 that this does not cross "RunStore is the sole writer under
  `.specwitness/runs/<run-id>/`" — that invariant governs the per-run subtree,
  and RunStore's own root creation is an idempotent recursive mkdir either way.

**Cross-story integration verified against merged code, not assumptions**

- The shipped template is loaded through story 1.3's real `loadConfig` in
  `tests/unit/template.test.ts`, importing only from `src/config/index.js` (deep
  imports into `src/config/` fail 1.3's boundary scan). Schema drift therefore
  fails this story's tests rather than a user's `init`.
- A hand-authored fully-configured fixture proves every commented example is
  valid too — including `services.<name>.ready`, which 1.3 made **required**
  mid-wave, and the kebab-case `ai.roles` keys.
- The skeleton declares **no** commands at all, so story 1.5's required
  `commands-resolvable` check has an empty scan set on a fresh `init`. This is
  asserted, not incidental: if a future story uncomments part of the skeleton,
  the test fails and forces a conversation with whoever owns doctor.

**Known limit, stated so UJ-4 is not oversold**

- `init` → `doctor` is green on a repository with at least one commit on its
  default branch. On a virgin `git init` with no commits, `refs/heads/<name>`
  does not exist, so `base-branch-exists` is correctly red no matter which
  placeholder is written — a diff cannot be verified against a branch with no
  commits. Story 1.5's author flags the same edge case from his side.

**CI (harness defect, not fixed here)**

- GitHub Actions is disabled repository-wide (`on: workflow_dispatch:` only):
  the account's Actions minutes are exhausted and the owner turned CI off rather
  than leave a meaningless red check on six PRs. Per the cohort rule that a
  harness defect outside the story stays unfixed, the workflow was neither
  re-enabled nor deleted. **There are no checks on this PR, and an absence of
  checks is not a pass.** The six workflow steps were run locally instead and
  their real output is in the PR body. Unverified: Linux, and Node at exactly
  22.12 (local runs are macOS on Node 22.20.0).
