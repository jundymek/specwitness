## Story

As a developer,
I want an installable `specwitness` CLI with command routing, house-style errors, and the single exit-code table,
so that every later feature ships inside a consistent, scriptable binary.

## Goal & Context

Bootstrap story for the whole product: it creates the npm package, build/test/CI toolchain, the commander-based CLI edge, the single exit-code table (`src/cli/exit.ts`), the AD-7 error-class seed, and the architecture guardrail (dependency-cruiser). Every other story in every epic merges into the structure this story establishes, so **structure and contracts matter more than feature count here**. This story runs ALONE (wave A of Epic 1); waves B (1.2, 1.3) and C (1.4, 1.5, 1.6) build on its merged result. Your PR must leave the repository fully coherent: installable, buildable, tested, CI-green (founder brief §64).

SpecWitness itself is an independent verification gate for agentic development — a local-first CLI (`specwitness`) that later gains `init`, `doctor`, `contract`, `plan`, `verify`, `report`, `clean`, `scorecard` commands. This story ships the skeleton those commands plug into.

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** the package is built and linked
   **When** I run `specwitness --help` or an unknown command/flag
   **Then** help renders, and the unknown invocation prints `ERROR: <what>` plus `HINT: <how to fix>` on stderr and exits 64
   **And** no code path outside `cli/exit.ts` defines a process exit code (verified by test).
2. **Given** any command throws an unclassified exception
   **When** the CLI terminates
   **Then** it exits 3 (infrastructure), never 0/1/2 (fail closed per AD-7).
3. **Given** the repo's CI
   **When** the build runs
   **Then** tsup produces an executable `bin` entry, vitest runs green, and the `engines` field enforces Node >=22.12 (Node 20 is EOL and commander 15/execa 10/dependency-cruiser 18 all require >=22.12 — spine review finding).
4. **Given** the pinned dependency majors (commander 15, execa 10, zod 4)
   **When** this story's dev notes are written
   **Then** a short breaking-change review against the previous majors (commander 14→15, execa 9→10) is recorded, per the spine version-reality review.

### Dependencies & upstream contracts

- No story dependencies (greenfield, wave A). Binding contracts: ADR-002 (exit codes 0/1/2/3/64, single table), AD-1 (dependency direction), AD-6/AD-7 (error hierarchy semantics; gate failure is NOT an error class — do not add one), spine Stack table (exact versions), spine Consistency Conventions (kebab-case files, `ERROR:`/`HINT:` stderr house style, no TTY assumptions), FR-27 partial.
- Node >=22.12 floor is a reviewed decision — do not lower it.

### Architecture compliance

- AD-1: `src/domain/errors.ts` imports nothing side-effectful. The depcruise rules you write here are the enforcement all later stories inherit — get the layer map right (see spine "Design Paradigm" layer list).
- AD-7 fail-closed: unclassified exception → exit 3, never 0/1/2. The global handler is the only place that catches broadly.
- Conventions: all commands prompt-free (no TTY reads anywhere in this story); stdout reserved for command output, human diagnostics on stderr.

### Testing requirements

- Unit: exit table mapping (every class, unknown error, constants match ADR-002 exactly).
- Integration: spawn the **built** binary (via execa) for help/unknown/stub paths asserting exit codes and stderr shape. No TTY. Keep tests hermetic (no network).
- The `process.exit`-location scan test.

### Integration expectations

- Stories 1.2–1.6 import `src/domain/errors.ts` and `src/cli/exit.ts` as-is; changing their public shape after this story requires cross-story coordination — design the signatures deliberately (errors carry optional `hint`; `exitCodeForError` accepts `unknown`).
- Epic exit criteria this story serves: `npx specwitness --help` works from a packed tarball; exit codes 3/64 demonstrated.

### Failure modes to consider

- Commander swallowing errors or calling `process.exit` itself (must use `exitOverride` + route through the table).
- ESM/bin pitfalls: shebang preserved by tsup, `dist/cli.js` executable bit, package `files` excluding `src`/tests from the tarball.
- Double-printing errors (commander writes its own message AND ours) — suppress commander's default output (`configureOutput`) so stderr carries exactly one `ERROR:`/`HINT:` pair.

### Security

- NFR-1 (blanket rule for the whole codebase, starts now): no code path may ever read `~/.claude/`, `~/.codex/`, or any credential store. Nothing in this story should touch the filesystem outside the repo/build dirs at runtime.

### Debug Log References

Four findings that changed the implementation, each caught by running something
rather than by reading docs:

1. **pnpm 11 ignores the `pnpm` field in `package.json`.** The first
   `pnpm install` ended in `ERR_PNPM_IGNORED_BUILDS: esbuild@0.27.7`, which
   leaves tsup unable to build. Adding `pnpm.onlyBuiltDependencies` to
   `package.json` produced `[WARN] The "pnpm" field in package.json is no
   longer read by pnpm`. pnpm 11 reads settings from `pnpm-workspace.yaml`, and
   `onlyBuiltDependencies` has been replaced by `allowBuilds`. Resolved with
   `allowBuilds: {esbuild: true}` in `pnpm-workspace.yaml`.

2. **The AD-1 zod allowlist did not match under pnpm.** `schemas-npm-allowlist`
   was first written as `pathNot: '^node_modules/zod/'` and rejected a
   legitimate zod import, because pnpm resolves through its content-addressable
   store (`node_modules/.pnpm/zod@4.5.4/node_modules/zod/…`). Changed to the
   unanchored substring `node_modules/zod/`, which matches both the pnpm and
   the flat npm layout.

3. **`adapters-core-only` initially forbade an adapter importing its own
   siblings**, which would have failed story 1.3's `src/config/load.ts` →
   `src/config/schema.ts`. Fixed with a `$1` back-reference to the adapter
   captured in `from`, so same-directory imports are allowed and cross-adapter
   imports are not.

4. **Both mechanical guardrails were verified by making them fail**, on the
   principle that a check which has never fired is not evidence:
   - The `process.exit` scan: a temporary `src/domain/__violation.ts`
     containing `process.exit(1)` produced
     `expected [ 'domain/__violation.ts' ] to deeply equal []`. File removed.
   - dependency-cruiser: six temporary modules (domain importing zod, domain
     importing `node:fs`, domain importing `src/cli`, schemas importing `yaml`,
     an adapter importing `src/cli`, an adapter importing another adapter)
     produced 9 errors across all five rules; a seventh module doing a legal
     sibling import was correctly **not** flagged. All removed; `src/` is back

### Completion Notes List

**All four acceptance criteria are met and mechanically verified.** Final state:
`pnpm lint`, `pnpm typecheck`, `pnpm test` (90 tests, 5 files), `pnpm build`
and `./scripts/pack-smoke.sh` all exit 0.

**AC1 — help, usage errors, single exit-code definition.** `--help` renders on
stdout and exits 0. Unknown command, unknown flag, unknown flag on a known
command, and bare invocation each exit 64 with exactly one `ERROR:` and one
`HINT:` line on stderr and nothing on stdout (asserted by counting the lines —
that count is what proves commander's own output was suppressed rather than
merely overwritten). Commander is configured with `.exitOverride()` so it never
calls `process.exit` itself, and `.configureOutput({writeErr, outputError})` so
it never prints its own message. The "no exit code outside `cli/exit.ts`" rule
is enforced by `tests/unit/exit-location.test.ts`, which scans `src/**` for
`process.exit(` / `process.exitCode`, asserts the only match is
`src/cli/exit.ts`, additionally asserts that file still *does* match (so the
scan cannot pass vacuously), and asserts it found more than five files to scan
at all.

**AC2 — fail closed.** `exitCodeForError(err: unknown)` maps `UsageError` → 64,
the other five AD-7 classes → 3, and anything unclassified (plain `Error`,
`TypeError`, a thrown string, a thrown object, `null`, `undefined`, a `Symbol`)
→ 3. A dedicated test asserts the result is never 0, 1 or 2 for unclassified
input, and a further test asserts the returned code is always a member of the
table. Subclasses classify by their parent (verified), which is what lets story
1.3 refine `ConfigError` without touching the table.

**AC3 — build, tests, engines, CI.** tsup emits `dist/cli.js` with a
`#!/usr/bin/env node` shebang and mode 0755 (an integration test asserts the
shebang, the executable bit, and `access(X_OK)` on the built file).
`engines.node` is `>=22.12`, with `.npmrc` `engine-strict=true` so the floor is
enforced at install rather than merely declared. CI runs on ubuntu-latest and
macos-latest at Node 22.12 — the floor itself, so a feature newer than the
declared minimum cannot creep in unnoticed — and executes install → typecheck →
depcruise → test → build → packed-tarball smoke.

**AC4 — breaking-change review** (verified against the shipped majors'
changelogs and the installed type definitions, not from memory):

*commander 14 → 15:*
- **Node floor raised to >=22.12.0** (for `require(esm)`) — independently
  confirms the story's Node decision; the spine's floor and commander's are the
  same number, so it is not negotiable downward.
- **The implementation migrated from CommonJS to ESM**, and the deprecated
  `commander/esm.mjs` export was removed. No impact: this package is
  `type: module` and imports commander as ESM already.
- **Negatable options changed**: only a lone `--no-*` option sets the default to
  `true`; the default is no longer implicitly set when both the positive and
  negative forms are defined. **No impact today** — this story defines no
  boolean option pairs — but stories 1.4 (`--force`) and 1.5 (`--json`) should
  know that a `--foo`/`--no-foo` pair no longer defaults to `true` implicitly.
- Error/exit handling itself was **not** changed in the major. `exitOverride()`,
  `CommanderError.exitCode`, and `configureOutput()` behave as in 14, which is
  what the exit routing here relies on. Verified empirically: `--help` and
  `--version` throw a `CommanderError` with `exitCode === 0` (output already
  written), while parse failures throw with a non-zero `exitCode` and a message
  prefixed `error: ` — the code strips that prefix before printing house style.

*execa 9 → 10:*
- **Node floor raised to >=22.** Consistent with the above.
- **The subprocess object is now a plain promise, not a `ChildProcess`
  augmented with promise methods.** Node-specific APIs (`.on()`, `.send()`,
  `.ref()`, `.unref()`) moved to `subprocess.nodeChildProcess`. **This is the
  item Epic 3 story 3.2 must plan around**: any code reaching for
  `subprocess.pid`, signal events, or IPC now goes through
  `.nodeChildProcess`.
- **`execaCommand()` / `execaCommandSync()` were removed** in favour of the
  template-string syntax. This is *helpful* for AD-3: there is no longer a
  first-class "run this command string" entry point, which is exactly the API
  the trusted-command boundary does not want to exist.
- **`stdio: [..., 'ipc']` was removed** in favour of `ipc: true`.
- **`input`/`inputFile` combined with inherited stdin now take precedence**
  instead of being ignored.
- Process-lifecycle options relevant to AD-8, read from execa 10.0.1's own type
  definitions: `cleanup` (default `true`, kill the subprocess when the parent
  exits), `detached` (default `false`), `killSignal` (default `'SIGTERM'`),
  `forceKillAfterDelay` (default `5000` ms, then SIGKILL, setting
  `error.isForcefullyTerminated`), `gracefulCancel` (default `false`), and
  **`killDescendants` (default `false`)** — which, per its documentation, "on
  Unix … spawns the subprocess in its own process group" and terminates
  descendants, best-effort. **`killDescendants: true` is the option AD-8's
  process-group requirement needs**; story 3.2 should build on it rather than
  hand-rolling `detached` + `process.kill(-pgid)`, and should note the
  documented caveat that descendants creating their own group or session are
  not terminated.

*zod 4:* adopted fresh, so there is no 3 → 4 migration burden — but every
schema in the codebase must target the zod 4 API from the start (`z.output`/
`z.input` inference, the reworked error customization, `z.strictObject` etc.).
zod is pinned as a runtime dependency here but **not imported by this story**;
the AD-1 rules deliberately allow it in `src/schemas/**` and forbid it in
`src/domain/**`.

**Deviations from the spec, all deliberate and recorded in `DECISIONS.md`:**

- `pnpm lint` is mapped to dependency-cruiser rather than a linter. The stack
  brief requires a `lint` script; the spine pins no linter and this spec forbids
  adding one. (1.1-D1)
- Exit is delivered with `process.exitCode`, not `process.exit()`, so buffered
  stderr/stdout always flush over a pipe. (1.1-D2)
- A bare `specwitness` with no arguments exits **64**, not 0. The spec does not
  cover this case; exit 0 means "merge-eligible" to the harness, so failing
  closed is the safer reading. (1.1-D3)
- The stubs *throw* `InfraError` rather than printing and exiting inline, which
  keeps exit-code knowledge in one file and guarantees a single print path.
  Observable behaviour is exactly what the spec prescribes. (1.1-D4)
- `--version` is inlined at build time by tsup `define` (mirrored in
  `vitest.config.ts`) rather than read from `package.json` at runtime, because
  the relative path differs between `src/` and `dist/`. An integration test
  asserts the emitted version equals `package.json`'s. (1.1-D5)
- `.gitignore`'s stale `.proofgate/runs/` entry was corrected to
  `.specwitness/runs/` (+ `scorecard.jsonl`, `*.tgz`). The old entry ignored
  nothing and the real run directory would have been committed. (1.1-D6)
- Two additions beyond the letter of the spec: `pnpm-workspace.yaml`
  (`allowBuilds` — without it esbuild has no binary and the build fails) and
  `scripts/pack-smoke.sh` (the AC3 tarball smoke test, extracted to a script so
  CI and a developer run exactly the same check).
