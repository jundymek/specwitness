### Codex review

`codex exec review --base epic/5-playwright-integration-environment-resolution`. **Two
findings, both real, both FIXED** — no dismissals, no escalations.

- **[P1] `src/surfaces/browser.ts` — assertion read errors were classified as product
  failures.** The generated driver wrapped every read in a `try/catch` that turned any
  Playwright exception into an ABSENT VALUE. So a page that crashed, closed or timed out
  WHILE BEING READ produced `outcome.ok = true` plus an unsatisfied assertion, and the
  criterion reported **product FAIL instead of infrastructure `error`** — the exact
  misclassification this story exists to prevent, arriving through the one door I had not
  guarded. Fixed: the read function now catches NOTHING. An ABSENCE (no element matches, or
  null text content) is a fact about the page and is reported as one; an EXCEPTION escapes
  to the driver's outer handler and becomes an `execError`. An unparseable selector escapes
  there too, which is correct — SpecWitness could not perform the read, so nothing was
  adjudicated, and exit 3 can never mint a pass. A new test PRODUCES the state with a real
  Playwright read exception and was verified red against the reintroduced catch (W10).
- **[P2] the exported `BROWSER_PROBE_TIMEOUT_MS` was dead, and the default outer bound
  ignored it.** Found independently while reviewing my own diff, minutes before the report
  landed; both descriptions agree. The spawn bound defaulted to `stepTimeoutMs + 30s`, so
  the exported 90-second constant had no effect and a legitimate multi-step scenario could
  exhaust the process bound while every individual step stayed inside its own. Fixed with an
  explicit `#bounds` method enforcing **step < test < spawn**, defaulting the outer bound to
  `BROWSER_PROBE_TIMEOUT_MS` and raising it if a caller's injected value would otherwise not
  exceed the inner test bound. The ordering is load-bearing and now says why: only the inner
  bounds produce a classified `execError` naming what hung, because the driver's `finally`
  still runs; the outer one kills a corpse.

**Re-review after those fixes: two further findings, one FIXED and one REPORTED.**

- **[P1] a verdict was drawn from the result file alone.** The driver writes its result in a
  `finally`, so `ok: true` can be on disk while the process is subsequently timed out, killed
  during teardown, or exits non-zero for a reason the driver never saw. That could report PASS
  for a browser that was killed. **Fixed:** a verdict now requires the driver's `ok` AND
  `result.outcome === 'completed' && result.exitCode === 0`; anything else is an `execError`
  naming the runner's own outcome. Verified red (W11); two new tests catch it.
- **[P1] the trace is stored unredacted, and it is machine-readable.** The distinction is
  sharper than the one I had written: a screenshot is pixels, while a trace is a zip of DOM
  snapshots, network requests and responses and console output, so a secret in it is greppable
  rather than merely visible. **NOT FIXED, and deliberately so** — the full reasoning is in this executor's own
  module header, under the redaction section, and in the PR body. AC1
  requires the trace (Q32), 5.6 needs it most for exactly the failing probes it will adapt,
  and a partial archive redactor would be worse than none by this module's own rule. It is a
  three-way tension between AC1, AD-10/Q49 and 5.6, which is a product decision with blast
  radius past this story, so it is **reported to the owner in the PR body** rather than
  silently accepted or silently closed. `sources: false` keeps the project's own source files
  out of the archive; the limitation is stated in the evidence member's `explanation` and
  rendered to reviewers by 5.3.

**Final round — three more findings, all real, all FIXED.** The owner had by then answered
the trace escalation (merge as-is, carried as pending-owner), so that finding was left exactly
as it was and is NOT re-opened here.

- **[P1] a click could leave the declared service origin (AD-3).** `goto` is validated as
  service-relative before any I/O, but a CLICK follows whatever the page put in an `href` —
  and the page is written by the system under verification. A provider-authored
  `click "a[href='https://production.example']"`, or a plain server-side redirect to another
  host, would have driven the verifier at an undeclared origin and then read that page as
  evidence. **This was the AD-3 hole of the story and I had missed it.** Fixed: the origin is
  re-checked after every navigation, after every step, and once more before any value is
  read; leaving it is an `execError` with zero assertions, so nothing from an undeclared host
  can become evidence. Two tests, both driving a real second fixture server on its own port.
- **[P1] tracing that could not START was swallowed**, into a field nothing read — so a probe
  with none of the trace evidence AC1 mandates could still report PASS. Fixed on both halves:
  the driver no longer catches `tracing.start`, and the executor refuses an attempt that
  observed the page but produced no trace.
- **[P2] the aggregate test bound did not scale with the number of operations.** It was fixed
  at `stepTimeoutMs + overhead`, so a scenario whose every operation finished inside its own
  documented 30-second bound could still be killed by the aggregate — a 20-second navigation
  and two 25-second actions add to 70 against a 60-second ceiling. That converts honest work
  into a spurious exit 3: this module's own headline misclassification, arriving through the
  timeout arithmetic rather than the classification code. Fixed by scaling with
  `1 + steps + reads`.
