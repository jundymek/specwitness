### ⚠️ Stage 4: your own sign-offs may be the last thing between your code and the epic branch

**This is the single most important paragraph in this spec, and it matters more here than in any other story in the epic — because you are the only story in the project that lets a provider modify an executable artifact.**

Until 2026-09-03 the harness documented *"Stage 4 (merge) deliberately does not exist — merging is always the owner's click."* It exists now, and this project carries the key (`SUPERVISOR_MERGE=1`, `~/.terminal-agents/config/projects/specwitness/project.env:213`).

The gate is **three factual conditions**, because `SECURITY_GATE=1` is also set here:

1. `codex_review` — `clean` or `addressed`, **and fresh**;
2. `security_check` — `clean` or `addressed`, **and fresh**;
3. the **rebase verdict** — `clean` (or absent).

The supervisor's judgement is **not among them**. It may decline and escalate, but it may never merge when a fact fails. **Your security sign-off may be the last thing between a provider-mutation path and the epic branch.** Sign off from the actual review report, never from a status line (Epic 3 action item e3-A's mitigation).

**"Fresh" is a CONTENT rule here, not a clock rule — and the harness's older docs describe the clock rule, which will mislead you.** Because this project declares `REVIEW_IGNORE_PATHS` (`project.env:189`), `verdict_is_stale()` (`~/.terminal-agents/lib/freshness.py:234-256`) takes its content branch: a verdict is fresh **iff the diff from the recorded `codex_review_commit`/`security_check_commit` to `HEAD`, restricted to the paths your branch touches, contains zero reviewable paths.** The clock is never consulted on this path. Committing only this spec, a `docs/findings/*.md` or `sprint-status.yaml` after signing off **keeps you fresh**; touching one line under `src/` or `tests/` **makes you stale**. The patterns are **fnmatch globs whose `*` crosses `/`** (`freshness.py:160-190`), so your spec **is** covered. **`CLAUDE.md` is deliberately NOT in that set** and always re-stales you.

**The rebase verdict** (`hooks/lib-pr-poll.sh:451-513`, invoked at 669-671, written at 690) is computed **only when an agent was told to rebase and did**; an agent that never owed one has **no key at all, and that passes** — absence is not `unknown`. ## Acceptance Criteria

From `docs/planning-artifacts/epics.md` § "Story 5.6" (authoritative — expand, never weaken):

1. **Given** a browser probe failing on element-not-found
   **When** `verify --adapt` is explicitly passed
   **Then** the provider may propose changes only to mechanics fields (schema-enforced: assertions/expected values structurally immutable in the adaptation payload), the proposal is applied to a plan copy, recorded in run metadata, and the run is marked `adapted: true` in report and JSON.
2. **Given** an adaptation proposal touching an assertion or expected value
   **When** validated
   **Then** it is rejected wholesale (test with adversarial fake provider), and the criterion keeps its original failure.
3. **Given** default invocation (no `--adapt`)
   **When** verify runs
   **Then** no adaptation is attempted (opt-in only; determinism default).

Clarifications (detail only, no weakening):

- **⚠️ THIS IS A SECURITY STORY THAT HAPPENS TO IMPROVE RESILIENCE, AND THE BOUNDARY IS ITS ENTIRE VALUE.** You are the **only story in the project** that lets a provider modify an executable artifact. Everything else a provider produces is a *draft* a human freezes or a *sentence* a human reads. Here a provider's output changes what gets executed on the next attempt. **The mechanics/assertions split exists for you, and it is recorded as existing for you in two merged files:**
  - `src/domain/plan.ts:46-52` — *"Every probe splits into `mechanics` (HOW to look…) and `assertions` (WHAT must be true). The split is structural so that Epic 5's mechanics-adaptation flow (FR-18, story 5.6) can be written to touch one sub-object and not the other: **a mechanics adaptation may alter mechanics fields only; assertion and expected-value fields are structurally read-only in that flow.** AI may adapt HOW, never WHAT."*
  - `src/schemas/plan.ts:331-338` — the same rule stated at the schema, *"load-bearing for Epic 5: story 5.6's mechanics-adaptation flow may alter mechanics fields only."*
  - **AD-2** states it as a spine invariant: *"Runtime mechanics adaptation (FR-18) may alter probe mechanics fields only (locators, navigation); assertion and expected-value fields are structurally read-only in that flow."*
  **The split is already built. Your job is to enforce it structurally.**
- **⚠️ "SCHEMA-ENFORCED" IS THE OPERATIVE PHRASE IN AC1 AND IT IS NOT NEGOTIABLE.** The immutability must be **structural — rejected wholesale by validation**, not by a reviewer, not by a prompt instruction, not by a post-hoc diff check that a future refactor could skip. Concretely: **the adaptation payload's schema must have nowhere to put an assertion or an expected value.** A `z.strictObject` carrying only mechanics fields makes an assertion edit an **unknown-key rejection**, which is the strongest form available — the same technique `src/schemas/plan.ts:458-462` already uses (*"A `needs-human` arm is a strict object with NO `probes` key, so attaching a probe to a human criterion fails as an unknown key rather than as a rule somebody remembered to write"*). **Follow that precedent exactly, and say in your header that you did.**
  - A prompt telling the provider not to touch assertions is **not** enforcement. Include it anyway — it improves the success rate — but never rely on it.
  - A validator that compares before/after and rejects differences is **weaker** than a payload that cannot express the difference. Prefer the latter; if you also do the former, say it is defence in depth, not the mechanism.
- **⚠️ VERIFY THE REJECTION TEST RED, AND SAY WHAT YOU PLANTED.** Epic 4 retro §2 observation 7 and §3 lesson 7: *a guard is only a guard once you have seen it fail* — two vacuous tests in one Epic 4 story, both passing against unfixed code, both caught only by planting the failure. **This applies with most force to your rejection test.** Neuter the validator (accept unknown keys; drop the strictness) and watch AC2's test go red. **PR #52 carried a table of six such plantings, each naming what was planted and what failed — write the same table.**
- **AC2's "adversarial fake provider" is a concrete requirement, and the tool for it is shipped.** `src/providers/fake.ts` is a **config-selectable product feature**, not a test double: its fixture format is `<mode>/<role>.json`, a JSON array of **raw response strings**, where call N returns entry N and the last entry repeats. Its own header says *"Its fixtures are deliberately allowed to be invalid; rejecting them is the gate's job."* **Write a fixture whose response proposes an assertion edit, and prove the whole pipeline rejects it wholesale and the criterion keeps its original failure.** Then write more: a payload changing an `expected` value; one adding an assertion; one removing one; one changing a probe's `id`, `surface` or `criterionId`; one proposing a **URL** where the plan may only carry a service id and a relative path (AD-3); one proposing a shell string. **Each must be refused, and none may partially apply.**
- **"Rejected wholesale" means exactly that: nothing partially applies.** A payload with one legal mechanics change and one illegal assertion change is **rejected entirely** — the legal half is not salvaged. FR-14's principle is already enforced by the merged gate through the type system (*"`parsed` exists only on the `ok: true` arm of `AgentResponse`"*), and `src/providers/invoke.ts:20-24` states the rule for rejected payloads: *"never parsed for partial data, never merged with a later attempt."* **Follow that; do not invent a merge.**
- **⚠️ THE PLAN COPY IS A HARD REQUIREMENT (AC1), AND THE FROZEN ORIGINAL IS NEVER TOUCHED.** The plan is persisted at `.specwitness/plans/<epic>.yaml`, committed to the target project's git (Q11), and **verified against the frozen contract's fingerprint at the edge** — `assertPlanMatchesContract` is named in `src/pipeline/stages/probes.ts:246-250`. ## Dev Notes

### Goal & Context

**You are the only story in this project that lets a provider modify an executable artifact, and your entire value is the boundary.**

The motivating case is real and small: a team relabels a button from "Create company" to "Add organization." No behaviour changed. A browser probe that located the button by its text fails on element-not-found, and SpecWitness reports a FAIL that is about a string, not about the system. FR-18 and brief §27 say a provider may propose a new locator — *how* to look — so that cosmetic drift does not manufacture false failures.

**The danger is one step past that, and it is the danger the whole product is built against.** A provider that may change *what must be true* can make any failing verification pass. That is not a slippery slope; it is one field away. The mechanics/assertions split exists precisely so that the dangerous edit has **nowhere to be written** — and both `src/domain/plan.ts:46-52` and `src/schemas/plan.ts:331-338` record, in merged code, that the split was built for this story.

**So the story is not "implement adaptation." It is "implement a boundary, and demonstrate that a hostile provider cannot cross it."** The resilience benefit is a consequence.

Three invariants carry it:

1. **Structural immutability.** Assertions and expected values are rejected by **validation**, not by a reviewer and not by a prompt. A `z.strictObject` with nowhere to put them.
2. **Nothing partially applies.** A payload with one illegal change is rejected entirely.
3. **The frozen artifacts are never touched.** The contract is not amended, the plan file is not written; adaptation lives on a copy, and the run says so.

### Failure modes (what "wrong" looks like here)

- **⚠️ An assertion or expected value that a provider can change.** The failure this story exists to make impossible. One field, and any failing verification can be made to pass.
- **Immutability enforced by a prompt, a reviewer, or a post-hoc diff** rather than by the schema. AC1 says *schema-enforced*, and the weaker forms all survive a refactor that the strong one does not.
- **A partially applied payload** — salvaging the legal half of a proposal that also tried something illegal. The merged gate's rule is that a rejected payload is never parsed for partial data.
- **Writing the adapted plan back to the project**, making the next run's provenance a lie and quietly changing what "the same verification" means.
- **Amending or touching the frozen contract.** That path exists, is explicit and audited, and is not yours.
- **Adaptation running without `--adapt`** — breaking FR-18/Q66 and spending quota nobody asked for.
- **Adapting an `execError`** — guessing at a locator while the browser is on fire.
- **A rejected proposal marked `adapted: true`**, or an accepted one that is not recorded. Both are lies about what the run did.
- **Presenting an adapted pass as an ordinary pass.** A human must be able to see that the pass required changing how the probe looked.
- **Confusing adaptation with retry/flake** — one word for two different things in the same report.
- **A URL, host or command string reaching the plan copy** through a mechanics field.
- **A leaked browser process tree** from your browser-bound tests (retro §2 observations 3 and 8).

### Completion Notes List

**The boundary.** `MechanicsAdaptationSchema` is a `z.strictObject` carrying `probeId` plus a
mechanics patch of `path` and `scenario` and nothing else. Assertions, expected values,
comparisons, assertion targets, probe `id`/`surface`/`criterionId`, URLs, hosts, commands,
`commandId` and `args` have **nowhere to be written** — an attempt is an unknown-key
rejection, following `src/schemas/plan.ts:458-462`'s precedent verbatim. The prompt also
states the prohibition, and the module header says in terms that the prompt is steering and
never the mechanism.

**`serviceId` is deliberately refused (D2)** even though it is a mechanics field, because
FR-18/AD-2 gloss the permitted surface as "(locators, navigation)" and `serviceId` is the
origin binding. Narrower than the merged mechanics type, on purpose.

**Nothing partially applies.** `attemptInvoke` is used rather than `invoke`, so an exhausted
budget is a value rather than a `ProviderError` — a refused adaptation therefore cannot move
the exit code (AC2). `applyAdaptation` validates every patch before constructing anything.

**The frozen artifacts are untouched.** The applier is pure and lives in `src/domain/`, which
has no file system in scope, so "the plan file is never written" is a property of the module
rather than a discipline. Asserted on serialized BYTES in three suites.

**An adaptation can only ever turn a `fail` into a `pass`.** The replacement result is taken
only when the re-derived criterion is `pass`; anything else leaves the original standing with
its original evidence. A hostile or incompetent proposal cannot introduce a new failure or
move the exit code in the bad direction.

**Deviations from the spec, both deliberate and both recorded:**

- **`src/pipeline/stages/probes.ts` is touched** (D1), which the spec's "Exact scope" does not
  list. AC1 requires the plan copy to be re-executed, and re-execution needs the worktree,
  the resolved services and the bound evidence sink — all of which exist only inside that
  stage. One additive optional `adapt` dep, injected from the edge exactly as `dispatch` and
  `retries` already are. When absent the stage collects nothing and calls nothing.
- **Three primitives are exported from `src/schemas/plan.ts`** (`Identifier`, `Prose`,
  `RelativePath`) so the payload imports the ONE definition of a service-relative path rather
  than copying its regex. That regex carries AD-3 and its comment records a backslash escape
  that nearly defeated it; a second copy would be a second thing to keep in step with a known
  attack. Export-only, no behaviour change.

**D12 was found, reported, and then CLOSED by owner decision — the largest change to this
story after the first commit.**

In 5.2's classification a missing element is an unsatisfied assertion when an ASSERTION reads
it, but an `execError` when a scenario STEP cannot find it — so the most obvious motivating
case, "the button was relabelled and the probe CLICKS it", was an `error` this story could not
adapt. Found by running, not reading (see Debug Log 2). I shipped it as a pending-owner
limitation because the safe fix touched a merged type; the supervisor put it to the owner and
argued against closing it, and the owner closed it anyway.

What that added: an optional, closed `reason` on `ProbeExecError`, established **where it is
known** — 5.2's generated driver, on a step failure, asks the page whether that selector
matched rather than reading Playwright's error text. *A missing element is a fact the page can
report; a dead browser is a page that cannot answer.* No prose matching anywhere, which was
the constraint that made D12 a limitation in the first place.

The candidate rule now admits exactly a step-target miss. A crash, a launch failure, a timeout
before the first assertion and — importantly — **an `execError` that states no reason** all
stay excluded; absence is never adaptable, which keeps every other surface and any future one
excluded by default.

**The invariant is re-stated rather than quietly widened.** It used to read "an adaptation may
only ever turn a `fail` into a `pass`". An `error` can now become a `pass` too. What survives
is that **an adapted run's verdict can only ever improve, never degrade**.

**⚠️ THE ROUND-4 FINDING IS THE ONE TO READ, because it was the real hole and it was not in
the payload schema.** My candidate rule admitted ANY unsatisfied assertion on a browser probe,
so a probe whose assertion read an existing but merely wrong value — the title says `Orders`
where the contract requires `Organizations` — was offered to the adapter. That is an ordinary
PRODUCT FAILURE, and offering it invites a provider to rewrite where the probe looks until the
UNCHANGED assertion passes somewhere else.

The payload schema cannot stop that: nothing about what must be true would be changing, so the
boundary it enforces is not engaged at all. The candidate rule is the only thing standing in
that door. The trigger is now one structured signal — a scenario STEP that could not find its
target — and every `fail` is excluded, including one whose assertion target was missing (that
target belongs to `assertions`, which adaptation may never change, so the only mechanics that
could fix it are ones that look elsewhere: the same laundering by a shorter route).

**Two consequences worth stating plainly.** The feature is narrower than the spec's framing
suggests — it adapts a probe that could not find a control it was told to click, and nothing
else; path drift is excluded because a renamed route is indistinguishable from a wrong page.
And **the owner's D12 closure is what makes the story work at all**: before it there was no
structured element-not-found signal, so the only candidates available were the assertion-based
ones — the unsafe half.

**Across fourteen review rounds, twenty-two findings, all fixed or dismissed with reasoning,
plus six I found by re-reading my own work afterwards** — nine of
them P1s on the story whose whole point is the boundary:

1. patches were validated against the whole PLAN rather than the offered candidates, so a
   hostile response could name a probe that PASSED and have provider-chosen mechanics executed
   against it;
2. the adapted re-execution restarted attempt numbering at 1 and therefore OVERWROTE the first
   pass's trace and screenshot — so a failed adaptation left the retained original failure
   pointing at the adapted run's evidence. *The criterion was preserved and its evidence was
   not, and only the first had a test:* the wave-2 pattern again;
3. mixed outcomes recorded only the successful changes, so executed-and-discarded ones vanished
   from the audit while the run was marked `adapted`.

**Two claims I had to correct rather than defects, and the pattern is worth naming.** Two of
the four review rounds found **overclaims**, not bugs: "depcruise proves the placement" and
"the adapted attempt list has exactly one attempt, so flaky is structurally false". Both were
true of the case in front of me and false in general, and neither could have been caught by a
test — the code was right and the prose was not. The planting discipline catches vacuous
guards; it does not catch a sentence that is too strong. Reviewers did.

The second: with `retries.browser` configured (5.4's feature), the adapted execution gets its
cycles too, so `flaky` CAN be true there. The behaviour is deliberate — flake within an
adapted execution is genuine flake of the SAME adapted probe — and the review's suggested fix
(force a single attempt) was declined with reasoning: a project that configured retries did so
because its browser is intermittent, which is exactly where adaptation matters most. The
cross-mechanics pair the supervisor's instruction actually named is still never built, at any
retry setting, and there is a test for that with retries ON.
