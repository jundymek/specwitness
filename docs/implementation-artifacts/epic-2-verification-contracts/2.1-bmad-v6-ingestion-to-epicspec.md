## Story

As a BMAD user,
I want SpecWitness to read my epic, stories, and acceptance criteria into a normalized EpicSpec,
so that contract generation is isolated from planning-artifact formats (FR-5, FR-6).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** configurable artifact roots (defaults `docs/planning-artifacts`; first-client override `docs/planning-artifacts` + `docs/implementation-artifacts`)
   **When** I ingest `epic-7` (input accepted as `7`, `epic-7`, or `epic-07`)
   **Then** the EpicSpec contains the epic id/title/goal and every story with its numbered acceptance criteria verbatim, with source file references.
2. **Given** per-story markdown files (`## Story`, `## Acceptance Criteria` numbered lists) and/or the epics file
   **When** either layout variant is present
   **Then** ingestion succeeds from both (fixtures for both variants).
3. **Given** an epic that cannot be found or parsed
   **When** ingestion runs
   **Then** an IngestError names what was searched and where (exit 3), and no empty EpicSpec is produced.
4. **Given** the EpicSpec type
   **When** downstream code is compiled
   **Then** no BMAD-specific types are imported outside `ingest/` (AD-1 boundary test).

Clarifications (detail only, no weakening):

- **AC1 epic id normalization is NOT yours to write.** `normalizeEpicId` already exists in `src/domain/ids.ts` (merged, story 1.2) and accepts `7` / `07` / `epic-7` / `EPIC-07` → canonical `epic-7`, throwing `UsageError` on anything else including `0`, negatives and unsafe integers. Call it; do not re-parse epic ids anywhere in `src/ingest/`.
- **AC1 roots come from config, never from a constant.** `config.planning.planningArtifacts` (default `docs/planning-artifacts`) and `config.planning.implementationArtifacts` (default `docs/implementation-artifacts`) are already declared, defaulted and validated in `src/config/schema.ts`. Ingestion takes the resolved config (or just the two root strings) as an argument — it must not call `loadConfig` itself, and must not hardcode `_bmad-output/` or the `docs/...` defaults.
- **AC1 "verbatim":** acceptance-criterion text is preserved exactly as written apart from trimming leading/trailing whitespace and the list marker itself (`1. `, `- `, `**Given**` prefixes stay). Do not normalize case, punctuation, or internal whitespace, and do not reflow. The contract author downstream reads these as the source of truth; a silently reworded criterion is the exact "correlated misunderstanding" failure this product exists to catch.
- **AC1 "source file references":** every story and every acceptance criterion carries the repo-relative path of the file it came from, plus a 1-based line number for where it starts. Relative to the project root passed in — never absolute, so an EpicSpec is portable and diffable.
- **AC2 both layouts, and both together.** Layout (a): the epics file `<planningArtifacts>/epics.md`, with `## Epic <n>: <title>` sections containing `### Story <n>.<m>: <title>` subsections and `**Acceptance Criteria:**` blocks (this repository's own `docs/planning-artifacts/epics.md` is the reference specimen — read it). Layout (b): per-story markdown at `<implementationArtifacts>/epic-<n>-<slug>/<task-id>.md` with `## Story` and `## Acceptance Criteria` (numbered list) headings (this repository's own `docs/implementation-artifacts/epic-1-*/*.md` are reference specimens). When BOTH are present for the same epic, per-story files WIN for the stories they cover (they are the later, more detailed artifact) and the epics file supplies the epic title/goal plus any story the per-story files do not cover. Record which source won for each story in that story's source reference. Ingesting an epic present in only one layout must succeed.
- **AC3 error content:** the `IngestError` message must name the canonical epic id, every path searched (both roots, both layout patterns, expanded), and what was found instead (e.g. "epics.md exists but contains no `## Epic 7`"). "Not found" without the search list is a failing implementation of this AC. `IngestError` already exists in `src/domain/errors.ts` — import it, do not define a new error class, and do not add a seventh AD-7 class.
- **AC3 "no empty EpicSpec":** an epic found with zero stories, or a story found with zero acceptance criteria, is an `IngestError`, not a successful empty result. Fail closed, then explain.
- **AC4 boundary:** add a `dependency-cruiser` rule confining `src/ingest/**` and add a unit test that proves the rule fires (plant a violation, observe red, revert) — `tests/unit/dependency-rules.test.ts` already establishes exactly that pattern and is the file to extend. A rule with no red-tested proof is not a guardrail; Epic 1's retrospective names this lesson explicitly.

### Architecture compliance

- **AD-1.** `src/domain/epic-spec.ts` imports nothing but sibling domain modules — no zod, no `node:fs`. The zod mirror lives in `src/schemas/`. `src/ingest/**` is application-layer: it may use `node:fs`, but nothing under `src/domain` or `src/schemas` may import from it.
- **AD-5.** `EpicSpec` carries `schemaVersion` from the registry. It is an in-memory model in V0 (nothing persists an EpicSpec to disk), but the version is part of the contract from day one.
- **Conventions.** Kebab-case filenames; PascalCase types; camelCase fields; ISO-8601 UTC for any timestamp; `ERROR:`/`HINT:` rendering is the CLI's job — you throw, you never print and you never set an exit code (`tests/unit/exit-location.test.ts` enforces this).

### Integration expectations

- **Story 2.6 (chuck) is your consumer.** It calls `ingestEpic` at the CLI edge after `loadConfig`, and hands the resulting `EpicSpec` to the contract-author provider. Your exported entry point should therefore be a plain function taking explicit arguments — no class, no builder, no module-level cache.
- Suggested shape (adjust names if you have a better reason; broadcast the final shape either way):
  ```ts
  export interface IngestInput {
    readonly projectRoot: string;
    readonly epicId: string;              // raw user input; normalized inside
    readonly planningArtifacts: string;   // repo-relative, from config
    readonly implementationArtifacts: string;
  }
  export function ingestEpic(input: IngestInput): EpicSpec;
  ```
- Epic exit criterion served: "Real BMAD epic (both layout variants) → draft contract" — your half is the ingestion of both variants.

### Failure modes to consider

- **Epic 10 vs epic 1 prefix collision.** `## Epic 1:` must not match when epic 10 was asked for, and `epic-1-slug/` must not match a request for `epic-11`. Anchor on the full number.
- **CRLF line endings and a BOM** in a checked-out artifact — normalize on read (strip a leading `﻿`, split on `\r?\n`) or your heading matcher silently finds nothing.
- **The two layouts differ in criterion syntax and the parser must handle each.** `<planningArtifacts>/epics.md` uses `**Acceptance Criteria:**` followed by unmarked `**Given**/**When**/**Then**` paragraph blocks — no list markers at all, one block = one criterion. Per-story files under `<implementationArtifacts>/` use `## Acceptance Criteria` with numbered `1.` items. Accept `- ` bullets in either. Both specimens are in this repository; read one of each before writing the parser.
- **A `## Acceptance Criteria` section followed immediately by another `##` heading** (empty section) — that is the AC3 zero-criteria error, not an empty array.
- **Symlinked or unreadable artifact directories** — an `EACCES` must surface as an `IngestError` naming the path, never as an unclassified crash (which would still exit 3, but with "this is a SpecWitness bug" text that misdirects the user).
- **A trailing `epic-7-something/` directory that is empty** — searched, found nothing, must be named in the error.

### Security

- Ingestion **reads files and nothing else**: no subprocess, no network, no environment reads, no writes. Nothing here may execute a project-declared command (AD-3), and nothing here may read outside the two configured roots under the given project root.
- Do not follow `..` out of the project root when expanding a configured root. A configured root that escapes the project root is a **`ConfigError`**, not an `IngestError`: the fault is in `.specwitness/config.yaml`, not in the planning artifacts. Both map to exit 3, but `INFRA_ERROR_CLASSIFICATIONS` in `src/domain/run-outcome.ts` carries `config` and `ingest` as distinct values that surface in run metadata and doctor — misclassifying sends the user to re-check the wrong thing. Name the resolved path either way.
- NFR-1 (no credential-store reads) is trivially satisfied here — do not touch the home directory at all.

- **The depcruise rule.** `src/ingest/` is application-layer, so model the new rule on the existing `adapters-core-only` rule but with the application layer's permissions. Two facts pinned by `tests/unit/dependency-rules.test.ts` that will save you a cycle: dependency-cruiser **does** substitute `$1` capture groups from `from.path` into `to.pathNot` (a Codex review claimed otherwise during Epic 1 and was wrong — verified three ways, see retrospective §2.3), and `src/infra/**` is deliberately allowed Node built-ins.  
  ```js
  {
    name: 'ingest-core-only',
    comment:
      'AD-1/Q2: src/ingest/** is application-layer. It may import src/domain/**, ' +
      'src/schemas/**, its own siblings and npm packages — never cli, config, ' +
      'infra, providers or surfaces. BMAD-specific types never leave this directory.',
    severity: 'error',
    from: { path: '^src/ingest/' },
    to: { path: '^src/', pathNot: ['^src/(domain|schemas|ingest)/'] },
  }
  ```
  Keep every existing rule byte-identical; one owner per guardrail.
