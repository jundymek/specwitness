## Story

As a story agent whose PR gate runs the suite while Codex runs it again,
I want `tests/unit/dependency-rules.test.ts` to be safe under concurrent runs in one worktree,
so that a green or red verdict from that file is about the rules and never about who else is running tests (retrospective "reproduce, do not trust").

## Acceptance Criteria

1. **Given** one worktree
   **When** two `vitest run tests/unit/dependency-rules.test.ts` processes are started concurrently and both complete
   **Then** both report every case passed, and a repeatable script in `scripts/` proves it (its output is pasted into the PR body).
2. **Given** every rule case the file carries at the time this story lands (14 as of PRs #9 and #11: `$1` sibling imports, `src/infra` built-ins, `src/schemas` zod/crypto/yaml, `src/ingest` rules, the cross-adapter, edge and side-effect blocks)
   **When** the suite runs
   **Then** every case still passes, and every case is shown to **discriminate** — it must be made to fail by a deliberate mutation, because a guard nobody has watched fail is not a guard. The mutation differs by case kind, and conflating them is why the first draft of this AC was unsatisfiable:
   - a **forbid** case (it asserts an import IS rejected) is discriminated by **deleting its rule** from `.dependency-cruiser.cjs` — the case must then go green-where-it-should-be-red, i.e. fail;
   - a **permit** case (it asserts a legitimate import is NOT rejected — `src/schemas` importing zod, `src/ingest` using Node built-ins, `canonical.ts` importing `node:crypto`) cannot be discriminated by deleting a rule: with the rule gone the import is still permitted and the case stays green. It is discriminated by **narrowing** the rule so the permitted import is no longer allowed — remove the allowance from the rule's `pathNot`/allowlist and the case must fail.
   - the `scratch-file cleanup is non-destructive` `describe` invokes no rule at all and is excluded from both.
   **Every rule case, not a sample of two.** The point of this AC is that the suite is trustworthy case by case, and a spot check on one forbid and one permit case would leave eleven guards unproven — which is the state this story exists to end. Each proof is one rule edit plus one targeted test run, so the whole set is minutes, not hours. Record the result as a table in the PR body: case name, mutation applied, observed failure. (Story 2.2's PR #13 is the worked example for a single rule, proving the crypto allowance in both directions — a permit case for `canonical.ts` and a forbid case for every other `src/schemas` module.)
3. **Given** any run of the suite — including one that is killed mid-case
   **When** it ends
   **Then** `git status --porcelain` under `src/` is empty: no scratch module ever remains where real source lives. Since a `SIGKILL` runs no `afterEach`, no signal handler and no other in-process cleanup, this AC can only be met by a design that never writes into the real `src/` at all.
4. **Given** `.dependency-cruiser.cjs` and the `pnpm depcruise` / `pnpm lint` scripts
   **When** this story merges
   **Then** they are byte-identical to before: this story changes how the rules are *tested*, never what they *are*.

Clarifications (detail only, no weakening):

- **AC1 "concurrently"** means two independent OS processes, not two vitest workers: the harness condition is a second `pnpm test` from Codex, not `fileParallelism`. A vitest `sequence` or `singleThread` setting does not satisfy this AC.
- **AC3 is the reason the fix is not "add a lock file".** A lock serialises the two runs but leaves the scratch-in-`src/` design in place, and a killed run then leaves both a probe and a stale lock behind. Prefer a design where the probes never touch the real `src/` at all.
- **Two known-viable designs, for the agent to choose from (state the choice and why in the PR body):**
  (a) **Per-test temp copy.** Copy into an OS temp directory per test (or per file), write probes there, run `depcruise src --config .dependency-cruiser.cjs` with `cwd` set to the copy. The rules' `^src/` anchors still match; nothing in the real tree is touched; concurrent processes have disjoint directories. Cost: a copy of `src/` per test (small — 59 modules).
      **Copy everything the config references, not just `src/` and the config itself.** `.dependency-cruiser.cjs:155` sets `tsConfig: { fileName: 'tsconfig.json' }` and `tsPreCompilationDeps: true`, both resolved relative to the cruise's working directory — so a temp copy without `tsconfig.json` either fails outright or, worse, silently cruises with different module resolution than the real tree, which would make every case pass for the wrong reason. Copy `tsconfig.json` too, confirm the module/dependency counts in the temp copy match the real `pnpm depcruise` output (68 modules / 170 dependencies at the time of writing), and assert that count in a test so a future config addition that this copy misses fails loudly instead of quietly weakening every case. `node_modules` needs to be reachable as well — symlink it rather than copying it.
  (b) **Programmatic API.** `import { cruise } from 'dependency-cruiser'` in-process on a temp copy — no subprocess, faster, same isolation as (a). Check that the installed version exports it and that the result shape is stable before committing to it.
  **Rejected: unique probe names under the real `src/`** (`__probe-<pid>-…` plus a cruise scoped to the probe files). It solves concurrency but cannot satisfy AC3: a `SIGKILL` between writing the probe and cleaning it up leaves the probe in the real tree, and nothing in-process can prevent that. Any design that writes into the real `src/` fails AC3 by construction.
- **AC2 "14 cases"** is a floor, not a count to assert on: count what is there when you start.

### Testing requirements

- **TDD:** the Task 1 script is the failing test — watch it fail before the rewrite.
- **Red-then-green on the guard itself** (AC2): delete one rule, observe the matching case fail, restore. A rewrite that accidentally cruises an empty directory passes everything and proves nothing.
- **Kill test** (AC3): start the suite, `kill -9` the vitest process mid-run, then `git status --porcelain src/` — empty.

### Failure modes to consider

- **Copying `src/` while an older, un-rewritten copy of this suite (another worktree's checkout, or a mid-rebase run) is still writing probes into it** — copy from the tracked tree only (`git ls-files src`), so a stray `__probe-*.ts` never enters the temp copy.
- **A temp copy that resolves differently from the real tree** — the failure that makes every case pass for the wrong reason, so it deserves the most care. `node_modules` must be reachable (symlink it; do not copy it) and `tsconfig.json` must be present, because `tsConfig` + `tsPreCompilationDeps` are what let the rules see type-only imports at all — the property `domain-is-dependency-free` rests on. Confirm the temp cruise reports the same module and dependency counts as the real `pnpm depcruise`, and assert those counts, so a future config addition this copy misses fails loudly. Test both a violating and a clean probe so a silently-empty cruise is caught.
- **Windows path separators** in the paths dependency-cruiser prints — unchanged from today; keep whatever normalisation the current helpers do.
- **A temp directory per test × 14 cases** costing noticeable seconds — measure; a per-file temp copy with per-test probe names is acceptable if isolation across processes is preserved.

### Security

- Test-only. Writes go to the OS temp directory and never to the real `src/`. No subprocess other than `depcruise`, which the file already spawns with an argument array. No environment reads, no network.
- `SECURITY_GATE=1`: `set-security-status.sh clean` with a one-line note (test-only, temp-dir writes, no new deps).

### Debug Log References

**RED (Task 1), before any change to the test.** `./scripts/concurrent-depcruise-check.sh`
reproduced the defect deterministically: `Tests 6 failed | 8 passed (14)` in run B,

**Design selection — (a) per-test temp copy + subprocess, not (b) programmatic API.**
Both were prototyped. Design (b) was rejected on evidence, in this order:

1. `cruise(['src'], { …, cwd: tempDir })` does **not** redirect the read. Deleting a
   real module from the copy left the module count at 85 and the module still listed:
   the cruise was reading the real repo the whole time. Every case would have passed
   for the wrong reason.
2. `cruise([absolutePathToCopy/src], …)` cruises the copy but emits relative paths
   (`../../../../var/folders/.../src/domain/errors.ts`), so the `^src/` anchors in
   every rule stop matching — 155 modules, **0** violations. A silent green.
3. `baseDir` (the documented option) cruised both trees at once: 154 modules,
   22 spurious violations.
4. Only `process.chdir()` into the copy worked, and that is process-global — it
   cannot be used from inside a vitest file that may run alongside others.

Design (a) with `execa(..., { cwd: tempCopy })` has none of these problems and keeps
the file's existing subprocess idiom.

**The finding that shaped the copy: `package.json` is required, not optional.** The
story anticipated `tsconfig.json` and a `node_modules` symlink. With only those, a
**clean** copy reports 5 violations of `schemas-core-only` — `src/schemas/*.ts → zod`
and `→ yaml`. Without `package.json` dependency-cruiser does not classify those edges
as `dependencyTypes: ['npm']`, so the `dependencyTypesNot: ['npm']` exemption in the
rule stops applying and the five legitimate core imports look like violations. This
is exactly the "passes for the wrong reason" failure mode the story warns about,
inverted, and it is why `COPIED_ROOT_FILES` carries `package.json` and why the
baseline test asserts the counts. `preserveSymlinks: true` was tried first and does
not fix it.

**Counts.** The story quotes 68 modules / 170 dependencies as the figure at writing
time; the tree has grown since. Real `pnpm depcruise` today: **85 modules, 246
dependencies**. The temp copy reproduces both exactly, and the baseline test compares
against a live `pnpm depcruise` rather than a hardcoded number, so growth does not
make it stale.

pnpm's environment. A test that is green because of how it was launched is the same
