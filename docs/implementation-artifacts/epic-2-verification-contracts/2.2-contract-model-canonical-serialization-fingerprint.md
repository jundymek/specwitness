## Story

As the product's trust anchor,
I want the Contract domain model with canonical serialization and SHA-256 fingerprinting,
so that freeze is verifiable and silent tampering is detectable (FR-8, FR-9, AD-5).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** a Contract (top-level `spec` — epic ref, version, criteria with id/statement/kind/severity/verifiability — and top-level `meta` — fingerprint, frozen flag, timestamps, version history; AD-5 partition)
   **When** it is serialized
   **Then** the YAML is human-readable/PR-reviewable, round-trips losslessly through the versioned zod schema (`schemaVersion` present), and criterion ids follow the canonical `E<n>-<NN>` format (`E7-01`).
2. **Given** the canonical serializer (sorted keys, LF, trimmed strings, hashing `spec` only — `meta` never fingerprinted)
   **When** the same content is fingerprinted twice — including after cosmetic YAML reformatting
   **Then** fingerprints are identical; any semantic change (one character in a statement) changes the fingerprint.
3. **Given** a frozen contract whose content was modified post-freeze
   **When** integrity validation runs
   **Then** an IntegrityError is raised (distinct from FAIL/PASS), matching Golden Corpus fixture 9 semantics.

Clarifications (detail only, no weakening):

- **AC1 the two top-level keys are exactly two.** A contract YAML file has `spec` and `meta` at the root and nothing else. The zod schema is `.strict()` at every level, matching the discipline `src/config/schema.ts` and `src/schemas/manifest.ts` already established: an unknown key is an error naming its path, never silently dropped. A dropped key in a *fingerprinted* document would be a silent expectation change.
- **AC1 criterion ids are not yours to format.** `buildCriterionId(epicNumber, sequence)`, `isCriterionId(value)` and `parseCriterionId(value)` already exist in `src/domain/ids.ts` (merged, story 1.2) and produce the frozen `E<n>-<NN>` shape — epic number unpadded, sequence zero-padded to a minimum of two digits, `E7-01`. The retrospective (§5.3) records this format as frozen with your story as its first consumer. Use these helpers in the schema's id refinement; do not write a second id regex.
- **AC1 the Kind / Severity / Verifiability vocabularies are closed and defined ONCE**, in `src/domain/contract.ts`, as `as const` arrays with derived union types — exactly the pattern `src/domain/result.ts` uses for `CRITERION_STATUSES`. The zod mirrors go in `src/schemas/`, derived from those arrays (never re-listed), with a test asserting `.options` deep-equals the source array — `tests/unit/schemas-enums.test.ts` is the existing precedent and the drift it prevents is real. Values, per the PRD Glossary:
  - `Kind` = `behavioral | integration | invariant | security | structural | performance | human`
  - `Severity` = `critical | normal`
  - `Verifiability` = `automated | human`
- **AC1 "round-trips losslessly":** parse(serialize(contract)) deep-equals the contract, and serialize(parse(yamlText)) is byte-identical to a canonically-written `yamlText`. Test both directions.
- **AC2 canonical form is defined once**, in `src/schemas/canonical.ts` (the spine names this file by path — it is not yours to relocate). It produces **canonical JSON of the `spec` block only**: recursively sorted object keys, array order preserved (criterion order is meaningful), strings trimmed, LF endings, no trailing newline ambiguity, no `undefined` members. The fingerprint is `sha256` of the UTF-8 bytes of that JSON, rendered lowercase hex. `node:crypto` **is currently rejected**, and by a rule you might not expect: not `no-side-effect-builtins-in-core` (`crypto` is absent from its `SIDE_EFFECT_BUILTINS` list) but `schemas-core-only`, whose `to: {pathNot: '^src/(domain|schemas)/', dependencyTypesNot: ['npm']}` matches because `node:crypto` is dependencyType `core`, not `npm`. Verified empirically by planting a probe module in `src/schemas/` and running `pnpm depcruise`:
  ```
  error schemas-core-only: src/schemas/__probe-crypto.ts → crypto
  ```
  So you **will** need a narrowly-scoped rule addition permitting `crypto` from `^src/schemas/`, with a comment naming AD-5 as the reason. Do **not** resolve this by moving the hash out of `src/schemas/` — AD-5 names `schemas/canonical.ts` as the single implementation — and do not weaken `schemas-core-only` itself.
- **AC2 "cosmetic YAML reformatting"** means: key order changed, quoting style changed, block vs flow scalars, comments added or removed, indentation changed, CRLF vs LF. All must yield the same fingerprint. Write one test per transformation, each parsing a hand-written reformatted fixture — not a programmatic re-dump, which would only prove your own serializer is deterministic.
- **AC2 `meta` is never hashed.** Freezing writes `meta.fingerprint`; recomputing must not include it (the trivial self-reference bug). Add an explicit test that mutating any `meta` field leaves the fingerprint unchanged, and that mutating any `spec` field changes it.
- **AC3 `IntegrityError` already exists** in `src/domain/errors.ts` — import it, never redefine it, and never add a seventh AD-7 class. It maps to exit 3 through `cli/exit.ts` with no new branch there.
- **AC3 "Golden Corpus fixture 9 semantics":** the corpus itself is Epic 6. What binds you is the *semantics*: an integrity failure is neither PASS nor FAIL; it is an infrastructure-class error, exit 3, with a message that says the content does not match the frozen fingerprint and a `HINT:` pointing at `git diff` on the contract file plus the amend flow. Do not create anything under `fixtures/corpus/`.
- **Contract versions are integers, monotonic** (spine Identifiers row). Version 1 is the first draft. Freezing does not bump the version; amending does (2.7 owns the amend flow and will call your primitives).

### Failure modes to consider

- **The self-referencing fingerprint.** Hashing a document that already contains `meta.fingerprint` — guard by hashing `spec` only, and prove it with the `meta`-mutation test.
- **JSON key ordering vs YAML key ordering.** They are different problems. Canonicalize the *data*, then hash; never hash the YAML text.
- **`JSON.stringify` and `undefined`.** An optional field present-as-`undefined` versus absent must hash identically — normalize before stringifying, and test it.
- **Number canonicalization.** `1` vs `1.0` vs `1e0` parse to the same JS number; ensure the version field is an integer in the schema so this cannot arise, and say so.
- **Unicode normalization forms.** Two visually identical strings in NFC vs NFD are different bytes and *should* produce different fingerprints (they are different content) — but decide explicitly, document the decision in the module header, and test it rather than leaving it accidental.
- **Trimming's blast radius.** "Trimmed strings" means leading/trailing whitespace on string values. It must not strip internal newlines from a multi-line criterion statement — that would silently alter a human's expectation.
- **A contract file hand-edited to remove `meta` entirely** — strict parse must reject with a path-naming message, not crash on a property access.

### Security

- Freeze is **tamper-evident, not tamper-proof** (ADR-005). Do not attempt signing, key storage, or any protection that would make the limitation seem stronger than it is; do not add a `--force`-style override to integrity validation. The honest limitation is recorded and deliberate.
- Nothing here executes anything, reads any environment variable, or touches the home directory.
- The fingerprint is not a secret; it is printed to stdout by 2.6 by design.

- **One cross-story shape confirmed rather than assumed.** After 2.7 reversed

  pinned from schema version 1 rather than resting on my care.

  null as a matter of course, so under my original reading a frozen contract's
