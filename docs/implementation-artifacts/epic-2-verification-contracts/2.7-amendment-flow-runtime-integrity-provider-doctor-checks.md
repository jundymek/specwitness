## Story

As the human authority over expected behavior,
I want contract changes to be possible only through an explicit, versioned, confirmed amendment — and provider readiness visible in doctor,
so that agents cannot silently redefine done (FR-9, FR-10, FR-3 completion; UJ-5; ADR-005).

## Acceptance Criteria

From `docs/planning-artifacts/epics.md` (authoritative — expand, never weaken):

1. **Given** a frozen contract
   **When** I run `specwitness contract epic-7 --amend` in an interactive terminal and confirm
   **Then** a new version is created referencing the superseded version, re-reviewed and re-frozen; the audit trail (who/when/what changed) is preserved in the contract file's version history.
2. **Given** a no-TTY context (agent invocation)
   **When** `--amend` is invoked
   **Then** it refuses with `ERROR:`/`HINT:` explaining amendments are an operator action (ADR-005 stance) — it does not fall back to a flag-only path.
3. **Given** doctor
   **When** run with providers configured
   **Then** per provider it reports: binary found, version, non-interactive capability, auth-appears-usable (probed only via the CLI's own public behavior — e.g. `codex doctor` / exit codes), configured mode, and ⚠ billing-risk env vars — without reading credential files (NFR-1).

Clarifications (detail only, no weakening):

- **AC1 the amend flow is: confirm → new version → re-freeze.** Concretely: verify the current contract's integrity first (a *tampered* contract is not amendable — restore it or the audit trail is meaningless); increment `meta.version` (integer, monotonic — spine Identifiers row); append a history entry recording the superseded version, its fingerprint, the timestamp, and the operator-supplied reason; clear the frozen state so the human can edit; and re-freeze via 2.2's pure `freeze`. Whether re-freezing is a second command invocation (`--freeze`) or part of the amend flow is your call — **state it in the module header and the PR body**, and make sure the file is never left in a state that is neither valid draft nor valid frozen contract.
- **AC1 "who": take the schema-compatible branch.** 2.2's history entry is fixed at `{version, fingerprint, timestamp, reason}` — **there is no author field**, and the bullet below forbids redesigning that shape unilaterally. V0 has no identity system and inventing one is out of scope, so record reason + timestamp and state in the schema comment that authorship is attested by **git history**, not by SpecWitness. If you believe an author field is genuinely required by AC1's "who", raise it with bob in the cohort thread **before** touching a merged schema — do not add it yourself, do not read environment variables looking for a username, and do not fabricate an author.
- **AC1 `meta.history`'s shape belongs to 2.2** and is in the schema from version 1. Populate it; do not redesign it. If bob's shape is genuinely missing a field you need, ask in the cohort thread before changing a merged schema — a shape change after freeze semantics exist is expensive.
- **AC2 no-TTY refusal is absolute** (ADR-005, PRD open question 3 resolved): detect a non-interactive stdin/stdout and refuse with `ERROR:` + `HINT:` explaining that amendment is an operator action. **There is deliberately no `--yes`, no `--confirm`, no `--force`, no environment-variable bypass — for anyone.** Do not add one "for tests"; test the TTY branch by injecting the TTY predicate, not by adding a flag to the product.
- **AC2 `--amend` is the second and last TTY-permitted command** (spine "Non-interactive first": only `init` confirm and `contract --amend` may block on input; every agent-callable command — `verify`, `plan`, `report`, `doctor`, `contract --status` — stays prompt-free). Note that story 1.4 ultimately made `init` prompt-free too, so **`--amend` is the only interactive path in the product**. Everything else you touch must stay prompt-free; adding a prompt to `--status` would break the harness.
- **AC1/AC2 the confirmation is a real confirmation:** it must show *what is changing* (at minimum the current version, its fingerprint, and the reason being recorded) before accepting. A blind "are you sure? [y/N]" is friction without information, and the friction is the point only when it carries the information the operator needs to say no.
- **AC3 provider checks plug into the merged registry via NEW check modules only.** `src/cli/doctor/registry.ts`, `context.ts`, `effects.ts` and the seven existing checks in `src/cli/doctor/checks/` are merged and **not yours to modify** — the seam was built for you and is already proven by `tests/unit/doctor/registry.test.ts`. Add new files under `src/cli/doctor/checks/` and register them in `checks/index.ts` (append; do not reorder the existing entries — order is part of that file's stated contract). If you need a new side effect, add it to `DoctorEffects` **additively**; if you need new context, add a field to `DoctorContext` **additively** — that single-object shape exists precisely so your addition breaks no existing check.
- **AC3 provider checks are OPTIONAL, never required.** A missing agent CLI must **warn**, never fail. UJ-4's edge case is explicit: with no agent CLI installed, contract *generation* is unavailable but execution of existing plans still works — so a missing provider must not make `doctor` exit 3. The `required: false` ⇒ warn ⇒ exit unchanged rule is already implemented in the merged registry and renderer; use it, and let the check's `detail` explain what is unavailable.
- **AC3 reuse the adapters' probes; do not write a third one.** 2.4 and 2.5 each expose a typed capability result and their auth probe (`codex doctor` for codex; exit codes of a trivial invocation for claude — Q58). Your checks call those. A second, doctor-only probe would drift from what an actual invocation does, which is the exact failure mode a diagnostic tool must not have.
- **AC3 billing-risk warnings name the variable** (FR-15, UJ-4): `⚠ OPENAI_API_KEY present in environment — provider calls could bill your API account; see provider modes`. This is a **warn**, not a fail. Note that the merged `tests/unit/doctor/credential-boundary.test.ts` asserts doctor reads **exactly one** environment variable, `PATH` — reading `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` will make that test fail, so you must **extend that assertion deliberately** to the explicit allow-list `['PATH', 'ANTHROPIC_API_KEY', 'OPENAI_API_KEY', ...configured equivalents]` and say in the test's comment why each is permitted. Widening it to "any variable" defeats the guard — keep it an exact list.
- **Runtime integrity (the story title's middle term):** wire 2.2's `verifyIntegrity` into the paths that exist today — `contract --status` reporting a mismatch honestly, and `--amend` refusing on a tampered contract. `verify` is Epic 3 and calls chuck's guard function; do not create it.

### Architecture compliance

- **AD-1.** `src/cli/doctor/**` is edge code and may use `execa`, `node:fs`, `node:net` — but route provider spawning through 2.3's `ProcessRunner` so probes and invocations cannot diverge. `src/authoring/**` is application layer and must not import `cli/`.
- **AD-4.** Capabilities probed and cached per session; auth readiness only via the CLIs' own public commands and exit codes; billing-risk variables reported and withheld from children; parent env never mutated; **no credential store is ever read**.
- **AD-5.** Contract versions integer monotonic; the amendment audit trail lives in `meta` (never fingerprinted, so amending does not perturb the `spec` hash of a version); provenance preserved.
- **AD-9.** No `new Date()` in `src/authoring/**`; the instant is injected. (Doctor itself takes the wall clock directly — the merged `doctor.ts` explains why: it produces no run id.)
- **ADR-002.** Exit codes only via `cli/exit.ts`; you throw, the edge classifies. A no-TTY `--amend` refusal is exit 3 (environment/policy class), not 64 — the invocation is well-formed, the context is wrong. State this reasoning in the module header.
- **Conventions.** ISO-8601 UTC; `ERROR:`/`HINT:` via the global handler; every agent-callable command stays prompt-free.

### Failure modes to consider

- **The no-TTY refusal accidentally being bypassable** — e.g. a `--reason` flag that skips the confirmation, or a check on `stdout.isTTY` only while the prompt reads stdin. Check the stream you actually read from, and add a test that the flag combination does *not* create a bypass.
- **An amend that leaves the file in a half state** (version bumped, history written, but not re-frozen, and the fingerprint now stale). Write atomically, and decide explicitly whether the post-amend file is a valid *draft* (recommended: yes, with `frozen: false` and the history intact) — never something `parseContract` rejects.
- **Amending a tampered contract**, which would launder the tampering into the audit trail as legitimate. Refuse: integrity first, always.
- **A doctor check throwing and taking the report down** — the merged registry already isolates checks (a throwing check reports `fail` with its detail), but a *provider* check reporting `fail` would change the exit code if you marked it required. Mark them all optional.
- **A provider probe hanging** — put a timeout on every spawn; the merged git checks use 5s and `checks/git.ts` holds the shared vocabulary for "missing / hung / said no". Follow that shape.
- **Doctor becoming slow** because each provider spawns two or three probes sequentially. Cache within the run; the registry is deliberately sequential, so keep individual probes cheap.
- **The credential-boundary test failing for a legitimate reason** and being "fixed" by loosening it to allow any env read. That would delete the guard. Extend it to an exact list.
- **A configured provider whose adapter is `fake`** — do not report it as a missing binary; report it as what it is.
- **No `ai` block at all in config** — no provider checks, no warnings, exit 0. That is a normal project state, not a diagnosis.

### Security

- **NFR-1 is the headline property of this story.** Auth readiness is probed exclusively through the CLIs' own public behavior (`codex doctor`, exit codes of a trivial invocation). No path reads `~/.claude/`, `~/.codex/`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `.netrc`, or any credential file. The AST guard enforces it; you keep the guard sharp by extending the env allow-list precisely rather than broadly.
- **ADR-005 is a security control, not a UX preference.** The no-TTY refusal with no escape hatch is what stops a coding agent from scripting a contract amendment. Do not add a bypass, and do not make the refusal conditional on anything an agent controls.
- **Billing safety:** report the variables, never their values. A warning that printed a key would be a credential leak into terminal scrollback and PR bodies.
- **No shell anywhere**; all probes go through `ProcessRunner` with argv arrays.
- `SECURITY_GATE=1`: this is the most security-relevant story in the epic — write a substantive `set-security-status.sh` note covering the no-TTY refusal's completeness, the credential-boundary allow-list change, and the absence of any bypass.
