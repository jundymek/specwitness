# The Golden Verification Corpus

This directory is SpecWitness's own quality gate. Each subdirectory is a small
application, a frozen contract that describes it, a precompiled plan that probes
it, and a **hand-written** `expected.json` saying what the real `specwitness`
binary must do when it verifies that application.

It exists because of one line in ADR-006 §4: *expected behavior can never be
derived from the implementation that is being judged.* Five epics of this
product's tests were written by the same agent that wrote the code they test, in
the same session, able to adjust either side until they agreed. That is normal
and it is not worthless, but it cannot answer the question this product exists to
ask. A corpus fixture can, because its expectation was written down first, by a
person, and cannot be edited while looking at the result.

---

## ⚠️ THE RULE THIS WHOLE DIRECTORY DEPENDS ON

**`expected.json` is hand-written. It is never generated by the code under test.**
(NFR-10, AD-12, brief §50.)

**There is no regeneration affordance, and there must never be one.** No
`--update-snapshots`. No `--write-expected`. No `UPDATE=1`. No
`pnpm corpus:bless`. Not as a convenience, not behind a flag, and not as a
comment showing how one would be written.

The reason is not tidiness. A red fixture is a **question** — either the product
changed behaviour, or the expectation was wrong — and answering it costs a human
five minutes of reading the run directory that the failure output names. A
regeneration button answers that question in one command, always in the product's
favour, and from then on the corpus records what SpecWitness currently does
rather than what it is supposed to do. There is no way back from that: once one
expectation has been machine-written, no reader can tell which ones still
weren't.

You will want the button. Whoever adds it will be helpful, reasonable, in a
hurry, and will have ended the corpus.

`tests/unit/corpus/no-regeneration-affordance.test.ts` asserts the absence of the
affordance. It is a weak test on purpose — it cannot catch every shape — and it
exists to put this argument in front of the person adding one, at the moment they
add it.

**What may be generated, and why that is different.** A fixture's frozen contract
carries a `fingerprint` produced ONCE, at authoring time, by
`specwitness contract <epic> --freeze`, and its plan repeats that fingerprint.
Those are **inputs**: the fingerprint is a hash the product must be able to
recompute from the contract's own bytes or refuse the run, and hand-computing
SHA-256 would prove nothing about anything. The **outcome** — verdict, exit code,
classification, criterion statuses — is what must never come from a run, and it
never does.

## ⚠️ TWO THINGS TO KNOW BEFORE YOU ADD A FIXTURE

**1. A fixture is committed executable content, not test data.** Its
`.specwitness/config.yaml` declares commands that a verification run will
execute (AD-3). This directory is the one place in the repository where that is
true. Adding a fixture is therefore a **security-relevant change** and should be
reviewed as one: keep every declared command trivially inspectable, local, and
obviously harmless; never `curl`, never a package install, never anything that
reads state from the machine running the suite. No fixture may contain a real
credential, token, or anything shaped like one — including in a comment showing
what would be redacted.

**2. `fixtures/corpus/` is NOT in `REVIEW_IGNORE_PATHS`.** For agents working
under the supervised-cohort harness this has a practical consequence that will
surprise you, because the path looks docs-shaped: **every fixture edit re-stales
your `codex_review` and `security_check` sign-offs**, exactly as an edit under
`src/` or `tests/` does. That is correct and deliberate — an `expected.json` is
the most security-relevant file in the epic, because it is the file that says
what a correct verdict looks like. Plan for it: land your fixtures, then sign
off, not the other way round.

## Layout

```
fixtures/corpus/
  README.md                       ← this file (not a fixture)
  <fixture-name>/
    expected.json                 ← HAND-WRITTEN. The whole point.
    project/                      ← copied to a temp workspace and verified
      .specwitness/
        config.yaml               ← declares gates, services, observations (AD-3)
        .gitignore                ← the shipped nested ignore (runs/, scorecard)
        contracts/<epic>.yaml     ← FROZEN, with a real fingerprint
        plans/<epic>.yaml         ← PRECOMPILED, referencing that fingerprint
      …the application itself…    ← any layout the config declares
```

Everything under `project/` is copied into a fresh `mkdtemp` workspace for each
run. The checked-in tree is read-only during a run and is asserted byte-identical
afterwards.

### Naming, and the fixture numbers

Fixtures that embody one of the **brief §7 defect classes** are named
`<nn>-<slug>`, where `nn` is that class's number. The allocation across Epic 6 is
fixed by `docs/planning-artifacts/epics.md`:

| numbers | story | what they are |
| --- | --- | --- |
| 1, 2, 3, 5, 10 | **6.2** | behavioural PASS/FAIL classes |
| 6, 7, 8, 9, 11 | **6.3** | classification: NEEDS_HUMAN, gate failure, InfraError, integrity, offline |
| (the non-Node one) | **6.4** | stack independence — a Python service, no `package.json` |

Fixtures that exist only to prove the RUNNER works carry a **non-numeric**
`runner-` prefix, so they cannot collide with an allocated class number. Story
6.1 shipped exactly two of them and deliberately built none of the numbered ones.

## `expected.json`, field by field

```jsonc
{
  "expectedVersion": 1,
  "fixture": "runner-pass",
  "why": "…prose: which brief §7 defect class this embodies and what it proves…",
  "proves": ["AC1", "NFR-10", "AD-12"],
  "command": ["verify", "epic-1", "--json"],
  "exitCode": 0,
  "outcome": { "verdict": "PASS" },
  "criteria": {
    "assertion": "exact",
    "statuses": { "E1-01": "pass", "E1-02": "pass" }
  },
  "stderrContains": [],
  "stderrAbsent": []
}
```

| field | required | meaning |
| --- | --- | --- |
| `expectedVersion` | yes | the format's own version, currently `1`. A future value is **refused**, never coerced. |
| `fixture` | yes | must equal the directory name. A copied expectation that still names its source is caught here. |
| `why` | yes | prose, at least a sentence. The defect class from brief §7 and the FR/AC this fixture proves. When it goes red in six months this is what tells the reader whether the fixture or the product is wrong — and that reader is not you. |
| `proves` | yes | requirement ids (`FR-…`, `NFR-…`, `AD-…`, `AC…`, `ADR-…`). |
| `command` | yes | argv passed to the built binary, after the binary. Each element is a separate argument — never a shell string (AD-3). |
| `exitCode` | yes | the **process** exit code (ADR-002: 0 PASS · 1 FAIL · 2 NEEDS_HUMAN · 3 infra · 64 usage). Pinned separately from `outcome` because the two are produced by different code paths. |
| `outcome` | yes | either `{"verdict": …, "gateFailed"?: …}` or `{"infraError": …}` — never both (AD-6). Compared as a whole object, so an unexpected `gateFailed` fails the fixture. |
| `criteria.assertion` | yes | `"exact"` or `"subset"`. **No default, on purpose** — see below. |
| `criteria.statuses` | yes | criterion id → `pass` / `fail` / `needs_human` / `skipped` / `error`. |
| `stderrContains` | no | substrings that must appear in **normalised** stderr. |
| `stderrAbsent` | no | substrings that must not. Assert a secret is ABSENT; never assert that `[REDACTED]` is present (Epic 3 retro §7). |

The file is validated strictly on load: an unknown key is an error, not a
silently ignored typo. A misspelled `exitcode` that parsed as "no exit-code
expectation" would leave a fixture asserting less than its author believed,
forever, while the suite stayed green.

### `exact` vs `subset` — why there is no default

A fixture that cares about one criterion should not have to enumerate the other
twelve. But **silence must never be readable as a claim**, so the file has to say
which it means:

- `"exact"` — *these are all of the criteria the run reported.* A criterion the
  run reports that the file does not list fails the fixture.
- `"subset"` — *these are the ones this fixture is about; it asserts nothing
  about the rest.*

Both are legitimate. Choosing is not optional.

### What is deliberately NOT assertable

Run ids, timestamps, durations, absolute paths, port numbers and commit shas are
**incidental**, not facts. A fixture that pinned one would fail on Tuesday, and a
corpus that fails for reasons nobody believes is a corpus the third person to
meet it disables.

They are therefore not comparable fields at all. Where they appear inside stderr,
the runner **normalises** them first (`tests/corpus/normalize.ts`), so a fixture
can pin the shape of a message without pinning its values:

| placeholder | replaces |
| --- | --- |
| `<RUN-ID>` | `run-<YYYYMMDDTHHmmssZ>-<4 base36>` |
| `<TIMESTAMP>` | any ISO-8601 UTC timestamp |
| `<SHA>` | a full 40-character git object id (an abbreviation is left alone) |
| `<PORT:name>` | a port allocated for that placeholder name |
| `<PROJECT>`, `<WORKSPACE>`, `<TMP>`, `<HOME>` | the run's own absolute paths |
| `<DURATION>` | any `durationMs`-style number, in the failure diff only |

**Normalisation never touches the decision.** Exit code, outcome and criterion
statuses are compared raw. Normalisation applies only to the failure diff and to
`stderrContains` / `stderrAbsent` matching — because a normaliser aggressive
enough to reach a verdict is a normaliser that can swallow a real difference, and
that failure is silent.

## Ports: `{{PORT:<name>}}`

A fixture that declares a service must **never** hardcode a port. Two runs of the
suite happen concurrently more often than you would think (the auto-review runs
`pnpm test` in the same worktree as the agent — harness defect H-8), and a fixed
port makes them fight.

Write `{{PORT:<name>}}` anywhere in any text file under `project/`. At
materialisation the runner allocates one fresh loopback port per distinct name
and substitutes it everywhere:

```yaml
services:
  app:
    run: node app/server.cjs {{PORT:app}}
    port: {{PORT:app}}
    ready:
      url: http://127.0.0.1:{{PORT:app}}/health
      timeoutSec: 30
```

The checked-in file keeps its placeholder forever; only the temp copy is
substituted. **Only loopback hosts may appear** in a fixture — the suite fails on
any other, and that check is what will meet an `https://api.example.com` in a
wave-2 config before CI does.

## What "hermetic" means here, and how each half is enforced

1. **No real providers.** Every fixture ships a precompiled plan, so `verify`
   compiles nothing and no provider is ever in scope (FR-18). Enforced twice:
   `providerUsage` must be empty in every run document, **and** `claude` /
   `codex` tripwire executables are placed first on `PATH` — an invocation leaves
   a marker file and fails the suite. Asserted, not assumed.
2. **No network beyond localhost.** Services bind `127.0.0.1` on a port
   allocated moments earlier. Nothing resolves a hostname, fetches a dependency
   or downloads a browser.
3. **No dependence on the developer's machine.** The binary runs with a
   *constructed* environment (`extendEnv: false`): `HOME` and `TMPDIR` point
   inside the fixture's own workspace, so `~/.claude/`, `~/.codex/` and every
   other credential store are not merely unread but **unreachable** (NFR-1, AD-4,
   Q59). Fixture text is also scanned for `$HOME` and credential-store paths.
4. **No leakage between fixtures.** Each fixture is copied into its own
   `mkdtemp` workspace, and the checked-in tree is hashed before and after the
   suite and asserted byte-identical.

And, one level above all of that: **the runner counts what it executed** and
compares it to the number of directories it discovered. An empty discovery is a
failure, not a pass. A directory it cannot parse is a failure, not a skip. A
fixture that does not run is a proof that does not exist, and a green suite that
ran nothing looks exactly like a green suite that ran everything.

## Adding a fixture

1. `mkdir fixtures/corpus/<nn>-<slug>/project` and build the smallest application
   that embodies the defect class. Node built-ins only, unless the fixture's
   whole point is that the target is not a Node project (story 6.4).
2. Write `.specwitness/config.yaml` by hand. Declare only what the fixture needs.
   Use `{{PORT:<name>}}` for every port.
3. Write `.specwitness/contracts/<epic>.yaml` by hand, `frozen: false` with a
   null fingerprint, then freeze it **once**:

   ```bash
   pnpm build
   cp -R fixtures/corpus/<name>/project /tmp/freeze && cd /tmp/freeze
   git init -q && node <repo>/dist/cli.js contract <epic> --freeze
   ```

   Copy the resulting `frozen: true`, `fingerprint:` and a hand-chosen fixed
   `frozenAt:` back into the checked-in contract, keeping your header comment.
   `--freeze` rewrites the file and strips leading comments, which is why the
   three fields are copied back rather than the whole file.
4. Write `.specwitness/plans/<epic>.yaml` by hand, repeating that fingerprint.
   **The plan probes for what the contract requires; the APP is what carries the
   defect.** A fixture whose plan is wrong fails too, and proves nothing about
   the class it claims.
5. Write `expected.json` **before you run anything**, by reasoning from the
   contract, the plan and the application. Then run
   `pnpm test:corpus`. If they disagree, work out which side is wrong. That
   moment — the disagreement, and having to decide — is the entire value of this
   directory.

## Running it

```bash
pnpm test:corpus     # just the corpus
pnpm test            # everything, corpus included
```

In CI the corpus is a separate required check, `corpus (ubuntu-latest)` and
`corpus (macos-latest)`, and it also runs inside the `verify` job's `pnpm test`.

When a fixture fails, the output names the fixture, its `why`, every mismatch,
and the **run directory** — open it. It is the evidence, and it is why the
failure is answerable rather than merely red.
